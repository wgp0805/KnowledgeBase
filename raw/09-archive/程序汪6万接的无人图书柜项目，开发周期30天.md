### 一、 核心技术选型与架构设计

#### 1\. 前端技术栈（微信小程序）

- **框架选择** ：推荐使用 **uni-app** （基于 Vue 语法）。相比原生开发，uni-app 在跨端部署、UI组件库（如 uView）集成以及生态扩展上更具优势，能大幅缩短开发周期。
- **核心交互** ：利用微信小程序的扫码API、RFID 读写器数据通信（若需与书柜近距离通信）以及微信订阅消息（用于还书成功、逾期提醒）。

#### 2\. 后端技术栈（Java）

- **基础框架** ：Spring Boot + MyBatis-Plus + MySQL + Redis。
- **计费与押金引擎** ：使用定时任务（XXL-JOB ）处理逾期计算，使用 Redis 缓存用户押金状态和图书实时状态，保证高并发下的数据一致性。
- **物联网通信** ：采用 **MQTT 协议** 作为云端与书柜中控主板的通信桥梁，实现毫秒级的指令下发与状态上报。

#### 3\. 硬件交互层（书柜端）

- **还书识别天线** ：在书柜外部特定区域（“还书感应区”）部署独立的RFID天线，专门用于识别用户拿在手里靠近柜子的书。
- **内部盘点天线** ：每个独立小柜门内部部署天线，用于确认书是否真正放入。
- **控制逻辑** ：书柜主板接收云端指令，控制电磁锁弹开，并实时将RFID读取结果反馈给云端。

### 二、 核心业务流程梳理

#### 1\. 用户注册与押金流程

- **微信授权登录** ：用户打开小程序，获取微信手机号和 OpenID 进行一键注册。
- **缴纳押金** ：系统校验用户是否为新用户，若是，则拉起微信支付，收取 100 元押金。
- **状态绑定** ：支付回调成功后，Java后端将用户状态更新为“正常可用”，并将押金信息存入数据库和 Redis。若用户后续退押金，需校验无未归还书籍且无欠款。

#### 2\. 借书核心流程（小程序选书 -> 自动开门）

- **扫码定位** ：用户在书柜前扫描柜体二维码，小程序获取书柜唯一编号（Cabinet\_ID）。
- **选书与校验** ：小程序展示该柜内的可用书籍列表。用户选择目标书籍点击“借阅”。后端校验用户押金状态、是否有逾期记录，并校验该书籍当前是否“在库”。
- **下发开柜指令** ：后端校验通过后，通过 MQTT 向对应书柜发送指令： `{action: "OPEN_DOOR", cabinet_id: "xxx", slot_id: "05", book_epc: "xxx"}` 。
- **取书与关门确认** ：书柜收到指令，05号柜门弹开。用户取书并关门。
- **状态变更** ：书柜主板检测到门已关闭，上报云端。后端将该书籍状态更新为“已借出”，生成借阅订单（记录借出时间），并通过微信订阅消息通知用户。

#### 3\. 还书核心流程（外部感应 -> 自动开门 -> 计费）

- **发起还书** ：用户在小程序点击“还书”，或直接在书柜屏幕/小程序上点击“我要还书”。
- **外部 RFID 识别** ：用户将贴有 RFID 标签的书籍 **靠近书柜外部的“还书感应区”** 。外部天线读取到书籍的 EPC 码，书柜主板将其上报给 Java 后端。
- **订单匹配与计费** ：后端接收到 EPC 码，匹配当前用户的借阅订单。根据公式： `费用 = (当前时间 - 借出时间) * 每日单价` ，计算应扣费用。
- **下发开柜指令** ：计费成功后，后端向书柜下发指令，打开与该书籍对应的 **内部空闲格口** 。
- **入柜确认** ：用户将书放入格口并关门。书柜内部天线盘点确认书籍已放入，上报云端。
- **订单完结** ：后端更新订单状态为“已归还”，记录归还时间。若产生费用，生成支付账单；若未产生费用，直接完结订单。

---

### 三、 关键难点与解决方案

#### 1\. 还书时的“外部感应”与“内部入柜”防作弊

- **痛点** ：用户可能只是把书靠近感应区，但并没有把书放进柜子里，导致订单被错误完结。
- **解决方案** ：采用 **“两步确认法”** 。外部天线识别仅作为“触发器”和“订单匹配器”，只有当内部天线在柜门关闭后， **再次读取到该 EPC 码** ，才真正触发订单完结和计费逻辑。如果外部识别了但内部没读到，系统会提示“请将书籍放入打开的柜门中”。

#### 2\. 按天计费的精度问题

- **痛点** ：如何定义“一天”？是自然日（0点结算）还是满24小时？
- **解决方案** ：在业务初期采用 **“满24小时计费”** （例如：借出时间为 10日 14:00，在 11日 14:00 前还书算1天，超过算2天）。在 Java 后端使用 `              ChronoUnit.HOURS.between()            ` 或 `Duration` 类进行精确的时间差计算，避免跨自然日带来的计费争议。

#### 3\. 押金扣除与退款逻辑

- **痛点** ：还书时如果产生费用，如何安全地扣除押金？
- **解决方案** ：
- **余额模式** ：做法是将 100 元押金作为用户的“账户余额”。还书计费时，直接扣除账户余额。当余额低于阈值80元时，提醒用户充值；当用户不再使用且无欠款时，允许申请退还剩余押金。
	- 直接支付：用户直接支付订单金额。

#### 4\. 硬件断网与弱网容灾

- **解决方案** ：书柜主板需具备本地缓存队列。当网络断开时，外部感应和内部盘点的 RFID 数据暂存在本地。网络恢复后，按时间戳顺序将数据推送到 Java 后端进行异步处理，确保计费不丢失、不漏算。
