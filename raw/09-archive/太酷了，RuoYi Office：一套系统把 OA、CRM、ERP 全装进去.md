程序汪 我是程序汪 *2026年11月24日 08:15*

一家公司业务稍微多点，系统就跟着多起来。OA 管考勤和审批，CRM 管客户，进销存再上一套 ERP，每套单独部署、单独维护，账号不通用，数据也不连。销售在 CRM 里签完合同，财务要照着再录一遍，仓库发什么货还得自己去问。问题不在某一套不好用，而在它们从根上就不是同一套。

RuoYi Office 想解决的就是这件事。这是个开源项目，把办公、人力、客户、合同、项目、进销存这些业务放进同一套组织和权限里，协议用的是 MIT。下面我从技术底子开始，按自己实际跑的顺序讲。

## 先说技术底子

后端是 Java 17 加 Spring Boot，持久层用 MyBatis-Plus，审批流程交给 Flowable。电脑前端是 Vue 3 加 TypeScript、基于 Vben Admin；手机端用 UniApp，同一套代码出 H5、App 和小程序。

比较实用的一点是， **同一套业务代码支持两种部署方式** 。团队小、想先跑起来，就用单体，一个 Spring Boot 应用直接启动，不需要额外组件。等业务量上来、要按模块独立扩容，再切到微服务模式：Spring Cloud Gateway 当统一入口，Nacos 同时管服务注册和配置，RocketMQ 处理异步消息，XXL-JOB 跑定时任务。这些组件不是一开始就全装上，而是按需要启用。

![图片](assets/%E5%A4%AA%E9%85%B7%E4%BA%86%EF%BC%8CRuoYi%20Office%EF%BC%9A%E4%B8%80%E5%A5%97%E7%B3%BB%E7%BB%9F%E6%8A%8A%20OA%E3%80%81CRM%E3%80%81ERP%20%E5%85%A8%E8%A3%85%E8%BF%9B%E5%8E%BB/9aec9c687b86d2987c1667d041cf7f96_MD5.png)

企业管理平台与智能体部署拓扑，含终端、网关、业务服务、数据与治理组件

数据层也比较常规：MySQL 存业务记录，Redis 做缓存和分布式锁，文件附件放 MinIO 或 OSS。因为是标准组合，技术团队接手不需要重新学一套陌生东西。

审批这块单独说一下。Flowable 负责流程怎么走——现在轮到谁、下一步到哪、不通过退回哪里；而合同、人事、资产这些模块只负责自己的单据字段和业务状态。两者分开，意味着不管哪个部门的申请，最后都能汇到同一张待办表，主管不用进五个系统各点一遍。

## 账号、权限、待办是同一套

我用演示账号登录，首页就是工作台。顶部导航把 OA、人力、合同、CRM、ERP、项目、资产排在一起，下面待办列表里同时躺着资产领用、合同发起、费用报销几种单据。每个人登录后看到什么菜单、什么数据，取决于岗位权限，但底层是同一个账号体系。

## 业务模块覆盖到什么程度

平台一共列了 21 个业务模块，我挑常用的列出来：

| 模块 | 用来做什么 |
| --- | --- |
| OA 协同办公 | 会议室、用车、用印、通知、文件 |
| HRM 人力资源 | 员工档案、入转调离、考勤、薪酬、绩效 |
| CRM 客户关系 | 线索、客户、联系人、商机、回款 |
| ERP 进销存 | 采购、销售、库存变化 |
| WMS 仓储管理 | 收发货、移库、盘点 |
| 合同 / 财务 | 合同台账、发票、费用、应收应付、凭证 |
| 项目 / 资产 | 任务工时里程碑、设备卡片与折旧 |

项目模块里，任务的起止时间画在同一条时间轴上，哪些先后、哪些并行，比翻一列日期直观。

## 智能体靠什么调真实业务

除了业务平台，项目还带一个能单独部署的 AgentOS。它通过 Spring AI 接入大模型，用 OAuth2 单点登录拿到当前员工身份，再去调用平台已经开放的业务接口。前端用 SSE 把处理过程一步步推到对话里，所以你能看到它正在查什么。

我实际跑了一遍会议预约。输入“我要预约一个会议室，6 个人，明天早上 9 点项目早会”，模型从口语里把时间、人数、时长提出来，交给会议查询能力，OA 再返回当时空闲的两间房，位置、座位数、要不要审批都列清楚。

![图片](assets/%E5%A4%AA%E9%85%B7%E4%BA%86%EF%BC%8CRuoYi%20Office%EF%BC%9A%E4%B8%80%E5%A5%97%E7%B3%BB%E7%BB%9F%E6%8A%8A%20OA%E3%80%81CRM%E3%80%81ERP%20%E5%85%A8%E8%A3%85%E8%BF%9B%E5%8E%BB/f4182580203d490a396157c1f36b9679_MD5.png)

对话查询空闲会议室，助手从 OA 查到两间符合条件的房间

我回复“选第 1 间”，系统没有立刻建单，而是先弹出确认信息，核对无误后才由业务服务保存，返回预约草稿和单号。这里有两个设计值得说：一是 **写入动作必须本人确认** ，模型不能直接替你下单；二是确认卡绑定了这次会话的结构化参数，点确认时用的是已保存的参数，不会让模型再猜一遍，网络重试时也有稳定的请求标识来识别是不是同一次操作。模型运行时还可以通过配置在 Spring AI 和 AgentScope 之间切换，不影响上层已经审核过的业务能力。

## 也得说几个问题

1. 开源版是 MIT，可以自己用和改，但平台分开源和商业版本，AgentOS 以及部分模块属于按需加购，具体范围以官方版本对照为准。
2. 智能体不是接个模型就什么都能办，能调用哪些业务，取决于对应接口有没有接入、审核上架，以及你有没有权限。
3. 项目 2026 年 4 月才建仓，还在快速迭代，接口和模块可能调整，重要项目建议先在非核心场景验证。
4. 上生产前自己把流程和数据完整跑一遍，演示界面好看不等于业务能直接用。

## 最后

整体看，受够了多套系统来回切、数据对不上的中小企业，尤其是想让 OA、CRM、ERP 共用一套账号和审批的，值得自己搭一套试试。先从单体起步，后面再按人数决定要不要上微服务和智能体，试错成本不高。
