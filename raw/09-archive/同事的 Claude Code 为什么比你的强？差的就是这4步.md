What Is Claude Code? A Beginner's Guide (2026) · Houtini

上个月，一位技术负责人问了我一个问题：

「我们团队两个人，用的是同一个 Claude Code、同一个模型，一个已经用 AI 把整个 App 端到端交付上线了，另一个还在每天手动补 AI 写的 bug。差别到底在哪？」

这个问题，最近一个月我听到太多次了。

「Harness」这个词开始在技术圈被反复提起，Agent 相关的面试题在 2026 年的面经里密集出现，很多人能顺畅地讲清楚 ReAct、LangGraph、Function Calling

但一旦面试官问： **「你的 [CLAUDE.md](http://claude.md/) 里写了什么？」「你的 Hook 拦过哪条命令？」** 不少人就安静了。

因为这两个问题，考的从来不是你会不会用 AI，而是 **你有没有把工程的经验，外化成了机制。**

大多数人还停在第一层：把 Claude Code 当成更快的 ChatGPT

有个判断方式很准： **看你每次开新对话时，要不要重新交代一遍项目背景。**

要交代，说明你还停在第一层——把 Claude Code 当成一个「能改代码的对话框」。不交代，说明你已经过了分水岭。

《Claude Code 实战》这本书里，把 AI 编程工具的定位讲得很透：

Copilot 的假设是「开发者知道怎么写，只是手速跟不上」；Cursor 的假设是「开发者知道改哪里，需要一个更精确的工具」；Claude Code 的假设是「开发者的瓶颈不是打字速度，而是把想法变成跨文件实现这个过程中的认知负担」。

三种假设，对应三种完全不同的工作流。前两种工具在解决「打字」这件事，第三种工具在解决「判断和执行之间的那一段路」。

书里给了一个非常实用的心态校准： **把 Claude Code 当成「30 秒给出 80% 可用代码草稿」的工具** ——剩下 20% 你来补，仍然比从零写 100% 快得多。抱着「一次到位」的期待用它，你只会持续失望。

而真正拉开差距的，是下面这四样东西。

第一样： [CLAUDE.md——给它长期记忆，而不是每次口述](http://claude.xn--md,-7n0aa9271e2sidlpt6i6uqlnc51sv8bo27iy0dh22dydpssx/)

[CLAUDE.md](http://claude.md/) 是每次会话自动加载的持久指令文件，分三层：

· **全局层** （ `~/.claude/             CLAUDE.md           ` ）：个人偏好，比如「注释用英文，文档用中文」  
· **项目层** （项目根目录）：技术栈、目录约定、禁止事项，通常提交到 Git 团队共享  
· **目录层** （子目录）：模块特有约定，Monorepo 项目特别有用

内层覆盖外层，越靠近代码的约定优先级越高。

关键认知是 **写什么** 。书里的原则很硬：

项目 [CLAUDE.md](http://claude.md/) 的价值，来自「项目做了特定选择、而 Claude Code 不知道」的地方。写错误的信息，比不写更糟——它会朝错误的方向工作。

所以不是把 README 搬进去（那是给人看的，对 AI 是噪声），而是写四类东西：

1\. **技术栈里「有多种选择、我们选了这种」** ——比如「认证用 jjwt，不是 java-jwt」  
2\. **目录结构与分层约定** ——「Controller 只调用 Service，不直接操作数据库」  
3\. **禁止事项**  
4\. **历史决策** ——「为什么没用 ORM」「为什么没上 Redis」

其中第 3 条，是全书我认为最值钱的一句话：

**「禁止的操作」是 [CLAUDE.md](http://claude.md/) 里投入产出比最高的部分。**

因为它会用它认为「合理」的方式解决问题，而「合理」未必符合你的项目约定。书里给的禁止事项长这样（这是作者踩过坑之后加的）：

```
- 不要在 Controller 层直接调用 Repository，必须通过 Service 层调用 - 不要使用 
            System.out.println，统一使用
           SLF4J logger - 不要引入新的 Maven 依赖，先和我确认 - 不要修改 src/lib/ 目录下的文件，除非明确讨论过
```

书里还专门对比了「有 [CLAUDE.md」和「没有」的实际效果：没有的时候，它会在项目规定用](http://CLAUDE.md」和「没有」的实际效果：没有的时候，它会在项目规定用) SLF4J 的情况下坚持 `              System.out.println            ` ，会在约定走 Service 层的项目里直接在 Controller 里写数据库查询，会随手引入 java-jwt——而项目用的是 jjwt。

它不是在捣乱，它只是不知道。

第二样：Hook——把「规则」变成纪律，而不是提醒

[CLAUDE.md](http://claude.md/) 有个天然上限： **它是软约束。** 写在里面的规范，靠模型「自觉遵守」。

想让某件事 **无条件发生** ，得用 Hook。

Hook 是在 Claude Code 生命周期固定节点执行的脚本，四个高频事件：

| 事件 | 触发时机 |
| --- | --- |
| PreToolUse | 工具调用前（ **可以拦截** ） |
| PostToolUse | 工具执行后 |
| Notification | 发送通知时 |
| Stop | 完成响应、即将停止时 |

书里给了三个最有价值的场景：

**场景一：写完代码自动格式化。** 把 PostToolUse 绑在 Write / Edit 上，它一改完文件立即格式化——代码风格问题当场消除，不会攒到 PR 审查时才被发现。

**场景二：危险文件保护。** 用 PreToolUse 拦住对 `.env` 、迁移文件、密钥配置的写入。你在对话里说「帮我给.env 加个注释」，改动在发生之前就被拦下，脚本信息回传给 Claude Code，它会换个方式继续，而不是反复重试。

**场景三：改完自动跑相关测试。** 从文件路径推断测试类名（ `              OrderService.java            ` → `OrderServiceTest` ），改完即跑。

两个容易被忽略的工程细节：

· **退出码语义** ：0 = 继续；非 0 = 它会收到警告并自行判断是否继续。它的设计哲学是—— **Hook 是把关人，不是拦截器。**  
· **性能红线** ：Hook 是同步执行的， **2 秒内返回，超过 5 秒会明显拖慢响应** 。耗时的检查（比如全量回归）交给命令手动触发，不要塞进 Hook。

第三样：Skill——把「每次都讲一遍的流程」，变成资产

你有没有过这种体验：

每次让它审代码，都要重新说一遍「先看正确性，再看安全，最后看可维护性」；每次调试，都要重新约定「先复现，再改，不许瞎猜」。

这些「每次都要重新交代」的流程，就是 Skill 要消除的东西。

一个 Skill 就是一个 `              SKILL.md            ` ，放在 `.claude/skills/<名称>/` 目录里。它的精妙之处在于 **渐进式披露** ：

Claude Code 平时只加载每个 Skill 的 description（一句话：做什么、何时用），不读正文；当你的请求和某个 description 匹配时，才把完整的 [SKILL.md](http://skill.md/) 读进上下文。

这意味着你可以沉淀几十个 Skill，平时几乎不占上下文。 **所以 description 写得好不好，直接决定它会不会在该用的时候被用上。**

书里的 `/review` 示例值得抄：

```
--- description: 多维代码审查。当用户要求审查改动、检查 diff，或在发 PR 请求前自检时使用。 argument-hint: "[可选重点，如 security / performance]" ---
```

注意 description 的写法——写的是 **用户会怎么说** （「审一下改动」「看下 diff」「发 PR 前自检」），而不是生硬的「代码审查」。这一句差异，决定它能否被自动触发。

正文里还有一行很酷的动态注入：`!'git diff HEAD'` ——技能被激活时，先执行这条命令把改动内容替换进来，等你看到审查结果时，diff 早就在上下文里了。

还有一条铁律，值得贴在显示器上：

Skill 最大的敌人是「写完不更新」—— **过期的 Skill 比没有更糟糕，因为它给的是错误的流程指导。**

第四样：子 Agent——当任务一个窗口装不下时，分工

前面三样解决「它懂不懂你的项目」，第四样解决「它一个人忙不过来」。

书里把子 Agent 存在的理由归为两个根本限制： **上下文窗口有限** ，以及 **注意力会随着职责数量稀释** 。一个 Agent 同时做审查、写测试、更新文档，每件事都在做，但没有一件能全力投入。

子 Agent 的机制要点：

· **无先验上下文** ：它只看任务描述，不看主对话历史——所以 **必须把背景写在任务书里**  
· **独立上下文窗口** ：主会话满了也不影响它，这是突破上下文瓶颈的关键  
· **独立工具权限** ：测试 Agent 只能写 `src/test/` ，绝不会误动 `src/main/`  
· **配合 git worktree 隔离** ：多个 Agent 各用独立工作目录和分支，互不干扰，最后合并回来

书里的经典模式是「并行多维代码审查」——把一次 review 拆成三个维度（正确性 / 安全性 / 可维护性），三个子 Agent 并行跑，各自只专注一件事。这是 **最轻量、最高价值、当天就能用上** 的一个模式。

但不要高估收益，书里把成本算得很清楚：

3 个各需 15 分钟的子任务并行执行，总耗时从 45 分钟压缩到约 18 分钟。代价是： **3 个子 Agent = 3 倍的 token 消耗** ，再加上任务分解、上下文传递、结果整合的协调开销。

判断标准也给了： **单个子任务预计超过 20 分钟、且子任务之间弱依赖时，才值得并行。只改 3 个文件的小任务，直接对话更快。**

地基：上下文管理，决定你能走多远

上面四样都是「配置」，但它们全建在一个地基上—— **上下文是有限资产** 。

书里有个比喻我很喜欢：

把上下文窗口想象成一张固定大小的桌面。每读一个文件、每聊一轮，就往桌面上摞一摞纸。桌面不会变大，纸摞得越高，抽出有用的那张纸越难。

它带来一个反直觉的事实： **Claude Code 在两次回复之间没有记忆** 。每按一次回车，到此刻为止的整段对话会被重新打包发给模型，它从头读一遍再生成下一句。所以—— **它不是「满了才出问题」，而是有效信息密度在持续下降。**

四个污染症状，出现前两个就该动手：

| 症状 | 典型表现 | 严重度 |
| --- | --- | --- |
| 记错信息 | 混淆两个文件的方法名、记错说过的约束 | 严重 |
| 重复否定方案 | 新实现里带着已明确否定的旧方案影子 | 严重 |
| 废话增多 | 大量「根据之前讨论的……」铺垫 | 轻度 |
| 响应变慢 | 从几秒变成十几秒 | 轻度 |

三个命令的决策树，建议直接背下来：

```
当前任务完成了？ ├── 是 + 下一个任务无关 → /clear ├── 是 + 下一个任务相关 → /compact └── 否（任务进行中）    → /compact 对话陷入死循环？          → /clear（无论任务是否完成）
```

书里还有一条跨天作战的技巧： **每天收工前写一份 `              session-notes.md            ` （任务、状态、已完成、进行中、已确认的技术决策、待确认问题、当前文件状态），第二天用 `/clear` 从快照重开，而不是用 `/resume` 。**

因为快照写的是昨天收工时的状态，文件可能被手动改过——先做状态核对，再继续工作。

最后一条，也是最重要的一条：判断权不能外包

看到这里，你可能会想：那是不是可以把一切都交给它？

书里在最后一章，把这件事说得很直白：

「人负责判断，Claude Code 负责执行」并非一句谦逊的话，而是对人机协作现实的准确描述。有一类任务，不是它能力不足，而是其核心是判断—— **而判断不能外包。**

被点名的三类任务：

· **架构选型** ：核心不是技术对比，而是权衡团队能力、业务预期、运维成本与扩展方向——这些约束只有当事人了解  
· **安全评审** ：它能扫描 SQL 注入、XSS 这类常见漏洞模式，但「这套权限设计是否符合团队的安全要求」，必须由人签字  
· **产品决策** ：它能给你一份看起来合理的优先级列表，但它不知道你的核心用户是谁、竞品在做什么、这个月最重要的事是什么

书里给的正确用法，一句话就能记住：

```
你：梳理单体架构 vs 微服务架构的技术利弊，不需要给出推荐，我自己来做决定。
```

回到最初那个问题——同样一个工具，为什么差距会越来越大？

因为这轮变化真正解放的是 **执行层** ，而不是 **判断层** 。

高级语言封装了寄存器分配，开源生态封装了基础模块，云计算封装了服务器运维。每一次封装，都让「一个人独立能做的事」上了一个台阶。

**判断——定义问题、权衡方案、确定边界——始终留给人。而这块判断力，恰恰是被解放出来的时间应该投进去的地方。**

所以别急着换更贵的模型。先花一个下午，做三件事：

**1.** 给它写一份 [CLAUDE.md，重点写「禁止事项」——这是投入产出比最高的一段](http://claude.xn--md,-8n0aa046vha2542dw9adiv9yxrau3bl63leklx9cyy0a9lb0qx69eh01arzn9h5ju1jg55bi5m/)

**2.** 装一个 Hook，先只做自动格式化，跑通链路

**3.** 把你在对话里说过三遍的那句流程，写成一个 [SKILL.md](http://skill.md/)

第四件事，是把三样东西提交到 Git—— **团队共享的那一刻，你才真正拥有了一支工程小队。**

---

在读这本书之前，你也许会觉得 AI 开发工具不过是少写一些样板代码。读完这本书之后你会发现，真正的转变不在于代码写得更快，而在于开始用不同的框架看待同一个问题： **什么是必须由人来判断的，什么是可以交出去的。** 这条线画在哪里，比任何工具的使用技巧都更重要。

全书分为五篇，按认知层次递进。

— **第 1篇** 先跑通对话，建立 “对话即开发环境”的心智模型。

— **第** **2** **篇** 讲如何管理上下文、建立项目记忆 — —这是多数人在实际使用中最先碰到的天花板。

— **第** **3** **篇** 接触真实工程的 “硬骨头”：大任务拆解、重构、测试、文档。

— **第** **4** **篇** 讲扩展能力 — —自定义命令、Hooks、MCP、子Agent — —把 Claude Code 从单点工具变成系统化工程。

— **第** **5** **篇** 用四个端到端项目和一个日常工作流实践，把全部方法论串成完整的产品线。
