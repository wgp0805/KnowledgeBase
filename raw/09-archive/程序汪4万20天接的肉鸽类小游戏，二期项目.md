### 项目背景

这是以前我们给甲方开发的线上街机项目，甲方感觉当下app功能比较单一，希望通过提升APP的可玩性与趣味性提升玩家在app的停留时长和日活数据，也是在同类产品中搞点差异化出来增加竞争力，另外从运营成本上讲甲方增加新游戏硬件设备成本太过高昂（一般几万），希望通过H5外接游戏，游戏方面的上手门槛不要太高，以休闲娱乐小游戏方向为主

## 3\. 总体架构

![图片](assets/%E7%A8%8B%E5%BA%8F%E6%B1%AA4%E4%B8%8720%E5%A4%A9%E6%8E%A5%E7%9A%84%E8%82%89%E9%B8%BD%E7%B1%BB%E5%B0%8F%E6%B8%B8%E6%88%8F%EF%BC%8C%E4%BA%8C%E6%9C%9F%E9%A1%B9%E7%9B%AE/dc4dc50690105ac8004d226928758831_MD5.png)

### 3.1 系统边界

**复用一期：**

- 用户 ID、登录态、实名结果、防沉迷结果。
- APP 埋点基础 SDK、设备信息、推送能力。
- 一期已有成熟的订单、地址、库存或物流模块，可直接复用。

**二期新增：**

- H5 游戏中心与 Cocos 游戏。
- 游戏会话、规则配置、服务端结算和回放验证。
- 礼品金币账本及余额投影，并向 APP 礼品商城提供统一余额。
- 礼品 SKU、库存预占、兑换订单和履约。
- 游戏专项风控、运营配置和数据看板。

**禁止耦合：**

- 二期服务不得直接依赖一期直播流、远控指令、街机设备连接状态。
- 二期发布、回滚和熔断不能影响一期主站和远程街机链路。

### 3.2 金币与 APP 礼品商城的统一方式

正确链路是游戏服务端调用钱包服务端入账，APP 和 H5 只是查询同一个账户：

![图片](assets/%E7%A8%8B%E5%BA%8F%E6%B1%AA4%E4%B8%8720%E5%A4%A9%E6%8E%A5%E7%9A%84%E8%82%89%E9%B8%BD%E7%B1%BB%E5%B0%8F%E6%B8%B8%E6%88%8F%EF%BC%8C%E4%BA%8C%E6%9C%9F%E9%A1%B9%E7%9B%AE/682d33229cf7cac941668238b20e09e4_MD5.png)

钱包接入按一期现状二选一：

| 一期金币现状 | 推荐接法 |
| --- | --- |
| APP 礼品商城已有“免费获得、专门兑礼”的金币 | 直接复用账户，新增来源 `H5_ROGUE_GAME` 、单局幂等键和每日上限 |
| APP 金币可充值、可投街机或承担其他付费价值 | 新建 `GIFT_COIN` ，前台可仍显示“金币”，但余额、流水和使用范围独立 |

这项选择必须在数据库设计前确定；不要先把两类金币混成一个余额，后续再拆账。

## 4\. APP 与 H5 接入方案

### 4.1 安全免登录流程

1. 玩家点击“玩小游戏领好礼”。
2. APP 调用 `POST /api/v2/game/launch` ，携带一期登录凭证。
3. 服务端校验账号状态、实名、防沉迷、活动资格，生成 60 秒有效且只能使用一次的 `launch_code` 。
4. APP 打开白名单域名： `              https://game.example.com/entry?code=xxx            ` 。
5. H5 立即通过 `POST /api/v2/game/auth/exchange` 换取短期访问令牌；换取后从地址栏移除 `code` 。
6. 访问令牌只保存在内存中，过期后通过受控 JSBridge 请求 APP 刷新，不把长期 token 放在 URL、localStorage 或日志中。

### 4.2 JSBridge 最小接口

| 方法 | 方向 | 用途 |
| --- | --- | --- |
| `getAppContext()` | H5 → APP | appVersion、platform、safeArea、locale、bridgeVersion |
| `refreshLaunchCode()` | H5 → APP | 登录续期，不返回长期凭证 |
| `closeGame()` | H5 → APP | 关闭页面 |
| `setOrientation(mode)` | H5 → APP | 锁定横竖屏，需白名单值 |
| `openNativePage(route, params)` | H5 → APP | 打开地址/客服等受控页面 |
| `showRewardedAd(request)` | H5 → APP | 调起 APP 原生激励视频，只返回广告任务 ID 和播放状态 |
| `reportClientEvent(event)` | H5 → APP | 补充端侧埋点，事件名白名单 |

桥接层必须版本化，限制来源域名、方法名和参数结构，禁止向 H5 暴露任意原生调用或任意 URL 跳转能力。Android/iOS WebView 应关闭非必要文件访问、调试能力和混合内容，线上只允许 HTTPS。

### 4.3 生命周期

- APP 切后台：Cocos 暂停逻辑帧和音频，记录本地检查点，同时向服务端发送 `pause` 。
- 恢复前台：先校验会话是否仍有效，再恢复游戏；超时会话进入结算中或失效页。
- WebView 被系统回收：允许通过服务端最近检查点恢复，MVP 可只恢复到最近关卡，而不是精确到每一帧。
- 返回键：战斗中先弹二次确认；退出后会话进入 `ABORTED` ，不得由客户端自行发金币。
- 弱网：事件分块保存在内存和受控临时缓存，按序重传，服务端按 `session_id + seq` 幂等接收。

## 5\. Cocos Creator 3.x 客户端方案

### 5.1 版本与构建

- 使用 Cocos Creator 3.8 LTS，并在仓库中固定到经过兼容测试的具体补丁版本，不跟随编辑器自动升级。官方 3.8 手册将其标记为 LTS，且支持 Web Mobile 发布。Cocos Creator 3.8 LTS 手册、Web 平台发布说明
- 构建目标为 `Web Mobile` ，按产品确认固定竖屏或横屏，不在战斗中动态旋转。
- WebGPU 不作为移动端生产依赖；官方 3.8 文档中的 WebGPU 仍针对 Web Desktop，移动 WebView 以 WebGL 兼容性为准。
- 编辑器版本、构建扩展、npm 依赖、资源导入参数全部纳入版本控制和 CI。

### 5.2 工程模块

```
assets/
  core/                 # 启动、网络、日志、事件总线、对象池
  game/
    config/             # 只读配置模型
    battle/             # 战斗系统、状态机
    actor/              # 玩家、怪物、技能、掉落
    roguelike/          # 随机房间、词条、选择逻辑
    replay/             # 输入记录、确定性随机、检查点
    ui/                 # 战斗 HUD、暂停、结果页
  bundles/
    common/             # 公共 UI、字体、音频
    season_x/           # 赛季与活动资源
  platform/             # H5 壳与 JSBridge 适配
```

关键规则：

- 玩法随机数统一使用服务端下发的 `seed` 和项目自定义确定性 PRNG，禁止在关键结算逻辑中直接使用 `              Math.random()            ` 。
- 金币规则不写死在客户端；客户端只展示服务端签名的 `rule_version` 和规则快照。
- 战斗采用固定逻辑步长；回放记录输入、选择和关键状态，不录制整帧画面。
- 表现层与数值层分离，回放验证可以在无渲染环境下运行核心数值逻辑。
- 将波次、怪物生成、伤害、升级、技能选择、Boss 和计分抽成不依赖 Cocos 节点/物理组件的纯 TypeScript `game-core` 包，由 Cocos 和 [Node.js](http://node.js/) 回放器共享；计分关键值使用整数或定点数，避免不同环境浮点漂移。

### 5.3 资源与首屏性能

Cocos 的 Asset Bundle 支持按需加载、远程 Bundle、预加载和版本 Hash，适合“启动壳 + 公共资源 + 赛季/关卡资源”的拆分。Asset Bundle 官方说明

拆分：

- `boot` ：启动场景、错误页、最小字体和加载动画。
- `common` ：通用 UI、玩家基础资源、核心音效。
- `gameplay` ：首个可玩关卡。
- `season_x` ：活动皮肤、后续怪物、非首局必需资源，放远程 Bundle。

性能目标（作为验收目标，不是引擎保证值）：

- 4G 中档 Android 冷启动 p75 首次可交互 ≤ 4 秒，p95 ≤ 7 秒。
- 首屏必需资源 gzip/brotli 后控制在 8 MB 内；非首局资源异步下载。
- 战斗帧率中档机稳定 45 FPS 以上，低端机可降级到 30 FPS。
- 内存峰值按目标 WebView 机型实测设线；必须覆盖连续游玩 30 分钟无持续增长。

优化手段：图集与 DrawCall 合并、对象池、弹幕和伤害数字上限、分帧生成、纹理分档、音频懒加载、减少运行时大对象和 JSON 解析、场景退出时释放对应 Bundle。

### 5.4 H5 业务壳与游戏画布分工

使用普通 H5 技术栈承载活动规则、金币到账状态和公告；Cocos 只承载加载页、战斗、技能选择和游戏内结果表现。礼品商城、地址、兑换订单和客服优先复用在线街机 APP 现有页面，H5 的“去兑换”通过 `openNativePage(giftMall)` 返回 APP。这样既降低 Cocos 首包，也避免在 H5 再建设一套商城和地址体系。

### 5.5 竖屏与页面改造

现有原型是竖屏肉鸽，设计分辨率固定为 720×1280 或 750×1334，战斗世界按宽度适配，顶部信息区与底部摇杆/武器区放在安全框内。APP 内使用沉浸式 WebView，禁止生产环境继续使用普通浏览器标题栏形态。

- 不只依赖 CSS `100vh` ；结合 `              window.visualViewport            ` 与 APP 下发的 `safeArea` 计算 Cocos 容器高度。
- iPhone 刘海/灵动岛、底部 Home Indicator 和 Android 手势区不得覆盖暂停键、技能、摇杆和武器按钮。
- 技能选择弹层出现时暂停战斗逻辑计时；若广告播放，服务端会话记录 `AD_PAUSED` ，广告时长不计入挑战时间。
- “尸潮来袭”等阶段事件由服务端规则版本和 seed 决定，事件 ID 写入回放流。
- “历史最佳”从服务端读取，按 `game_id + season_id + rule_version` 分区，避免规则调整后新旧成绩直接比较。

失败页将单一“金币 167”改为双阶段展示：

| 结算状态 | 页面展示 | 可执行操作 |
| --- | --- | --- |
| `LOCAL_RESULT` | 挑战时间、杀敌、等级、Boss、技能；金币显示“计算中” | 返回大厅、等待结算 |
| `VERIFYING` | “本局预计金币”，明确“审核中、暂未到账” | 返回 APP，后台继续结算 |
| `SETTLED` | “本局到账 +X”“APP 金币余额 Y” | 再来一局、去 APP 兑换 |
| `REJECTED` | “本局未通过结算”及可理解的原因码 | 申诉/客服，不展示虚假余额 |

“重新开始”必须重新向服务端创建 `session_id` ，不能沿用上一局；“去兑换”只负责打开 APP 礼品商城，不携带可修改的金币值。
