
> 场景：线上 Java 服务 CPU 突然飙到 400%，接口卡死，**优先保留现场，不要立刻重启** 排查链路：`进程 → 线程 → 堆栈 → 代码行`

## 一、整体排查思路

1. 不急于重启实例，重启会丢失线程现场，无法定位根因
2. 排查链路：找到高 CPU 进程 → 找到进程内高 CPU 线程 → 线程 ID 进制转换 → jstack 抓取堆栈 → 定位到具体代码行

## 二、分步操作命令

### 1. top 找到高 CPU Java 进程

```
top
```

观察 CPU 使用率，记录 Java 进程 PID。

### 2. 定位该进程下高 CPU 线程

```
top -Hp <PID>
```

- `-H`：显示线程
- `-p`：指定进程 PID 找到占用 CPU 最高的线程 ID（十进制）

### 3. 线程 ID 进制转换：十进制 → 十六进制

jstack 堆栈里线程 ID 是**十六进制**，需要把 top 拿到的十进制线程 ID 转 16 进制。 示例：

```
printf "%x\n" <十进制线程ID>
```

保存输出的十六进制线程编号。

### 4. jstack 抓取 Java 线程堆栈

```
jstack <PID> > stack.log
```

> 建议多抓 2~3 次，间隔 1 秒，方便区分是持续阻塞还是瞬时问题

### 5. 在堆栈文件中搜索十六进制线程 ID

打开 `stack.log`，搜索转换后的十六进制线程号，找到对应线程栈，直接定位到有问题的 Java 代码行。

## 三、常见根因参考

- 死循环：while/for 循环没有退出条件，大量消耗 CPU
- 复杂正则表达式回溯（灾难性回溯）
- 频繁 GC（可配合 jstat、jmap 辅助排查）
- 大量计算密集型逻辑，无限流

## 四、补充注意事项

1. 保留现场优先，重启会丢失线程栈信息，问题很难复现
2. 生产执行 jstack 对服务影响很小，可安全抓取
3. 如果怀疑 GC 问题，可搭配：

```
jstat -gc <PID> 1000
```

观察 GC 频率、FullGC 情况
