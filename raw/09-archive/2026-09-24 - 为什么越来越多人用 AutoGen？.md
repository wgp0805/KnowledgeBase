## 前言

> 当其他框架都在教AI“按流程办事”时，AutoGen让AI学会了“开会”

最近有小伙伴说，他们团队正在做一个合同审查系统。

需求本身不复杂：把一份采购合同丢进去，让AI找出其中的风险条款，标注出来，给个修改建议。

但他们试了好几种方案，都不太满意。

用单Agent方案，让一个大模型从头读到尾，结果模型经常“读到后面忘了前面”，而且它给出的判断里夹杂着大量幻觉。

用LangGraph画状态图，流程倒是清晰——先提取条款、再逐条分析、最后汇总建议。

但问题在于，“逐条分析”这个环节，每一条条款该怎么分析、该关注什么风险点，很难用固定的图结构表达清楚。

合同里可能藏着完全超出预设流程的陷阱。

技术负责人说了一句话，让他印象很深：“**我们需要的不是一个‘按流程办事’的系统，而是一个‘能开会讨论’的系统。** ”

这个需求，恰恰命中了AutoGen最核心的设计理念。

## 一、AutoGen到底是什么？

AutoGen是微软研究院在2023年末开源的多智能体对话框架。

它带来了一套完全不同的心智模型—— **智能体是对话的参与者，整个系统就是一个群聊，有时有结构，有时自由发挥**。

智能体之间可以委派任务、互相批评与纠正、调用工具、编写并执行代码、向人类发起询问，在目标达成后自行终止。

**没有任何一个中央控制器需要提前知晓完整计划。**

这套流程和人类解决复杂问题的方式高度吻合：分工、讨论、审查输出。

早期几个病毒式传播的demo——编码者加评审者加执行者联合解数学题、网络研究小组、股票分析团队——在许多任务上展现出比单智能体高**2到10倍**的表现。

**一句话说清：LangGraph是“流程图”，AutoGen是“会议室”。**

流程图适合确定性任务，每一步该做什么都提前画好。

会议室适合开放式任务，参与者根据讨论进展动态决定下一步。

## 二、一张图看懂AutoGen的架构

![](assets/2026-09-24%20-%20%E4%B8%BA%E4%BB%80%E4%B9%88%E8%B6%8A%E6%9D%A5%E8%B6%8A%E5%A4%9A%E4%BA%BA%E7%94%A8%20AutoGen%EF%BC%9F/a4053d6d2a65f2224da7ddf4b518445e_MD5.jpg)

AutoGen的核心机制是**群聊协作循环**：所有参与者共享一个对话上下文，每条消息被广播给所有Agent。

谁来发言由发言者选择策略决定——可以是轮询、随机、自动（由LLM决定谁最适合发言），或者手动指定。

每轮结束后检查终止条件：是否有人说了TERMINATE、是否达到最大轮次、是否目标达成。满足条件就结束对话，输出结果。

## 三、从“一个群聊”到“事件驱动”

2025年初，AutoGen发布了v0.4，这是一次从底层重写的架构级重构。

**同步API变成了异步事件驱动架构，0.2.x的代码在v0.4下无法运行**。

### 3.1 三层架构

v0.4把框架明确分成了三层：

| 层级 | 包名 | 定位 |
| --- | --- | --- |
| ** Core ** |  `autogen-core`  | 事件驱动Actor运行时 |
| ** AgentChat ** |  `autogen-agentchat`  | 高层多Agent对话API |
| ** Ext ** |  `autogen-ext`  | 可插拔扩展 |

**Core是管道和布线**，提供 `RoutedAgent` 、订阅、发布/订阅消息传递等底层原语。

**AgentChat是预制房屋**，提供 `AssistantAgent` 、 `UserProxyAgent` 、 `GroupChat` 等开箱即用的高层API。

**Ext是扩展坞**，提供OpenAI Assistant API、MCP工作台、gRPC分布式Agent等。

### 3.2 Actor模型

v0.4的核心是**异步事件驱动的Actor模型**。

每个Agent是一个独立的Actor，有自己的消息队列和状态，Agent之间通过异步消息通信，不再有中央协调器。

这个变化的直接收益：**更好的可扩展性**——Agent可以分布式部署在不同进程甚至不同机器上；

**更好的可观测性**——原生集成OpenTelemetry追踪，每一步消息传递都可追溯；

**更好的错误恢复**——Agent崩溃后可以从检查点恢复。

## 四、Java开发者怎么用AutoGen？

> 有些小伙伴可能会说：“AutoGen是Python框架，Java项目怎么办？”

AutoGen的核心是Python生态，但Java开发者有两条路可以走。

### 4.1 方案一：autogen4j（纯Java移植）

社区提供了多个Java移植版本。以 `autogen4j` 为例，它用Java 17+重新实现了AutoGen的核心抽象。

```
<dependency>
    <groupId>io.github.hamawhitegg</groupId>
    <artifactId>autogen4j-core</artifactId>
    <version>0.1.0</version>
</dependency>
```

**双Agent对话示例**：

```
// 创建AssistantAgent
var assistant = AssistantAgent.builder()
    .name("assistant")
    .build();

// 创建UserProxyAgent，配置代码执行
var codeExecutionConfig = CodeExecutionConfig.builder()
    .workDir("data/coding")
    .build();

var userProxy = UserProxyAgent.builder()
    .name("user_proxy")
    .humanInputMode(HumanInputMode.NEVER)
    .maxConsecutiveAutoReply(10)
    .isTerminationMsg(e -> e.getContent().strip().endsWith("TERMINATE"))
    .codeExecutionConfig(codeExecutionConfig)
    .build();

// 发起对话
userProxy.initiateChat(assistant, "What date is today? Compare the year-to-date gain for META and TESLA.");
```

**群聊示例**：

```
var codeExecutionConfig = CodeExecutionConfig.builder()
    .workDir("data/group_chat")
    .build();
// 创建GroupChat并添加多个Agent...
```

这个方案的优点是**纯Java实现、类型安全、与Spring Boot集成方便**。

缺点是**版本较旧，对应的是AutoGen 0.2.x的API**，与v0.4+的事件驱动架构不兼容。

### 4.2 方案二：Java调用Python Agent

如果你的项目已经用了Spring Boot，又想用上AutoGen v0.4+的新架构，最务实的方案是**Java做业务编排，Python做Agent运行时，两者通过REST/gRPC通信**。

这种“双栈融合”模式在企业级项目中越来越常见。

Java负责用户认证、数据持久化、事务管理、接口暴露这些企业级能力；

Python负责意图识别、任务拆解、多Agent协作这些AI能力。

![](assets/2026-09-24%20-%20%E4%B8%BA%E4%BB%80%E4%B9%88%E8%B6%8A%E6%9D%A5%E8%B6%8A%E5%A4%9A%E4%BA%BA%E7%94%A8%20AutoGen%EF%BC%9F/54de1f88fb73544f5e9afbb70dfa96f7_MD5.jpg)

**Java侧调用示例**：

```
@RestController
publicclass ContractReviewController {

    privatefinal RestTemplate restTemplate;

    @PostMapping("/review")
    public ReviewResult review(@RequestBody ContractRequest request) {
        // 调用Python AutoGen服务
        AgentRequest agentReq = AgentRequest.builder()
            .task("review_contract")
            .content(request.getContractText())
            .agents(List.of("risk_analyst", "legal_reviewer", "summarizer"))
            .maxRounds(10)
            .build();

        ResponseEntity<AgentResponse> response = restTemplate.postForEntity(
            "http://autogen-service:8000/agent/execute",
            agentReq,
            AgentResponse.class
        );

        return ReviewResult.from(response.getBody());
    }
}
```

## 五、AutoGen到底适合什么场景？

AutoGen的适用场景有一个清晰的边界：**当工作流天然是“对话”的形状，而不是“流程图”的形状。**

**合同审查**就是典型案例。

你把风险分析、法律合规、条款摘要三个Agent放进一个群聊，让它们围绕同一份合同讨论。风险分析Agent提出“这条违约金比例过高”，法律合规Agent回应“根据民法典第585条，违约金超过损失30%可能被认定过高”，摘要Agent负责记录共识。

**这个过程没有固定的执行顺序，参与者根据讨论进展动态发言。**

**金融交易系统**是另一个典型。

AutoGen可以用来搭建一个群聊，让市场分析Agent、风险控制Agent、执行Agent围绕一笔交易进行讨论和决策。

每个Agent可以调用不同的工具——行情查询、风控计算、订单执行——通过对话达成共识。

**但在以下场景，AutoGen不是最优选择**：

- 确定性流水线 ——如果每一步该做什么都提前确定了，LangGraph的状态图更清晰、更可控
- 极低延迟要求 ——AutoGen的对话式协作天然有多轮往返，延迟高于单次调用
- Token成本极度敏感 ——对话协作意味着多轮消息传递，Token消耗远高于单次Prompt

## 六、优缺点

### 优点

**1. 对话驱动，天然适合开放式任务**当工作流是“讨论式”而非“流水线式”时，GroupChat比状态图更自然。

**2. v0.4架构先进**异步事件驱动Actor模型，支持分布式部署、原生OpenTelemetry追踪、检查点恢复。

**3. 人类介入机制完善**Human-in-the-loop是原生支持的核心能力，不是事后补上的。

**4. 代码执行沙箱**UserProxyAgent内置代码执行能力，Agent可以写代码、跑代码、根据结果调整。

**5. AutoGen Studio低代码**提供拖拽式的Agent编排界面，不需要写代码就能搭建多Agent工作流。

**6. 微软官方背书**即使进入维护模式，bug修复和安全补丁仍在持续发布。

### 缺点

**1. Python优先，Java生态薄弱**核心框架是Python，Java只有社区维护的移植版本，版本落后。

**2. 已进入维护模式**不再新增功能，新项目应直接考虑MAF。

**3. 0.2.x与0.4+ API不兼容**老代码迁移成本高，网上大量教程还是0.2.x的写法。

**4. 对话式协作Token消耗高**多轮消息传递意味着Token消耗远高于单次调用。

**5. 不确定性较强**开放式的发言者选择机制可能导致对话跑偏，需要设计好的终止条件和引导策略。

## 七、适用场景

| 场景 | 推荐程度 | 理由 |
| --- | --- | --- |
| ** 开放式讨论/辩论 ** | ✅✅✅ 强烈推荐 | GroupChat天然适合多视角讨论 |
| ** 合同/文档审查 ** | ✅✅✅ 强烈推荐 | 多Agent从不同角度审查，互相补充 |
| ** 头脑风暴/方案设计 ** | ✅✅✅ 强烈推荐 | 多角色碰撞比单Agent更全面 |
| ** 需要人类介入的审批流 ** | ✅✅✅ 强烈推荐 | Human-in-the-loop原生支持 |
| ** 确定性流水线 ** | ⚠️ 需评估 | LangGraph的状态图更清晰 |
| ** 极低延迟要求 ** | ❌ 不推荐 | 对话式协作天然有多轮往返 |
| ** Java原生项目 ** | ⚠️ 需评估 | 建议双栈方案，或考虑MAF |

## 八、写在最后

回到最初的问题：**为什么越来越多人用AutoGen？**

答案其实不复杂—— **因为它把AI协作的“心智模型”从“流程图”变成了“会议室”。**

在LangGraph里，你画一张图，定义节点和边，指定流程走向。

一切都在你的掌控之中，但也意味着一切都在你的预设之中。

在AutoGen里，你给Agent定义角色，把它们放进一个群聊，让它们自己讨论。

流程不是预设的，是涌现的。

**你不再需要提前知道“第三步该做什么”，因为Agent会在讨论中自己决定。**

这套心智模型，恰恰匹配了人类解决复杂问题的真实方式。

合同审查也好，方案设计也好，头脑风暴也好，人类的做法从来不是“按流程图走”，而是“开会讨论”。
