# 多 Agent 协作开发框架（知识经验总结）

> 本文是一份通用的方法论文档，不绑定任何具体项目。任何人想用多个 AI agent 分工开发（不同工具协作，或同一工具的多个子 agent 协作），都可以直接照搬。

## 0. 这份文档解决什么问题

用多个 AI agent 分工开发时，常见三个痛点：

1. **角色越界**--Planner 顺手写了实现，Coder 顺手改了架构，Reviewer 顺手改了代码。
2. **靠对话协作**--agent 之间靠"记得刚才说过什么"传递信息，上下文一长就漂移、就丢失。
3. **互相包容**--同一个底层模型的多个子 agent 互相评审时，倾向"互相放水"，评审形同虚设。

本文给两套可照搬的框架：

- **框架 A**：跨工具协作（如 Claude Code + Codex）。
- **框架 B**：单工具多子 agent 协作 + 防"互相包容"。

## 1. 核心思想（三句话）

1. **不靠对话记忆协作，靠文件显式交接。** agent 之间的信息只通过磁盘上的 markdown 文件传递，不依赖任何一方的上下文记忆。
2. **角色靠硬约束切分，不靠自觉。** 每个角色定义里写死"不能做什么"，并用工具白名单做物理闸门。
3. **闭环靠客观验收，不靠互相认可。** 任务的完成判据是可独立核对的命令/断言全部通过，而不是某方说"我觉得 OK"。

## 2. 三个角色

| 角色 | 职责 | 产出 | 不能做 |
|------|------|------|--------|
| Planner | 需求拆解、接口设计、验收标准 | `spec.md` | 写实现代码 |
| Coder | 按 spec 实现 + 测试 | 代码 + `impl.md` | 改架构、扩范围 |
| Reviewer | 对照 spec 评审 | `review.md` | 直接改代码 |

**关键：三角色利益不完全一致。** Planner 为"可执行性"负责，Coder 为"按 spec 落地"负责，Reviewer 为"挑出问题"负责。Reviewer 的 KPI 是发现问题，不是让任务通过。

## 3. 角色定义（模板 + 完整示例）

### 3.1 模板的 7 个区块及其作用

每个角色一个定义文件，固定下面 7 块（最后一块可选）。每一块都不是格式装饰，而是有明确用途：

| 区块 | 作用 | 为什么必须有 | 写法要点 |
|------|------|-------------|---------|
| ① frontmatter（`name`/`description`/`tools`） | 给主 agent 的元信息：何时调用、能调什么 | `name` 是调用入口；`description` 决定主 agent 会不会在正确时机选它；`tools` 白名单是职责隔离的物理闸门 | description 写"什么时候用我"而非"我是谁"；tools 精确到能/不能，宁可少给 |
| ② 角色一句话定位 | 给子 agent 自己的身份证，一进来就锚定职责边界 | agent 没有持续自我意识，每次靠开头第一句定位 | 一句话，含"职责 + 对谁负责" |
| ③ 输入 | 明确"拿什么当依据"，限制信息来源 | 信息来源限制本身就是隔离手段（盲审的基础） | 列上游产物 + 必读规范；明确哪些是"辩词"不作依据 |
| ④ 产出 | 固定产出文件名 + 章节骨架，让下游能机械解析 | 文件交接要求结构稳定，下游要按章节核对 | 贴出章节骨架占位符 |
| ⑤ 硬约束 | 写死"不能做什么"，越界即违规 | 角色靠约束切分不靠自觉；agent 倾向"帮人把事做完"会越界 | 每条可验证（"不写实现逻辑"优于"保持克制"） |
| ⑥ 工作步骤 | 把流程固化成步骤，避免自由发挥顺序 | 顺序很关键（盲审就靠步骤顺序保证） | 编号步骤，含"读什么 → 干什么 → 交接给谁" |
| ⑦ 协作要点（可选） | 重申交接纪律，防止"聊着干" | 廉价但有效的反复强调 | 强调只走文件、规范唯一来源 |

**工具白名单是隔离的物理闸门，不是装饰：**

| 角色 | 应有 | 不应有 | 理由 |
|------|------|--------|------|
| Planner | Read/Write/Edit/Glob/Grep | Bash | 不能跑代码，避免顺手实现 |
| Coder | 全（含 shell） | -- | 要跑测试 |
| Reviewer | Read/Write/Glob/Grep + **Bash** | Edit | Bash 用于独立重跑验收命令；无 Edit 则不能改代码 |

> 工具白名单写错，整道隔离就形同虚设。最典型的错误：Reviewer 不给 Bash，导致它只能采信 Coder 的自证--这是"互相包容"最常见的入口。

### 3.2 完整示例：Planner

适用形式：subagent 定义文件（如 `.claude/agents/planner.md`）。

```markdown
---
name: planner
description: 需求拆解与规格编写。当用户提出一个功能需求、需要把模糊想法变成 Coder 可执行的 spec 时使用。产出 tasks/<id>/spec.md。
tools: Read, Write, Edit, Glob, Grep
---

# Planner 规划角色

你是本项目的规划者。职责是把用户需求拆解成 Coder 可直接执行的规格文档，对"可执行性"负责。

## 输入

- 用户的一句话或多句话需求（可能模糊）
- 必读：项目主指令文件、共享 convention 文件（技术栈与规范）

## 产出

`tasks/<id>/spec.md`，固定结构：

    # <任务标题>
    ## 背景          <一两句说明为什么做>
    ## 目标          <动词开头、可验证>
    ## 验收标准      <可独立核对的命令/断言，逐条 checkbox>
    ## 文件清单      <路径：职责，每行一个>
    ## 接口契约      <函数签名 / CLI 用法 / 输入输出示例>
    ## 测试要求      <必须覆盖的场景含边界>
    ## 边界情况      <明确不处理的场景>

## 硬约束

1. 不写实现代码。可写接口签名与示例 I/O，但不写实现逻辑。
2. spec 不清晰时停下来问用户，不要猜。
3. 任务粒度要小：一个独立功能点一个 spec。
4. 验收标准必须可被 Reviewer 逐条独立核对（避免"代码质量好"这种模糊表述）。

## 工作步骤

1. 读项目主指令与 convention 文件，了解技术栈与规范。
2. 确认需求边界，不清楚就问用户。
3. 在 tasks/ 下建目录（编号 001、002 递增 + 短横线描述）。
4. 写 spec.md。
5. 告诉用户 spec 已就绪，可交给 Coder。

## 协作要点

- 你与 Coder、Reviewer 通过 tasks/ 下文件交接，不靠对话记忆。
- 规范以共享 convention 文件为唯一来源。
```

**设计要点：**

- `tools` 不含 Bash -- 物理上不能跑代码，从源头避免"顺手实现"。
- 硬约束第 4 条把"可独立核对"作为验收标准的硬性要求 -- 这是整个防包容体系的入口，spec 这一步没卡住，后面 Reviewer 没法独立验证。
- 硬约束第 2 条"停下来问，不要猜" -- 防止 Planner 自己脑补需求塞进 spec。

### 3.3 完整示例：Coder

适用形式：执行类工具的角色指令文件（如 `AGENTS.md`，给 Codex 类工具）。这类工具通常默认带 shell，没有 frontmatter 的 `tools` 字段，靠硬约束做范围控制。

```markdown
# AGENTS.md - Coder 角色指令

你是 Coder，与 Planner、Reviewer 协作。按 Planner 产出的 spec 实现代码与测试，接受 Reviewer 评审。

## 工作流

1. 读 tasks/<id>/spec.md：目标、验收标准、文件清单、接口契约、测试要求。
2. 读共享 convention 文件：编码规范。
3. 实现代码与测试，只动 spec"文件清单"里列出的文件。
4. 写 tasks/<id>/impl.md，三段：
   - 改动文件：列出新增/修改的文件及一句话说明
   - 运行方式：怎么跑测试、怎么验证结果
   - 遗留疑问：spec 不清的地方、你做了哪些假设、待 Reviewer 确认的点
5. 等 Reviewer 产出 review.md。若有 Blocker，按建议修改后更新 impl.md，重新提交评审。

## 硬约束

1. 严格按 spec 实现，不扩大范围、不改架构、不添加 spec 未要求的"灵活性"。
2. spec 不清晰时标 TODO，并在 impl.md"遗留疑问"里列出，不猜。
3. 只改本任务文件清单内的文件，不动其他任务代码、不动配置类文件（除非 spec 明确要求）。
4. 闭环条件：review.md 结论为"通过"（无 Blocker）。Major/Minor 可在后续迭代处理。
5. 实现时不要顺手"改进"相邻代码、重构没坏的东西。

## 协作要点

- 你与 Planner、Reviewer 通过 tasks/ 下文件交接，不靠对话记忆。
- 规范以共享 convention 文件为唯一来源。
```

**设计要点：**

- 没有前置 `tools` 字段（执行类工具默认带 shell），所以靠硬约束第 3 条"只改清单内文件"做范围控制 -- 范围隔离从"工具白名单"换成"文件清单约束"。
- 硬约束第 2 条"标 TODO 列疑问，不猜" -- 让 Coder 的不确定性显式留在 impl.md，给 Reviewer 留把柄，而不是悄悄自己决定。
- impl.md 的三段结构是给 Reviewer 看的"自述" -- 但注意它只是辩词，不是通过依据（见 Reviewer 硬约束第 4 条）。

### 3.4 完整示例：Reviewer

适用形式：subagent 定义文件（如 `.claude/agents/reviewer.md`）。这份示例已内置防"互相包容"的对抗机制。

```markdown
---
name: reviewer
description: 代码评审。当任务代码实现完成后，对照 spec.md 与 convention 进行评审，产出 tasks/<id>/review.md。
tools: Read, Write, Glob, Grep, Bash
---

# Reviewer 评审角色

你是本项目的评审者。职责是对照 spec 检查实现质量，对"发现问题"负责，不对"让任务通过"负责。

## 输入

- tasks/<id>/spec.md：验收标准与接口契约
- 实际代码（src/ 下相关文件）
- tasks/<id>/impl.md：Coder 的实现说明（标注为"Coder 自述"，参考但不作通过依据）

## 产出

`tasks/<id>/review.md`，固定结构：

    # 评审：<任务标题>
    ## 结论                <通过 / 不通过>
    ## 验收标准核对        <逐条 [x]/[ ] + 证据>
    ## 问题清单
    ### Blocker（必须修，不通过）
    ### Major（强烈建议修）
    ### Minor（可选）
    ## 亮点（可选）

## 评审维度

1. 规范符合度
2. 正确性（满足 spec 接口契约与验收标准）
3. 简洁性（无过度工程、无用抽象）
4. 测试覆盖

## 硬约束

1. 不直接改代码。只提问题和建议，改是 Coder 的事。
2. 问题必须给 <文件:行> + 修改建议，不能只说"这里不好"。
3. 默认立场是怀疑：通过需要你主动为每条验收标准找到独立证据（自己跑命令 / 读断言），找不到证据就标 Blocker"未独立验证"，不得采信 impl.md 自述作为通过依据。
4. impl.md 的"验证情况/遗留疑问"是 Coder 的辩词，参考但不作豁免依据。
5. 结论只看 Blocker：有 Blocker 就不通过，否则通过（Major/Minor 不阻塞）。
6. 不为评审而评审--没有问题的维度不硬凑。

## 工作步骤

1. 读 spec.md 拿验收标准与接口契约（先不看 impl.md）。
2. 读代码，逐条独立核对，形成初步结论。
3. 再读 impl.md，仅用于核对 Coder 是否已自述已知问题。
4. 用 Bash 自己跑 spec 验收命令与测试套件，记录实跑结果。
5. 按维度找问题，分级。
6. 写 review.md，给出明确结论。

## 协作要点

- 只通过 tasks/ 文件交接，不靠对话。
- 规范以共享 convention 文件为唯一来源。
```

**设计要点（防包容三件全在这里）：**

- `tools` 含 Bash（独立重跑）但不含 Edit（不能改代码） -- 隔离的核心闸门。Bash 让它能自己跑验收命令，不靠 Coder 自证；无 Edit 让它只能提建议不能动手。
- 硬约束第 3、4 条是对抗性 prompt -- 默认怀疑、自述不作依据，把"包容"从道德问题变成"找不到独立证据就标 Blocker"的硬规则。
- 工作步骤第 1→2→3 步是盲审顺序 -- 先独立看 spec + 代码下结论，再看 Coder 的辩词，避免被辩词带偏。
- 工作步骤第 4 步是独立验证 -- 自己跑测试，把"通过"建立在实跑结果而非任何一方的说法上。

> 三份示例放一起看：Planner 用"无 Bash"卡住实现、Coder 用"文件清单"卡住范围、Reviewer 用"有 Bash 无 Edit + 对抗 prompt"卡住放水。三个角色的隔离手段各不相同，组合起来才形成完整闭环。

## 4. 项目目录骨架（通用）

```
项目根/
├─ <主 agent 指令文件>      # 如 CLAUDE.md / AGENTS.md，含角色表与流程
├─ docs/
│  └─ convention.md        # ★ 唯一规范来源，所有角色共用，防风格漂移
├─ <agents 配置目录>/       # 如 .claude/agents/
│  ├─ planner.md
│  └─ reviewer.md
└─ tasks/                  # ★ 消息总线
   ├─ README.md           # 交接契约说明
   └─ <编号>-<短描述>/
      ├─ spec.md          # Planner 产
      ├─ impl.md          # Coder 产
      └─ review.md        # Reviewer 产
```

**三个"唯一来源"原则：**

- 规范唯一来源 = 共享的 convention 文件。
- 消息总线唯一通道 = `tasks/` 目录。
- 闭环唯一判据 = `review.md` 结论"通过"（无 Blocker）。

## 5. 任务三件套契约

| 文件 | 产出者 | 必含章节 |
|------|--------|----------|
| `spec.md` | Planner | 背景 / 目标 / **验收标准（必须可独立核对）** / 文件清单 / 接口契约 / 测试要求 / 边界情况 |
| `impl.md` | Coder | 改动文件 / 运行方式 / 遗留疑问 |
| `review.md` | Reviewer | 结论 / 验收逐条核对 / 分级问题（Blocker/Major/Minor，每条带 `文件:行` + 修改建议）/ 亮点 |

**验收标准是整个体系的基石**，必须写成可独立核对的形态：

```
✅ 好的验收标准（可独立核对）：
- echo '{"a":1}' | <tool> format --lang json  输出 2 空格缩进多行，退出码 0，stderr 空
- <tool> foo  退出码 1，stderr 含 "unknown command"
- 测试套件全部通过，退出码 0

❌ 坏的验收标准（依赖主观判断）：
- 代码质量好
- 结构清晰
- 命名规范
```

验收标准不可独立核对，Reviewer 就只能"信任"某方的判断，互相包容就有了温床。

## 6. 协作流程

```
Planner ──> spec.md
Coder   ──> 代码 + impl.md
Reviewer ──> review.md
            ├ 通过（无 Blocker）──> 任务关闭
            └ 不通过 ──> Coder 按 review.md 改 ──> 重新 review
```

任务编号从 `001` 递增，一个独立功能点一个任务，粒度要小。

## 7. 单工具能否实现多 agent 协作？

**能。** 关键不在"用几个工具"，而在"隔离 + 对抗 + 文件交接 + 客观验收"四件事。

- **Claude Code 单独**：有 subagent 机制，每个 subagent 独立上下文、可限工具白名单，天然适合三角。
- **Codex 单独**：靠 `AGENTS.md` + 多个会话实例分饰角色。
- **其他 agent 工具**：只要支持"独立上下文 + 可配置系统提示 + 工具白名单"，都能做。

单工具的弱点是**同源模型容易互相包容**，需要框架 B 的对抗机制补强。

## 8. 防"互相包容"

### 8.1 为什么会互相包容

同源子 agent 互相放水，根源是四件事叠加：

1. **训练偏好同源**--同一家模型倾向礼貌、配合、肯定，看到"同类"的产出默认认可。
2. **共情偏差**--Reviewer 看到 impl.md 里 Coder 解释"环境受限/已尽力"，会代入对方视角放松标准。
3. **确认偏置**--拿到 spec + 代码，倾向于找"符合"而非"违反"。
4. **责任稀释**--Reviewer 知道"反正还能退回重改"，放水成本低。

### 8.2 防包容六层（从强到弱）

| 层 | 机制 | 具体做法 |
|----|------|----------|
| 1 | **客观验收闸门** | spec 验收标准 = 可独立执行的命令 + 退出码/输出断言；Reviewer 自己跑，不采信 Coder 自证 |
| 2 | **上下文隔离** | 子 agent 独立会话，不继承 Coder 思考历史；只读 spec + 代码 + impl.md（impl.md 标注为"自述"） |
| 3 | **盲审** | Reviewer 先不看 impl.md 的"遗留疑问/验证情况"独立下结论，再对照 Coder 自述 |
| 4 | **对抗性 prompt** | Reviewer 系统提示写死："默认立场是怀疑，通过需主动举证，举证不足 = Blocker" |
| 5 | **异构模型 / 红队** | Coder 与 Reviewer 用不同厂商模型；或派第二个"红队 reviewer"只挑 Blocker |
| 6 | **环境硬闭环** | 闭环条件含"干净环境跑通官方命令"；断网时的等价验证只能算"条件性通过"，必须联网复验才关闭 |

**第 1、6 层是硬骨头**：它们把"包容"从道德问题变成"跑不过测试"的物理事实。其余层是 prompt/流程层面补强。

### 8.3 单工具落地方案

**① Reviewer 加对抗性 prompt（写进角色定义的硬约束）：**

```markdown
## 硬约束
1. 不直接改代码，只提问题和建议。
2. 问题必须给 <文件:行> + 修改建议。
3. 默认立场是怀疑：通过需要你主动为每条验收标准找到独立证据
   （自己跑命令 / 读断言），找不到证据就标 Blocker"未独立验证"，
   不得采信 impl.md 的自述作为通过依据。
4. impl.md 的"验证情况/遗留疑问"是 Coder 的辩词，参考但不作豁免依据。
5. 不为评审而评审，没问题不硬凑。
```

**② 给 Reviewer 配 Bash 并限定用途：**

```yaml
tools: Read, Write, Glob, Grep, Bash
# 配套约束：Bash 只用于重跑 spec 验收命令与测试套件，
# 不得用于修改源码（改代码是 Coder 的事）。
```

没有 Bash 的 Reviewer 只能听 Coder 一面之词，这是最常见的包容缝隙。

**③ 盲审流程（在 Reviewer 工作步骤里写死顺序）：**

```
1. 读 spec.md 拿验收标准（先不看 impl.md）
2. 读代码，逐条独立核对，形成初步结论
3. 再读 impl.md，仅用于核对 Coder 是否已自述已知问题
4. 自己跑 spec 验收命令 + 测试，记录实跑结果
5. 写 review.md，结论只看 Blocker
```

**④ 红队 reviewer（重要任务用）：**

加一个 `red-team-reviewer`，工具只读，硬约束写死"只找 Blocker，不许说通过"。流程变双评审：

```
Planner ──> spec
Coder   ──> 代码 + impl
Reviewer(合规) ─┐
                ├─ 都通过才关闭；任一不通过回 Coder
RedTeam(挑刺) ──┘
```

**⑤ 异构模型（最狠，成本高）：** Coder 和 Reviewer 用不同厂商的模型，训练偏好不同，串通成本高。跨工具协作天然异构，本身就是防包容的优势。

## 9. 跨工具 vs 单工具 对照

| 维度 | 跨工具（如 Claude+Codex） | 单工具（同工具子 agent） |
|------|--------------------------|--------------------------|
| 隔离强度 | 高（不同工具天然物理隔离） | 中（靠子 agent 独立上下文） |
| 异构模型 | 天然异构（防包容加分） | 同源，需对抗 prompt 补偿 |
| Coder 能力 | 各取所长 | 取决于该工具 |
| 协作摩擦 | 两端规范要对齐 | 一端，无对齐成本 |
| 适合场景 | 真实项目、想体验多工具 | 学习协作机制、快速迭代 |

## 10. 可照搬清单

### 10.1 最小集（无论跨工具还是单工具，先做到这些）

- [ ] 三个角色定义文件，含工具白名单
- [ ] 共享的 `convention.md` 作为唯一规范来源
- [ ] `tasks/` 目录 + 三件套（spec/impl/review）
- [ ] spec 的验收标准全部可独立核对（命令 + 退出码/断言）
- [ ] Reviewer 有 Bash，能独立重跑验收命令
- [ ] 闭环判据 = review.md "通过" + 官方命令在干净环境实跑通过

### 10.2 防包容加固（在最小集之上）

- [ ] Reviewer 默认怀疑的对抗性 prompt
- [ ] 盲审顺序（先 spec+代码，后 impl.md）
- [ ] impl.md 的"验证情况"标注为 Coder 自述，不作通过依据
- [ ] 断网/受限环境的等价验证只算"条件性通过"，必须复验才关闭
- [ ] 重要任务加红队 reviewer

## 11. 常见坑

| 坑 | 表现 | 对策 |
|----|------|------|
| Reviewer 无 shell | 只能采信 Coder 自证，"条件性通过"永远不复验 | 给 Reviewer 配 Bash |
| 验收标准模糊 | "代码质量好""结构清晰" | 改成命令 + 退出码/断言 |
| 角色靠自觉 | Planner 顺手实现，Reviewer 顺手改代码 | 工具白名单物理闸门 |
| 靠对话协作 | "刚才说过的忘了" | 只走 tasks/ 文件 |
| 同源互相放水 | Reviewer 全票通过但问题没找 | 异构模型 / 红队 / 对抗 prompt |
| 闭环没复验 | 受限环境标"待复验"后无人跟进 | 闭环判据含"干净环境实跑通过" |
| 任务粒度过大 | 一个 spec 裹多个功能 | 一个独立功能点一个 spec |

---

**一句话总结：** 多 agent 协作的精髓是"文件交接 + 客观验收"。防互相包容补三件事就够：Reviewer 能独立重跑、Reviewer 默认怀疑、受限环境的"条件性通过"必须有复验才算闭环。
