## 一、面试坑点：不要一上来就说 MD5 哈希

很多同学第一反应：对长链接做 MD5，截取前 6/7 位当做短码。

**这个回答在高并发面试中很容易露馅，核心问题：哈希碰撞。**

1. **哈希碰撞风险**：两条完全不同的长链接，MD5 截取后得到相同短码。高并发场景下，小概率事件会必然发生，会导致跳转到错误地址。
2. **冲突处理逻辑复杂**：发生碰撞需要拼接随机字符重新哈希，增加数据库查询、重试逻辑，性能下降。
3. **不适合大规模生产**：MD5 哈希适合小型玩具项目，不适合亿级流量的短链接服务。

> 面试官真正考察的 3 点：
> 
> 1）如何生成全局唯一、无冲突的短码
> 
> 2）读多写少场景如何扛住高并发跳转
> 
> 3）重定向状态码 301/302 取舍、存储、缓存架构

## 二、核心方案：分布式发号器 + 62 进制 (Base62) 转换

### 1. 原理

1. 通过**分布式发号器**生成全局唯一递增十进制 ID；
2. 将十进制 ID 转换为**62 进制**，得到短码；

> 字符集：`0‑9 a‑z A‑Z`，合计 62 个字符。
> 
> 数学保证：ID 唯一，转换出来的短码就一定唯一，**从根源消除哈希碰撞**。

### 2. 容量计算

- 6 位 62 进制：`62^6 = 568亿`，绝大多数业务足够使用；
- 7 位 62 进制：`62^7 = 3.5万亿`，可支撑超大规模业务。

### 3. 分布式发号器如何实现

1. **数据库号段模式（推荐）**
    
    - 数据库维护一张号段表；
    - 应用一次性批量申请一大段 ID（例如 1~10000），放到内存用 AtomicLong 发放；
    - 号段消耗完，再去数据库取下一批；
    - 优点：极大降低数据库访问次数，写 QPS 大幅提升，实现简单。
    
2. 备选：雪花算法、百度 Leaf 分布式 ID 组件。

> 不推荐单机数据库自增 ID：存在单点故障、写入性能瓶颈，分布式环境下无法保证全局唯一。

### 4. Base62 转换简单逻辑

- ID (十进制) → 不断对 62 取余，映射到 62 字符集，拼接得到短码；
- 反向解析：短码还原回十进制 ID，再查询数据库。

> 注意：直接递增 ID 作为短码会被爬虫批量遍历，对外输出使用 Base62 混淆，避免 ID 直接暴露。

## 三、完整业务流程

### 流程 1：长链接生成短链接（写流程）

1. 校验长 URL 合法性，过滤恶意网址；
2. 判断长链接是否已经生成过短链，存在直接返回旧短链，避免重复生成；
3. 调用发号器获取全局唯一 ID；
4. ID 转 Base62 得到短码；
5. 数据库存储映射关系：`短码、原始长链接、创建时间、过期时间`；短码建立唯一索引；
6. 将`短码→长链接`写入 Redis 缓存；
7. 返回拼接好的短链接。

> 优化点：高并发下可以 MQ 异步落库，先返回结果，后台异步持久化。

### 流程 2：短链接跳转访问（读流程，系统性能瓶颈）

> 短链接是典型**读多写少**：生成一次，可能被访问百万次，性能重点在跳转读取。

1. 用户访问短链接，解析 url 拿到短码；
2. 优先查询 Redis 缓存：
    
    - ✅缓存命中：拿到长链接，执行重定向；异步埋点统计点击、UV、PV；
    - ❌缓存未命中：查询 MySQL 数据库；
        
        - 数据库不存在：返回 404；
        - 数据库存在：校验链接是否过期；有效则回写 Redis，执行重定向；过期返回 404。
        
    

> 数据库只做兜底，绝大多数请求走 Redis，保障高并发。

## 四、面试高频考点：重定向状态码 301 vs 302

表格

|状态码|含义|优缺点|短链业务选择|
|---|---|---|---|
|301|永久重定向|浏览器本地缓存，后续不再请求服务端；**无法统计点击量**|❌一般不用|
|302|临时重定向|每次访问都请求后端，可以统计访问数据；会多一次 http 请求|✅业务主流选择|

> 面试标准答案：
> 
> 默认使用**302 临时重定向**，因为短链接多用于营销推广，需要统计点击、UV、PV。只有极少永久不变的链接，才考虑使用 301。

## 五、数据库表设计参考

sql

```
CREATE TABLE short_url (
    id BIGINT PRIMARY KEY COMMENT '发号器原始ID',
    short_code VARCHAR(10) NOT NULL COMMENT '短码',
    long_url TEXT NOT NULL COMMENT '原始长链接',
    expire_time DATETIME COMMENT '过期时间，null代表永久有效',
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_short_code(short_code)
) ENGINE=InnoDB;
```

## 六、高并发与工程优化点

1. **Redis 缓存**：key = 短码，value = 长链接；设置合理 TTL，防止缓存雪崩 TTL 随机打散；热点短链可以叠加本地 Caffeine 缓存。
2. **过期策略**：支持链接过期；过期不立即删，惰性删除，访问时判断过期返回 404；后台定时任务清理过期数据。
3. **分库分表**：数据量巨大时，按照短码哈希分库分表，解决单表数据量瓶颈。
4. **安全风控**：校验长链接，拦截恶意、钓鱼网址；IP 限流，防止恶意刷短链。
5. **统计埋点**：点击数、访问来源、UV/PV，走 MQ 异步日志，不能同步阻塞跳转流程。
6. **布隆过滤器**：可以前置过滤不存在的短码，减少穿透到数据库的请求。

## 七、面试口述版回答（直接背）

> 面试官：请设计一个高并发短链接系统？

答：

短链接系统核心两个能力：长链生成短链，短链跳转回长链。

首先短码生成我不会直接用 MD5 哈希，因为会存在哈希碰撞问题，高并发下风险高。我会采用**分布式发号器 + Base62 (62 进制)**方案。通过号段模式的发号器生成全局唯一 ID，再把十进制 ID 转 62 进制得到短码，从根源保证短码不冲突，6 位短码就可以支持几百亿的数据量。

存储上数据库保存短码和长链接的映射，短码建立唯一索引。因为读流量远大于写流量，必须使用 Redis 做缓存，大部分跳转请求直接命中 Redis，数据库只做兜底。

跳转的时候状态码选择 302 临时重定向，保证能够统计点击数据。301 永久重定向浏览器会缓存，统计不到后续访问，业务场景很少使用。

另外还要考虑 URL 校验、过期时间、分库分表、限流风控，访问统计走 MQ 异步处理，不阻塞主流程。

## 八、拓展思考（面试官追问）

1. **缓存雪崩、缓存穿透怎么处理？**
    
    - 雪崩：TTL 随机；热点数据永不过期；
    - 穿透：布隆过滤器拦截不存在短码；缓存存空值。
    
2. **短链支持自定义短码怎么实现？**
    
    - 新增自定义字段，生成时优先校验自定义短码唯一性。
    
3. **Redis 挂了怎么办？**
    
    - 降级走数据库，服务性能下降，但功能可用；保证高可用 Redis 集群。
