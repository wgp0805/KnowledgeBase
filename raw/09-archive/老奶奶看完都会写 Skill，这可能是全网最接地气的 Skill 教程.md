这篇我尽量讲得直白些，看完你应该能自己写出第一个能跑的 Skill。

## 一、Skill 到底是什么

先说个场景。

假设你每周都要写一份周报，格式固定：先写本周完成了什么，再写下周计划，最后列风险项。每次你都得跟 AI 说一遍"帮我写周报，要包含这三部分，语气正式一点，不要用花哨的词"。

说了十几次之后你会想：能不能把这段话存起来，以后 AI 自己知道？

这就是 Skill。

**一句话解释：Skill 是一份写给 AI 看的操作说明书，告诉它在什么情况下、按什么步骤、做出什么结果。**

它和你平时打的字（Prompt）最大的区别是：Prompt 是一次性的，说完就没了；Skill 是常驻的，AI 每次遇到相关任务都会自动想起它。

再打个比方。Prompt 像你临时喊一嗓子"帮我倒杯水"，Skill 像你在冰箱上贴了张纸条："客人来了先倒水，用玻璃杯，要温水不要冰水。"下次不用你说，看到纸条就知道该怎么做。

![图片](assets/%E8%80%81%E5%A5%B6%E5%A5%B6%E7%9C%8B%E5%AE%8C%E9%83%BD%E4%BC%9A%E5%86%99%20Skill%EF%BC%8C%E8%BF%99%E5%8F%AF%E8%83%BD%E6%98%AF%E5%85%A8%E7%BD%91%E6%9C%80%E6%8E%A5%E5%9C%B0%E6%B0%94%E7%9A%84%20Skill%20%E6%95%99%E7%A8%8B/168ced0f2cdeaa5337fab14f2f38b06b_MD5.webp)

**它能帮你干什么：**

- • 把重复的要求固化下来，不用每次重说
- • 统一输出格式，这次和上次的结果长得一样
- • 把你的经验和偏好塞进去，AI 按你的习惯干活
- • 复杂流程分步骤，AI 不会做到一半跑偏

## 二、一个 Skill 长什么样

Skill 就是一个文件夹，里面放一个叫 `              SKILL.md            ` 的文件。就这么简单。

文件本身分两部分： **头部信息** 和 **正文** 。

先看一个完整的最小例子，你可以直接抄：

```
---
name: weekly-report
description: 写周报时使用。当用户说"写周报"、"总结这周"、
  "汇报一下进度"，或者需要整理一周工作产出时，都用这个技能。
---

# 周报生成

## 什么时候用

用户需要产出周报、周总结、进度汇报时。

## 怎么做

1. 先问用户这周做了哪几件事，如果对话里已经有信息就直接用
2. 按下面的结构整理内容
3. 写完通读一遍，删掉没有信息量的套话

## 输出格式

## 本周完成
- 用一句话描述结果，不写过程
- 有数据的地方带上数据

## 下周计划
- 每条都要能判断做没做完
- 不写"继续推进"这种没有终点的说法

## 风险与需要支持
- 没有就写"暂无"，不要硬凑

## 注意

语气平实，不用"赋能""抓手"这类词。宁可写得短，也不要用空话凑长度。
```

把这段存成 `              SKILL.md            ` ，放进指定目录，就能用了。

### 头部信息：最关键的两行

文件最上面被 `---` 包起来的部分叫 frontmatter，只需要填两个字段：

**name** ：技能的名字，用小写英文和连字符，比如 `weekly-report` 。

**description** ：这个技能是干什么的，以及 **什么时候该用它** 。

这两行是整个 Skill 里最重要的部分，重要到我要单独拿一节讲。

### 正文：告诉 AI 具体怎么做

正文就是普通的 Markdown，你怎么写都行，但通常要说清三件事：

- • **什么时候用** （When）：适用场景，以及什么情况下不该用
- • **怎么做** （How）：具体步骤
- • **产出什么** （What）：输出的格式长什么样

如果有固定格式要求，直接把模板贴进去，比用文字描述有效得多。

## 三、文件放在哪

不同工具位置不一样，但结构都一样：

| 工具 | 路径 |
| --- | --- |
| Claude Code | `~/.claude/skills/技能名/             SKILL.md           ` |
| Codex | `~/.codex/skills/技能名/             SKILL.md           ` |

`~` 是你的用户目录。以周报为例，完整路径就是 `~/.claude/skills/weekly-report/             SKILL.md           ` 。

注意文件名必须是 `              SKILL.md            ` ，全大写，不能改。文件夹名随意，但建议和 name 保持一致，方便自己找。

放好之后重启一下工具，跟 AI 说"帮我写个周报"，它就会自动用上。

## 四、description 决定了它会不会被用

这节最关键，很多人第一个 Skill 写完发现 AI 根本不理，问题基本都出在这。

**原因是这样的：** AI 平时并不会读你的 [SKILL.md](http://skill.md/) 正文，它只能看到 name 和 description 这两行。正文要等它决定"我要用这个技能"之后才会加载。

所以 description 相当于你技能的门面。写得含糊，AI 就不知道什么时候该用你，你的正文写得再好也没机会被看到。

**新手最常见的写法是这样：**

```
description: 生成周报
```

看起来没毛病，但 AI 看到这句话，只有在你原话说出"生成周报"四个字时才可能想起它。你说"帮我总结下这周"、"给老板汇报一下进度"，它可能就不用了。

**应该这么写：**

```
description: 写周报时使用。当用户说"写周报"、"总结这周"、
  "汇报进度"、"月度总结"，或者需要整理一段时间的工作产出时，
  都用这个技能。
```

区别在于：后者把 **用户可能怎么说** 全都列出来了。

![图片](assets/%E8%80%81%E5%A5%B6%E5%A5%B6%E7%9C%8B%E5%AE%8C%E9%83%BD%E4%BC%9A%E5%86%99%20Skill%EF%BC%8C%E8%BF%99%E5%8F%AF%E8%83%BD%E6%98%AF%E5%85%A8%E7%BD%91%E6%9C%80%E6%8E%A5%E5%9C%B0%E6%B0%94%E7%9A%84%20Skill%20%E6%95%99%E7%A8%8B/67f85680f343897d65bcd9970dbf1de6_MD5.png)

这里有个反直觉的点： **description 要写得主动一点，甚至有点"推销"的意思** 。因为 AI 有个倾向，它宁可自己做也不太愿意调用技能，你不明确告诉它"这种情况也算"，它就不会用。

我总结的写法是三段式：

1. 1\. 一句话说清这个技能干什么
2. 2\. 列出用户可能说的各种说法（越具体越好，包括同义词和口语说法）
3. 3\. 如果有明确不该用的场景，也写上（比如"但如果是年终总结，用另一个技能"）

## 五、正文别写太长

第二个常见问题：把 [SKILL.md](http://skill.md/) 写成一篇技术文档。

我第一个 Skill 写了三百多行，解释了背景、原理、各种情况的考量，结果 AI 读完还是不知道该干嘛。

原因有两个。

一是 **AI 的上下文空间是有限的** ，你写的每一句废话都在挤占它思考的空间。原理和背景对人有用，对 AI 来说是干扰。

二是 **Skill 的目的是下指令，不是讲道理** 。你不用告诉它"为什么周报要写风险项"，直接说"要有风险项这一栏，没有就写暂无"就够了。

经验值是 **控制在 500 行以内** ，一般的技能一百行都用不到。

那内容确实很多怎么办？拆文件。

比如你写一个"做数据分析报告"的技能，主文件里只放流程和判断逻辑，具体的图表规范单独放一个 `              chart-guide.md            ` ，SQL 写法放一个 `              sql-reference.md            ` ，在主文件里写清楚"需要画图时读 [chart-guide.md"。](http://chart-guide.md/)

这样 AI 平时只加载主文件，真要画图了才去读那个文件。省资源，也更清楚。

有个小坑要避开： **引用只做一层** 。别让 A 文件引用 B、B 又引用 C，AI 很可能读到一半就开始干活了。所有分文件都从 [SKILL.md](http://skill.md/) 直接链过去。

## 六、少写命令，多讲原因

再说个我自己走过的弯路。

刚开始写 Skill 我特别喜欢用强硬语气，满篇都是"必须"、"绝对不要"、"禁止"，觉得这样 AI 才会听话。

后来发现效果反而不好。

举个具体的例子。我给一个技能写过"配图必须 5 张"，结果遇到一个内容特别长的选题，5 张根本讲不完，AI 硬是压缩成 5 张，效果很差。

后来我改成这样：

> 配图默认 5 张左右。因为图太多会让读者中途放弃，而且每张图信息量太小，单独存下来没价值。如果确实是步骤很多的长教程，可以多几张，但每张都要保证信息完整。

改完之后，AI 遇到长教程会自己判断该用几张，遇到短内容也不会硬凑。

**道理很简单：你写死一个规则，AI 只能在你规定的情况里照做；你把原因讲清楚，它能处理你没想到的情况。**

所以如果你发现自己在 Skill 里写满了大写的 MUST 和 NEVER，通常说明你没把道理讲明白，只能靠喊。

当然也不是完全不能用强制语气。涉及安全、不可逆操作的地方（比如"删除前必须确认"），该硬就得硬。判断标准是： **这条规则错了会不会造成损失** 。会的话就写死，不会的话就讲道理。

## 七、写完怎么验证

很多人写完就直接用了，这一步其实不能省。

**最简单的验证方法：同一句话说两遍。**

第一遍，把技能挪走（或者新开个对话不加载它），让 AI 直接做这件事，看它做成什么样。

第二遍，把技能装上，同一句话再说一遍。

对比这两次的结果。如果差不多，说明你的 Skill 没起作用，要么是没被触发（检查 description），要么是正文没说清楚。

**测的时候要用真人会说的话。** 别用"生成周报"这种标准指令，要用"这周干的活挺杂的，帮我理个周报出来给我老板看"这种真实说法。前者太规范，测不出问题。

还有个容易忽略的： **测试它不该被触发的情况** 。比如你写了周报技能，问它"帮我写个年终总结"，它应该不用这个技能。如果用了，说明你的 description 范围写太宽了。

## 八、第一个 Skill 写什么

如果你不知道从哪下手，建议按这个标准挑：

**你最近一个月内，用同样的要求跟 AI 说过三次以上的事。**

比如：

- • 固定格式的周报日报
- • 代码提交信息的写法规范
- • 会议纪要的整理方式
- • 特定风格的文案改写
- • 数据查询后的固定分析角度

别一上来就挑复杂的。第一个技能越简单越好，跑通了有正反馈，你自然会想写第二个。

## 最后，三步走

1. 1\. **建文件夹** ，路径 `~/.claude/skills/你的技能名/             SKILL.md           `
2. 2\. **写两部分** ：头部的 name 和 description（重点是把用户可能怎么说都列全），正文说清什么时候用、怎么做、产出什么
3. 3\. **对比测一次** ：装上技能和不装技能各跑一遍，看有没有区别

写不好也没关系，Skill 是可以随时改的。真正的好技能都不是一次写成的，是用一段时间发现问题、改一次、再用，慢慢磨出来的。

先写一个能跑的，比想一个完美的强。
