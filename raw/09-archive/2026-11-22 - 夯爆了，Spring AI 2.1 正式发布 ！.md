## 一、先聊聊 Spring AI 是什么

如果你是 Java 后端，过去两年大概率有过这种体验：老板说"咱们也接个大模型吧"，然后你打开 Python 的 LangChain 文档，陷入沉思。

Spring AI 就是为了解决这个问题而生的。它是 Spring 官方出品的 AI 应用开发框架，核心思路一句话就能说清：**用 Spring 的方式写 AI 应用**。

它给你提供了这些东西：

- 统一的模型抽象 ：OpenAI、Anthropic、Google GenAI、Amazon Bedrock、Ollama、DeepSeek、Mistral……换模型基本就是换个 starter、改几行配置，业务代码不用动。
- ChatClient 流式 API ：写起来跟  `WebClient`  、  `RestClient`  一个味道，Spring 老用户零学习成本。
- Advisor 机制 ：记忆、RAG、安全护栏、日志都能像拦截器一样插拔。
- 工具调用、结构化输出、RAG、向量数据库、MCP、可观测性 ：做 AI 应用常用的那一套，基本都有现成方案。

从 2025 年的 1.0 GA，到基于 Spring Boot 4 的 2.0，再到今天的 2.1，Spring AI 已经从"能用"走到了"好用"，现在开始往"能撑起生产级 Agent"的方向迈进。

## 三、Decision Models：让模型做"选择题"

这是我个人觉得 2.1 最实用的新东西。

平时写业务，很多判断其实只有几个固定答案：这条评论是不是广告？这个工单属于哪个分类？用户满不满意？以前我们只能让聊天模型输出一段文字，再用正则或者 JSON 解析硬抠结果，模型偶尔"放飞自我"多说两句，解析就挂了。

 `DecisionModel`  专门干这个：**你把可选答案列出来，模型从中挑一个，并且告诉你每个答案的概率**。有了概率，"多有把握才执行"就由你的代码说了算。

![](assets/2026-11-22%20-%20%E5%A4%AF%E7%88%86%E4%BA%86%EF%BC%8CSpring%20AI%202.1%20%E6%AD%A3%E5%BC%8F%E5%8F%91%E5%B8%83%20%EF%BC%81/59d7079bbcc41a1c5592254401009403_MD5.png)

下面是一个客服工单自动分诊的例子。本地装个 Ollama，拉一个  `d1-omni:600m`  模型就能跑，不需要任何 API Key：

```java
package com.example.ai.service;

import org.springframework.ai.decision.DecisionModel;
import org.springframework.ai.decision.DecisionPrompt;
import org.springframework.ai.decision.DecisionResponse;
import org.springframework.ai.decision.question.ChoiceQuestion;
import org.springframework.ai.decision.question.ScoreQuestion;
import org.springframework.ai.decision.question.YesNoQuestion;
import org.springframework.stereotype.Service;

/**
 * 客服工单分诊服务
 * 借助 DecisionModel 一次性判断：是否反馈缺陷、问题分类、用户满意度
 */
@Service
public class TicketTriageService {

    /** 决策模型，由 starter 自动配置 */
    private final DecisionModel decisionModel;

    /**
     * 构造方法注入决策模型
     *
     * @param decisionModel 决策模型
     */
    public TicketTriageService(DecisionModel decisionModel) {
        this.decisionModel = decisionModel;
    }

    /**
     * 对一条客户留言进行分诊
     *
     * @param message 客户留言
     * @return 分诊结论
     */
    public String triage(String message) {
        DecisionResponse response = decisionModel.call(DecisionPrompt.builder()
                .text(message)
                // 是非题：是否反馈了商品缺陷
                .question("defect", YesNoQuestion.builder()
                        .text("Does the customer report a defect?")
                        .whenYes("Part of the item does not work as it should")
                        .whenNo("The item works, and the message is about something else")
                        .build())
                // 单选题：留言属于哪个分类
                .question("topic", ChoiceQuestion.builder()
                        .text("What is the message about?")
                        .option("delivery", "物流、配送进度")
                        .option("product", "收到的商品有问题")
                        .option("account", "登录、地址或支付信息")
                        .option("other", "以上都不是")
                        .build())
                // 打分题：用户满意度
                .question("satisfaction", ScoreQuestion.of(
                        "How satisfied is the customer?", "unhappy", "neutral", "happy"))
                .build());

        // 模型有九成把握时才自动开维修单
        boolean defect = response.getYesNo("defect").isYes(0.9);
        String topic = response.getChoice("topic").getValue();
        int satisfaction = response.getScore("satisfaction").getNearestLevel();

        return "缺陷=" + defect + "，分类=" + topic + "，满意度等级=" + satisfaction;
    }
}
```

配置也很简单：

```cs
spring:
  ai:
    ollama:
      init:
        # 启动时如果本地没有模型就自动拉取
        pull-model-strategy: when_missing
```

目前有三个实现： `OpenAiDecisionModel` 、 `OllamaDecisionModel`  和  `SystemOneDecisionModel` 。而且框架里已经有功能基于它构建了，比如 RAG 里的  `DecisionDocumentReranker` （文档重排序）和  `DecisionDocumentFilter` （过滤提示词注入），还有工具检索用的  `DecisionToolIndex` 。

> 提醒一句哈：决策模型再准，它也是机器学习模型，不是规则引擎。那种一旦判错代价特别高的场景，最好还是留个人工确认的环节。。

## 四、更丰富的消息模型：推理过程不再丢

2.0 之前，一条消息就是"一段文本 + 工具调用列表 + 媒体列表"。可现在的模型返回的东西越来越复杂：先思考一会儿，调个工具，再思考，再输出文本，中间可能还夹着图片。老结构装不下这些，顺序也保不住。

2.1 把  `AssistantMessage` 、 `UserMessage` 、 `ToolResponseMessage`  改成了**有序的片段列表**： `TextPart` 、 `ReasoningPart` 、 `ToolCallPart` 、 `ToolResultPart` 、 `MediaPart` ，以及兜底用的  `UnknownPart` 。像 Anthropic 的 thinking 签名这种需要原样回传的数据，也能完整保留下来。

```java
/**
 * 图表对比服务：一次发送文本加两张图片，并打印模型的推理过程
 */
@Service
public class ChartCompareService {

    /** 聊天模型 */
    private final ChatModel chatModel;

    /**
     * 构造方法注入聊天模型
     *
     * @param chatModel 聊天模型
     */
    public ChartCompareService(ChatModel chatModel) {
        this.chatModel = chatModel;
    }

    /**
     * 对比两张图表的差异
     *
     * @param firstChart  第一张图表
     * @param secondChart 第二张图表
     * @return 模型给出的对比结论
     */
    public String compare(Media firstChart, Media secondChart) {
        // 按顺序组装多个片段：文本 + 图片 + 图片
        UserMessage question = UserMessage.builder()
                .part(TextPart.of("这两张图表有什么变化？"))
                .part(MediaPart.of(firstChart))
                .part(MediaPart.of(secondChart))
                .build();

        AssistantMessage answer = chatModel.call(new Prompt(question)).getResult().getOutput();

        // 新增的 getReasoning()，可以拿到模型的思考过程
        for (ReasoningPart reasoning : answer.getReasoning()) {
            System.out.println("推理过程：" + reasoning.text());
        }
        return answer.getText();
    }
}
```

好消息是， `getText()` 、 `getToolCalls()`  这些老方法都还在，只是变成了片段之上的"视图"，**老代码不用改**。

顺带一提，2.1 还新增了  `OpenAiResponsesChatModel` ，对接 OpenAI 的  `/v1/responses`  接口。从 GPT-5.4 开始，Chat Completions 接口不支持"工具调用 + 推理强度"的组合，做 Agent 得用 Responses API。切换只要一行配置：

```ini
# chat-completions（默认）| responses
spring.ai.openai.chat.api=responses
```

另外，每个  `Generation`  现在都带一个统一的  `FinishReasonCategory` （ `COMPLETED` 、 `TRUNCATED` 、 `TOOL_CALL` 、 `FILTERED`  等），再也不用为每家厂商的  `stop` 、 `end_turn` 、 `STOP`  写一堆 if-else 了。

## 五、Agent 的地基：Session、工具确认与调用上限

![](assets/2026-11-22%20-%20%E5%A4%AF%E7%88%86%E4%BA%86%EF%BC%8CSpring%20AI%202.1%20%E6%AD%A3%E5%BC%8F%E5%8F%91%E5%B8%83%20%EF%BC%81/9375c6cd86d3c3b05db1e789376ef63a_MD5.jpg)

模型本身只会"续写文本"，让它变成 Agent 的，是外面那层壳：循环、工具、记忆、权限和检查。2.1 在这层壳上一口气补了好几块。

### 5.1 Session API：取代 ChatMemory

 `ChatMemory`  本质上就是按会话 ID 存一串消息。对话一长、或者跑 Agent 时，它就有点力不从心了。2.1 引入的 Session API 把会话存成**只追加的事件日志**，在此基础上做了三件事：

- 按轮次压缩 ：历史太长时自动压缩，而且一定在"轮次边界"切，不会出现"有工具调用、没工具结果"的尴尬情况。压缩不改原始日志，只是追加一个边界标记。
- 回溯检索 ：被压缩掉的内容还在日志里，模型可以通过内置的  `conversation_search`  工具自己翻旧账。
- JDBC 持久化 ：  `JdbcSessionRepository`  支持 PostgreSQL、MySQL、MariaDB、SQL Server 和 H2。

![](assets/2026-11-22%20-%20%E5%A4%AF%E7%88%86%E4%BA%86%EF%BC%8CSpring%20AI%202.1%20%E6%AD%A3%E5%BC%8F%E5%8F%91%E5%B8%83%20%EF%BC%81/8e9522b222339eaecdc03c0c81b9d8e6_MD5.png)

引入  `spring-ai-starter-model-session-jdbc` ，接上 MySQL：

```bash
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/db_spring_ai?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
    username: root
    password: 123456
```

然后注册 Session 相关的 Advisor 和回溯工具：

```typescript
/**
 * ChatClient 配置类：启用 Session 记忆、压缩与回溯
 */
@Configuration
public class ChatClientConfig {

    /**
     * 构建带会话记忆的 ChatClient
     *
     * @param chatModel      聊天模型
     * @param sessionService 会话服务
     * @return ChatClient 实例
     */
    @Bean
    public ChatClient chatClient(ChatModel chatModel, SessionService sessionService) {
        return ChatClient.builder(chatModel)
                // 超过 20 轮触发压缩，压缩后保留最近 10 轮
                .defaultAdvisors(SessionAdvisors.builder(sessionService)
                        .compaction(new TurnCountTrigger(20),
                                WindowCompactionStrategy.builder().lastTurns(10).build())
                        .build())
                // 让模型可以检索被压缩掉的历史
                .defaultTools(SessionRecallTools.builder(sessionService).build())
                .build();
    }
}
```

调用时每次都带上会话 ID：

```typescript
/**
 * 聊天接口
 */
@RestController
@RequestMapping("/api/chat")
public class ChatController {

    /** 聊天客户端 */
    private final ChatClient chatClient;

    /**
     * 构造方法注入 ChatClient
     *
     * @param chatClient 聊天客户端
     */
    public ChatController(ChatClient chatClient) {
        this.chatClient = chatClient;
    }

    /**
     * 发送一条消息
     *
     * @param sessionId 会话 ID
     * @param message   用户消息
     * @return 模型回复
     */
    @GetMapping
    public String chat(@RequestParam String sessionId, @RequestParam String message) {
        return chatClient.prompt()
                .user(message)
                .advisors(SessionAdvisors.session(sessionId))
                .toolContext(Map.of(SessionRecallTools.SESSION_ID_CONTEXT_KEY, sessionId))
                .call()
                .content();
    }
}
```

注意，框架**故意没有提供默认会话**，因为共享会话会把不同用户的聊天记录悄悄混在一起。Advisor 本身也不保存状态，所以多实例部署时，任何一台机器都能接着处理同一个会话。

 `ChatMemory`  相关的类已经标记为废弃，计划在 3.0.0 移除，新项目建议直接上 Session。

### 5.2 工具调用确认：敏感操作先问人

订机票、删文件、发邮件，这类操作你肯定不想让模型说干就干。现在给工具加一个属性就行：

```typescript
/**
 * 订票相关工具
 */
@Component
public class BookingTools {

    /** 订票业务服务 */
    private final BookingService bookingService;

    /**
     * 构造方法注入订票服务
     *
     * @param bookingService 订票服务
     */
    public BookingTools(BookingService bookingService) {
        this.bookingService = bookingService;
    }

    /**
     * 预订航班，需要用户确认后才会真正执行
     *
     * @param flightNumber 航班号
     * @return 预订结果
     */
    @Tool(description = "Book a flight", requiresConfirmation = true)
    public String bookFlight(String flightNumber) {
        return bookingService.book(flightNumber);
    }

    /**
     * 查询航班状态，无需确认
     *
     * @param flightNumber 航班号
     * @return 航班状态
     */
    @Tool(description = "Get the status of a flight")
    public String flightStatus(String flightNumber) {
        return bookingService.status(flightNumber);
    }
}
```

整个确认流程长这样：

![](assets/2026-11-22%20-%20%E5%A4%AF%E7%88%86%E4%BA%86%EF%BC%8CSpring%20AI%202.1%20%E6%AD%A3%E5%BC%8F%E5%8F%91%E5%B8%83%20%EF%BC%81/883f13a7a36e5ed1af441927a9380d1f_MD5.png)

用户做完决定后，这样恢复执行：

```java
// 每个工具调用都要给出一个决定
ToolCallDecisions decisions = ToolCallDecisions.of(
        ToolCallDecision.allow("call_1"),
        ToolCallDecision.deny("call_2", "用户取消了这次预订"));

// 同意的执行，拒绝的把原因告诉模型
ToolExecutionResult result = toolCallingManager.executeToolCalls(prompt, reply, decisions);

// 带着工具结果继续对话
String answer = chatClient.prompt()
        .messages(result.conversationHistory())
        .call()
        .content();
```

最妙的是这个过程是**无状态**的：暂停就是一次普通的响应，恢复就是一次普通的请求。只要你把对话存下来，服务重启了也能接着走。

对于 MCP 这种不是你自己写的工具，可以用  `ToolCallConfirmationPolicy.forTools("bookFlight", "cancelBooking")`  按名字指定。

### 5.3 工具调用上限：防止死循环烧钱

模型陷入"调工具、再调工具"的死循环，账单会很好看。2.1 给工具循环加了默认上限：单个工具每轮最多 40 次，总共最多 150 次，可以通过  `spring.ai.tools.limits.*`  配置，也可以代码里调：

```java
ToolCallingManager manager = ToolCallingManager.builder()
        .maxCallsPerTool(20)
        .build();
```

### 5.4 护栏拒绝统一处理

护栏拦下的请求现在会被标记为  `GuardrailRefusal` ，厂商安全过滤拦下的也有对应的  `ContentFilteredException` 。一个  `catch`  全搞定：

```kotlin
try {
    Order order = chatClient.prompt().user(message).call().entity(Order.class);
} catch (ContentFilteredException ex) {
    // 护栏拒绝或厂商安全过滤，统一友好提示
    return "抱歉，这个问题我没法回答。";
}
```

## 六、MCP 2026-07-28：无状态的新协议

MCP 的 2026-07-28 版本是一次大改：**没有握手、没有会话**，每个请求自带协议版本和客户端能力。对服务端来说，这意味着水平扩展变得简单多了。

服务端开启新协议只要一行配置，原来写的  `@McpTool` 、 `@McpResource`  等注解一个字不用改：

```ini
spring.ai.mcp.server.protocol=MODERN
```

```typescript
/**
 * 天气查询 MCP 工具
 */
@Component
public class WeatherMcpTools {

    /**
     * 查询指定城市的天气
     *
     * @param city 城市名称
     * @return 天气描述
     */
    @McpTool(name = "weather", description = "查询城市天气")
    public String weather(@McpToolParam(description = "城市名称") String city) {
        return city + "：晴，18℃";
    }
}
```

客户端可以新老协议混用，同一个工具提供者会把两边的工具一起交给模型：

```bash
spring:
  ai:
    mcp:
      client:
        streamable-http:
          connections:
            billing:
              url: http://localhost:8081   # 老协议
            tickets:
              url: http://localhost:8080
              protocol: MODERN             # 新协议
```

新协议客户端不持有会话、创建成本很低，默认每个  `ChatClient`  请求一个客户端（ `PER_REQUEST` ），按用户身份隔离调用变得很自然。

## 七、向量库支持"自带向量"

以前  `VectorStore.add()`  总是用向量库自己配置的嵌入模型来算向量。但实际项目里，向量可能是夜间批处理算好的，也可能是别的团队维护的嵌入管道产出的。

2.1 新增了  `upsert()`  和"用向量直接检索"的能力：

```javascript
// 写入已经算好的向量，相同 ID 会覆盖，任务重跑也安全
vectorStore.upsert(List.of(new EmbeddedDocument(document, embedding)));

// 直接用自己算的查询向量做相似度检索
List<Document> results = vectorStore.similaritySearch(queryEmbedding,
        SearchRequest.builder().topK(5).similarityThreshold(0.7).build());
```
