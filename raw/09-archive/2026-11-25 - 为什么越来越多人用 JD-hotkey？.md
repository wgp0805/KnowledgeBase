# 为什么越来越多人用 JD-hotkey？

大家好，我是程序汪。

> 做后端的同学多少遇到过这种情况：大促零点一到，某个爆款商品的请求集中到同一个 key，Redis 单 key 访问量瞬间拉满；缓存一旦失效，请求直接打到 MySQL，一条慢查询就可能拖垮连接池。 这类热点在发生前往往无法预知。京东开源的 JD-hotkey 就是为这个场景做的，经过 2020 年 618 和多次压测，线上每天探测的 key 以数十亿计，worker 单机压测 QPS 可达 35 万。

今天程序汪和大家聊聊它的原理和接入方式。

## 一、热 key 不处理会发生什么

Redis 虽然性能高，但单个 key 的请求都落到同一个线程和同一台机器上，热点集中时网卡和 CPU 会先到上限。如果这个 key 同时过期，大量请求穿透到数据库，就是典型的缓存击穿。

JD-hotkey 的处理思路是：在请求到达 Redis 和数据库之前，先由 client 端把每次访问的 key 上报给独立的 worker 集群统计。某个 key 在设定时间内访问次数超过阈值，就判定为热 key，再推送到这个应用所有机器的 JVM 内存里。之后对这个 key 的请求直接读本地 Caffeine 缓存，不再访问 Redis，整个集群内的热 key 保持一致。

热用户、热接口也是同样的用法，区别只在业务侧拿到判断结果后怎么处理：热商品做本地缓存，热用户直接拒绝，热接口熔断或返回默认值。

## 二、整体架构：四个组成部分

| 组件 | 作用 |
| --- | --- |
| ** etcd 集群 ** | 配置中心，存放规则、worker 地址、探测出的热 key，提供监听订阅 |
| ** client jar ** | 引入业务系统，负责 key 上报、监听变更、热 key 本地缓存 |
| ** worker 集群 ** | 独立部署的 Java 程序，接收上报的 key 做累加计算，判定后推送 |
| ** dashboard 控制台 ** | 配置各应用的规则，查看和手工增删热 key，记录探测历史 |

整个框架没有依赖 Redis，client 和 worker 之间走 Netty 长连接，比较轻量。worker 是无状态的，多台机器各自分摊 client 连接，扩容时把新节点地址注册到 etcd，client 会自动感知。

## 三、客户端接入实操

项目在 Gitee 上开源（jd-platform-opensource/hotkey），先把源码打包到本地仓库或公司私服，再引入依赖：

```
<!-- JD-hotkey 客户端 -->
<dependency>
    <groupId>com.jd.platform.hotkey</groupId>
    <artifactId>hotkey-client</artifactId>
    <version>1.0-SNAPSHOT</version>
</dependency>
```

应用启动时初始化客户端：

```
/**
 * JD-hotkey 客户端初始化
 */
@Component
publicclass HotKeyInit {

    /** Bean 创建完成后启动探测通道 */
    @PostConstruct
    public void initHotkey() {
        ClientStarter starter = new ClientStarter.Builder()
                // 应用名，需要和控制台里的应用一致
                .setAppName("order-service")
                // etcd 集群地址，多个用逗号分隔
                .setEtcdServer("http://10.0.0.1:2379,http://10.0.0.2:2379")
                // 本地 Caffeine 缓存最大条数，默认 5 万
                .setCaffeineSize(50000)
                // 批量上报间隔，默认 500ms
                .setPushPeriod(500L)
                .build();
        starter.startPipeline();
    }
}
```

规则在控制台配置，比如商品 key 2 秒内被访问 20 次就判定为热 key，本地缓存 10 分钟：

```
{
  "key": "product_",
  "prefix": true,
  "interval": 2,
  "threshold": 20,
  "duration": 600,
  "desc": "热门商品，前缀匹配，缓存10分钟"
}
```

## 四、业务代码怎么用

客户端核心操作类是 JdHotKeyStore，常用方法有四个： `isHotKey`  判断是否热 key 同时上报访问， `get`  只读本地缓存， `smartSet`  仅在 key 为热 key 时写入缓存， `getValue`  读不到时自动上报。

商品查询的完整写法：

```
/**
 * 商品查询服务：热 key 走本地缓存，其余走正常链路
 */
@Service
publicclass ProductService {

    @Autowired
    private ProductDao productDao;

    /**
     * 按商品 ID 查询详情
     *
     * @param productId 商品 ID
     * @return 商品详情
     */
    public ProductDetail query(Long productId) {
        String key = "product_" + productId;
        // 调用即上报，返回 true 表示该 key 已被判定为热 key
        if (JdHotKeyStore.isHotKey(key)) {
            Object cached = JdHotKeyStore.get(key);
            if (cached != null) {
                // 本地缓存命中，不再访问 Redis 和数据库
                return (ProductDetail) cached;
            }
            ProductDetail detail = productDao.findById(productId);
            // 非热 key 调用此方法不会真正写入
            JdHotKeyStore.smartSet(key, detail);
            return detail;
        }
        return productDao.findById(productId);
    }
}
```

黑名单场景更简单，不需要缓存值，只取判断结果：

```
// 热 key 黑名单用户直接拒绝，请求不落到数据库
if (JdHotKeyStore.isHotKey("black_user_" + userId)) {
    throw new BizException("访问受限");
}
```

## 五、实际使用的几个注意点

-  `isHotKey`  每次调用都会上报计数，不要在一个请求里重复调用同一个 key，需要多次判断时先保存结果
-  `push-period`  不是越小越好。单机 QPS 不高时保持默认 500ms 即可，调得太小会产生大量空上报
- 客户端依赖较新版本的 Guava，老项目如果 Guava 版本过低，先升级或排除冲突，否则启动会报 NoSuchMethodError
- 热 key 缓存的是 JVM 内存，规则里的 duration 要结合业务数据的更新频率设置，避免本地缓存长时间保存旧数据
- worker 建议至少部署两台，client 会同时保持多条长连接，单台 worker 下线不影响探测
- 控制台支持手工添加热 key，大促前可以把已知的活动商品提前录入，不用等流量上来再探测
