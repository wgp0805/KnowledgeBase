# 远程弹珠机 APP 技术解决方案

真实硬件弹珠机 + 摄像头直播 + APP 远程控制 + 积分兑换商城 · 全栈技术方案

技术栈：uniapp + Python涉及：硬件开发 / IoT / 视频流 / 支付版本：v1.0

## 一、技术栈选型

| 层级 | 技术选型 | 选型理由 |
| --- | --- | --- |
| APP 端 | ** uniapp (Vue3 + Vite) ** | 用户指定；一套代码编译 Android/iOS；生态成熟，直播/支付插件丰富 |
| 后端框架 | ** Python FastAPI ** | 异步高性能（ASGI）；自动生成 OpenAPI 文档；类型提示；比 Django 轻量，比 Flask 规范 |
| 实时通信 | ** MQTT (EMQX) ** + ** Redis Pub/Sub ** | APP 与后端低延迟双向通信；多实例部署时 Redis 做消息总线 |
| 设备通信 | ** MQTT (EMQX) ** | 物联网标准协议；断连自动重连；QoS 保证指令不丢；支持遗嘱消息检测设备离线 |
| 视频流协议 | ** RTMP推流 ** + ** WebRTC播放 ** | 设备端ffmpeg推RTMP到腾讯云，APP端WebRTC拉流；延迟~800ms，适合实时操控 |
| 视频直播 | ** 腾讯云快直播（LEB） ** | 基于WebRTC，端到端延迟~800ms；RTMP推流+WebRTC播放；无需自建流媒体服务器，按量付费 |
| 数据库 | ** MySQL 8.0 ** + ** Redis 7 ** | MySQL 存用户/订单/商品等关系数据；Redis 缓存房间状态、在线会话、排行榜、限流 |
| 硬件主控 | ** ESP32-S3 ** / 树莓派 Zero 2W | WiFi+BLE 双核，Arduino/ESP-IDF 开发，成本低（~¥35）； |

## 二、项目概述

本项目是一套**远程真实弹珠机**娱乐系统（类似"云抓娃娃机"模式）。用户通过手机 APP 远程操控线下真实弹珠机，观看实时直播画面进行游戏，胜利后获得积分，积分可在商城兑换实物商品。

## 三、整体架构

采用**三层核心架构**：客户端 → 后端服务 → 硬件终端，MQTT Broker 作为后端与硬件之间的实时通信枢纽。视频流由硬件直接推送到**腾讯云 LEB（快直播）**，APP 端通过 WebRTC 拉流，无需自建流媒体服务器。

### 4.3 围观流程（游客可围观，不能操作）

**围观者（含游客）：**

- 进入房间列表，看到"X人围观"
- 点击房间 → 以  `watcher`  身份订阅 MQTT 房间主题
- 接收视频流（只读）+ 游戏结果广播
- 不能发送投币/震动等控制指令（服务端按角色拦截）
- 离开时围观人数 -1

**技术实现要点：**

- MQTT 订阅分角色：  `player`  /  `watcher`
- 房间用 Redis  `Hash`  存 player_id + watcher 集合
- 围观人数用 Redis  `INCR/DECR`  ，过期自动清理
- 视频流对围观者同样开放，但可限制码率/分辨率节省带宽
- 游客（未登录）只能围观，点击"开始游戏"时引导登录

## AI 提效最明显的三个环节

**第一名：固件开发（驱动层 + 应用层  提效50%）**这是 AI 提效最大的地方。 GPIO 初始化、SPI 配置、W5500 驱动、分时轮询算法、TCP 客户端、协议打包解析 —— 这些都是标准模块化代码，AI 直接生成可编译的 C 代码，你只需要调参数和联调。 原来一个嵌入式工程师 2 周的固件活，现在 3~5 天能出初版。

**第二名：需求与方案设计（提效60%）**芯片选型对比、电路方案选型、通信协议设计、需求文档 ——AI 一次给你拉齐，不用自己翻 datasheet 查半天。 特别是芯片选型，AI 直接给你 STM32F103 vs ESP32 vs GD32 的对比表，包括价格、资源、开发难度、供货情况。

**第三名：联调与测试（提效60%） **AI 可以生成 Python 模拟后端代码，你硬件还没完全好就能先模拟联调。 测试用例、自动化测试代码，AI 直接出，你只需要跑。

### 5.4 MQTT 主题设计

| 主题 | 方向 | QoS | 说明 |
| --- | --- | --- | --- |
|  `device/{id}/cmd`  | 服务端 → 设备 | 1 | 控制指令：投币/震动/复位/LED |
|  `device/{id}/event`  | 设备 → 服务端 | 1 | 事件上报：投币完成、卡球、故障 |
|  `device/{id}/result`  | 设备 → 服务端 | 2 | 游戏结果（弹珠落位），QoS2 确保不丢不重 |
|  `device/{id}/heartbeat`  | 设备 → 服务端 | 0 | 心跳，每 15s 一次，含温度/电压 |
|  `device/{id}/status`  | 保留消息 | 1 | 在线/离线状态（LWT 遗嘱） |

**防作弊关键：**游戏结果（弹珠落位）由**硬件传感器直接上报**，服务端只做校验和积分发放，APP 端不参与判定。MQTT QoS2 + session_id 绑定，防止重复计分和伪造结果。

```

{
  "type": "join_room",       // join_room / leave_room / drop_ball / shake / get_status
  "room_id": 1,
  "data": { }
}

// 服务端 → 客户端 消息格式
{
  "type": "room_state",      // room_state / round_result / session_end / error / watcher_update

    "room_id": 1,

  }
}

// 单局结果推送

  "type": "round_result",
  "data": {

    "point_earned": 50,  // 获得积分

    "balance": { "coin": 190, "point": 50 }
```

## 九、视频流方案（调用腾讯云直播服务）

视频是远程操控的核心体验，**延迟必须控制在 1 秒以内**，否则用户投币后看不到弹珠轨迹，体验极差。我们采用的是https://cloud.tencent.com/product/leb

### 9.1 方案对比

| 方案 | 延迟 | 兼容性 | 复杂度 | 适用 |
| --- | --- | --- | --- | --- |
| ** WebRTC（推荐） ** | 200~500ms | uniapp 需原生插件 | 中 | 实时操控，首选 |
| RTMP 推流 + HTTP-FLV 拉流 | 1~2s | 好（flv.js） | 低 | 备选，兼容性好 |
| RTMP + HLS | 3~6s | 最好 | 低 | 仅围观降级，不适合操控 |

### 9.2 推荐架构（WebRTC）

视频流链路

### 9.3 关键参数

- 分辨率： 720p（1280×720）足够，1080p 带宽翻倍，初期用 720p
- 帧率： 30fps，弹珠运动需要流畅
- 码率： 1.5~2Mbps（720p），单台机器上行带宽需 ≥2Mbps
- 编码： H.264（硬编，树莓派支持），不要用 H.265（兼容性差）
- 音频： 不需要，弹珠机无关键声音，省带宽

**带宽成本提醒：**10 台机器同时直播，每台 2Mbps 上行 = 20Mbps 上行带宽（机房/店铺需保障）；用户端拉流按并发观看人数算，100 人同时看 = 200Mbps 下行，云服务器带宽成本是主要运营支出，建议用 CDN 或按流量计费。

## 十一、安全与合规

### 11.1 技术安全

| 维度 | 措施 |
| --- | --- |
| 通信安全 | 全链路 HTTPS / MQTT over TLS；MQTT 用 TLS + 用户名密码认证；设备证书绑定 device_sn |
| 身份认证 | JWT（2小时过期 + Refresh Token）；敏感操作（充值/兑换）需二次验证 |
| 防作弊 | 游戏结果由硬件传感器上报，服务端权威判定；MQTT QoS2 + session_id 绑定；异常结果（频率过高/分值异常）告警 |
| 资金安全 | 钱包余额乐观锁 + 条件更新防超扣；所有余额变更写流水；支付回调验签+幂等；日终对账 |
| 接口安全 | 限流（Redis 令牌桶，单用户 60次/分钟）；SQL 注入防护（ORM 参数化）；XSS 防护（输入过滤） |
| 设备安全 | 设备固件签名校验（OTA 防刷）；控制指令带 token + 时间戳防重放；设备首次激活绑定房间后不可篡改 |

### 11.2 合规要点

**必须做：**

- APP 内显著位置标注"仅供娱乐 严禁赌博"（机器上已有）
- 弹珠币 不可提现、不可反向兑换 ，只能消费游戏
- 积分只能兑换实物/虚拟商品，不能兑换现金
- 用户实名注册（手机号 = 实名），防沉迷系统
- 未成年人限制：每日游戏时长 + 充值限额
- 平台公告明确"禁止一切不合规行为"
- ICP 备案 + 游戏版号
