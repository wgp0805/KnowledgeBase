很多人第一次用 Codex，动作都差不多。

打开终端，丢一句：“帮我做个：xxxx”

然后开始等。

等它读文件、写代码、改配置、补测试。中间看着挺热闹，结果一跑，报错。再让它修。修完又冒出一个新问题。来回两三轮以后，人开始烦了：这玩意儿到底靠不靠谱？

我现在的看法很简单：Codex 靠不靠谱，往往不在它聪不聪明，而在你懂不懂它。

你不能把一句愿望扔进去，就期待它吐出一个能上线的功能。真实项目里，需求、代码、约束、测试、历史包袱都挤在一起。你让一个 Agent 上来就动手，它只能先猜。猜对了是效率，猜错了就是连环返工。

我现在最推荐的 Codex 工作流是这样的：

**读上下文 → 写计划 → 确认范围 → 小步实现 → 跑验证 → 总结结果 → 开新会话**

看起来慢，其实省时间。

## 第一件事：别急着让它写代码

尤其是陌生项目、课程项目、论文复现、接第三方 SDK 这种任务，第一轮最好不要让 Codex 改任何东西。

先让它读。

可以直接这样说：

```
不要修改代码。请先阅读这个项目，告诉我：

1. 项目结构是什么
2. 程序的入口在哪里里
3. 运行、测试、构建命令分别是什么
4. 哪些文件最可能和当前任务有关
5. 你不确定的地方有哪些
```

最后那一句很重要： **你不确定的地方有哪些** 。

很多翻车不是因为 Codex 不会写代码，而是它太快进入“我已经懂了”的状态。而实际上它没有完全了解你的需求，直接就”硬着头皮“开工了。

日常使用中，我还会反问Codex：在开始之前，你还有什么需要向我确认的？ 或者 请罗列出当前要执行的任务。

## AGENTS.md 不是项目说明书

很多人会把 [AGENTS.md](http://agents.md/) 写成一份又长又全的项目介绍。

Codex 能从代码里看出来的东西，不必写进去。比如“这是一个 React 项目”“这个文件是组件”“这个目录放工具类”，这些信息通常不值上下文。

[AGENTS.md](http://agents.md/) 更适合放三类东西：

第一类，是项目里确实有约束的规则。

比如不能改哪些目录，接口命名有什么要求，后端必须保留兼容字段，测试必须用哪套命令跑。

第二类，是你希望 Codex 每次都遵守的工作习惯。

比如修改前先读相关文件，只做当前任务需要的最小改动，完成后必须跑验证，不要顺手重构无关代码。

第三类，是踩过坑以后沉淀下来的提醒。

比如某个包不能升级，某个测试必须先启动本地服务，某个目录下的生成文件不要手改。

一个好用的 [AGENTS.md，不需要长。甚至越短越好。](http://agents.xn--md,-928dy13ykbp7mc.xn--5us955d84bixp4roba./)

```
## 工作规则
- 先阅读相关代码和文档，再开始修改。
- 修改前说明影响范围。
- 只做当前任务相关的最小改动。
- 提交前运行最小验证。
- 说明用中文，命令和文件名保留英文。
- 不要修改无关文件。

## 验证命令
- npm run lint
- npm test
- npm run typecheck
```

这里有个判断标准：如果一条规则只是“希望它更专业”，大概率可以删。如果一条规则能减少一次真实返工，就值得留下。

## 复杂任务一定先 Plan

只要任务超过一个文件，我基本都会先让 Codex 写计划。

这样做的目的，是让Codex把你的任务拆解出来，提前发现它有没有理解错。如果一切都正常，再让它逐步去完成。

可以先开启计划模式，这样问：

```
先不要写代码。帮我设计实现方案：

1. 这次要解决的问题是什么
2. 会影响哪些模块
3. 拆成 3-7 个步骤
4. 每一步怎么验证
5. 哪些地方最容易出错

等我确认后再开始实现。
```

这一步的价值，经常比代码本身还高。

因为你会看到它准备从哪里下手、准备改哪些文件、准备怎么验证。只要这个计划里有一处离谱，马上修改，避免不必要的试错。

最怕的是它已经改了 8 个文件，你才发现它把需求理解成了另一个方向。那时候再去二次修改，不仅浪费时间，还可能引发出新的问题。

论文复现也一样。

不要上来就说“帮我复现这篇论文”。更好的方式是让它先读论文和官方 repo：

```
请先阅读论文和官方实现，不要开始写代码。

先输出：
1. 论文核心 idea
2. 关键公式或模块
3. 官方实现和论文描述是否一致
4. 最小复现路径
5. 可能复现不出来的风险点
```

研究类任务最怕“看起来完整”。一堆 ablation 表格补得很漂亮，但没有任何信息增益。先把假设、风险和最小路径讲清楚，反而更像正常研究。

## Bug 修复时，少教它怎么修

这点有点反直觉。

很多人遇到 Bug，会把自己的猜测一股脑塞给 Codex：

“我觉得是这里的异步问题，你看看是不是 Promise 没 await，可能要改成这样……”

结果你把它带偏了。

更好的方式是把错误日志、复现步骤、相关文件贴清楚，然后说：

```
fix
```

或者稍微完整一点：

```
这是报错日志和复现步骤。请定位原因并修复。
修复后运行对应测试，不要改无关文件。
```

它的调试能力并不差。差的是你把一个还没验证的猜测，当成了前提。

当然，也别无限纠缠。同一个问题如果修了两轮还没过，也可能是上下文太长，把它带偏了。我一般会开一个新的会话。

把问题、现象、已经试过的方案、失败原因整理一下，再让新的上下文重新判断。长会话里残留的旧假设，有时候比 Bug 本身更难处理。

## “完成了”不算完成，跑过才算

Codex 很容易说“已完成”。

这句话只能说明它认为自己写完了，不能说明这个改动真的能用。

我眼里的完成，至少要回答五个问题：

1. 1\. 改了哪些文件
2. 2\. 每个文件为什么改
3. 3\. 跑了哪些验证
4. 4\. 哪些验证没跑，原因是什么
5. 5\. 哪些地方还需要人工确认

我建议把这几条写进 [AGENTS.md，或者每次任务结束时直接要求它输出。](http://agents.xn--md,-hv9d10lv2a286bvmmxmdowhpne0vov9bg3bn32gcl0arie7y5cxdy./)

还有一个很容易忽略的点：测试也要审。

AI 生成的测试有时会很“配合”。代码错了，它就把测试改到能通过；边界条件没覆盖，它也能写出一堆看起来很勤奋、实际没抓住问题的 happy path。

所以测试变更比业务代码更要认真看。

业务代码写错，测试可能抓住。测试也写错，就等于你给自己造了一个假的安全感。

## Skills 和 MCP，别一上来就全装

Codex 用久以后，肯定会碰到重复任务。

比如每次都让它按同一套规则做代码审查，每次都让它整理实验记录，每次都让它生成发布说明。这个时候，Skill 就有价值了。

Skill 更像一个固定工种的操作手册。

你不需要每次重复说：“请用中文、先看 diff、按风险排序、只列 bug、不写彩虹屁。”

把这套规则写成一个 Skill，下次直接调用。

MCP 处理的是另一类问题：上下文不在代码仓库里。

比如数据在数据库里，任务在 Jira 里，文档在 Notion 里，表格在飞书里。过去你要复制粘贴，现在可以通过 MCP 把这些外部资源接进来。

但我不建议一开始就接一堆 MCP。

工具越多，表面上能力越强，实际上判断成本也越高。先接一两个你每天真的会用的，再往外扩。能减少手动复制、能稳定复用，这才值得接。

## 一个任务结束，就给上下文清个场

长会话会干扰Codex的判断和执行。

上下文越来越长，旧决策、旧错误、旧假设都会留在里面。你继续让它做下一个功能，它可能还在用上一个任务的思路看问题。

我的习惯是每完成一个相对独立的任务，就让它输出一句交接：

```
请用一句话总结刚完成的任务、修改过的文件、当前状态和下一步注意事项。
```

然后开新会话，把这句总结贴进去。

这一步很小，但很管用。它像给项目扫了一下桌面。该留下的留下，该丢掉的丢掉。

## 最后说句实在的

Codex 不是替你做判断的。它更像一个很能干、动作很快、但必须被放进正确工作流里的同事。

你给它错误上下文，它会很认真地错下去；你不给它验收标准，它会把“写完了”当成“完成了”；你让它在一个越来越脏的长会话里连续干活，它迟早会带着旧假设撞墙。

让 Codex 稳下来，靠的不是某一句神奇 Prompt。

是这几件普通到有点无聊的事：

- • 先读项目，不急着改
- • 复杂任务先写计划
- • [AGENTS.md](http://agents.md/) 只放长期规则
- • 小步实现，不顺手扩大范围
- • 跑验证，认真看 diff
- • 任务结束就总结，然后开新会话
- • 重复流程沉淀成 Skill
- • 外部上下文再用 MCP 接进来

把这些做好以后，Codex 才会从“偶尔惊艳的聊天框”，变成一个能长期协作的工程工具。

这时候你会发现，提效这件事不只是多写几行代码。

而是它让你每一次动手之前，都更清楚自己到底要改什么、为什么改、怎么知道它真的改对了。
