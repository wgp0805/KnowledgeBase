## ZXing 拿到手里是什么样

平时真正要引的是两个包。

 `core`  只管码本身：把文字编成矩阵，或者把一块黑白图解成字符串。它不认识 JPG、PNG，也不依赖 AWT。 `javase`  负责和  `BufferedImage`  对接，命令行小工具也放在这里。只在内存里摆矩阵、自己负责画图的话，第二个包可以不引。

所以它的典型工作是两头。一头是你给一段文字，它画出二维码或条码；另一头是你已经有一张图，它告诉你里面写了什么、是哪种码、码在图的哪个位置。批量打门票、对账时读面单、测试里先生成再读回来做闭环，都是这个路子。

手机镜头实时扫，系统扫码和 ML Kit 往往更省事，因为对焦、旋转和帧率要另写。ZXing 的 Java 版更适合「图已经在手里」。官方这些年也淡化了 Android 示例的持续集成，服务端和普通 Java 程序才是 3.5 的主场。

## 日常能碰到的码，它基本都覆盖

大家提到 ZXing，第一反应通常是二维码。能扫的其实宽得多。

方块和层叠这一类，有 QR Code、Aztec、Data Matrix、PDF417、MaxiCode。商品包装上常见 EAN-8、EAN-13、UPC-A、UPC-E。物流和工业场景里还有 Code 39、Code 93、Code 128、ITF（交叉二五码）、Codabar，以及 RSS-14、RSS Expanded。

3.5.0 在 2022 年 5 月发布，Aztec、PDF417、Data Matrix 的解码修过一轮，还加了更省容量的 minimal 编码模式。后面的 3.5.1 到 3.5.3 继续补边界：二维码在两种极端图上不再死盯很久、Code 128 去掉了过死的长度限制、GS1 应用标识按 2023 年规范更新、RSS Expanded 少了一些误识别。3.5.4 是这条线上的最新一档，方向还是把旧坑填平。

![](assets/2026-11-01%20-%20ZXing%203.5%20%EF%BC%88%20Java%E7%89%88%20%EF%BC%89%20%E5%88%B0%E5%BA%95%E6%9C%89%E5%A4%9A%E5%BC%BA%20%EF%BC%9F/3e58631c763daa64ee06bfaf65cf26f5_MD5.jpg)

上图只帮你留下形状印象。真正的码以库画出来的为准，静区、模块大小和纠错等级都会影响能不能被读回去。

## 一张图是怎么被读出来的

业务代码里就这四步，记牢之后，排错也有地方下手。

![](assets/2026-11-01%20-%20ZXing%203.5%20%EF%BC%88%20Java%E7%89%88%20%EF%BC%89%20%E5%88%B0%E5%BA%95%E6%9C%89%E5%A4%9A%E5%BC%BA%20%EF%BC%9F/cdc2a52a2ce85cf69ca721dd2481b88e_MD5.png)

亮度图把彩色或灰度收成 0 到 255 的亮度，0 是黑，255 是白。二值化再决定每个点算黑还是算白。照片用  `HybridBinarizer`  比较稳；图特别干净、几乎就是一张纯码时，可以试  `GlobalHistogramBinarizer` ，有时更快。

最后一步不要什么码都试。面单场景里多半是 Code 128 和 QR，用  `POSSIBLE_FORMATS`  收窄，速度和误判都会好一截。 `TRY_HARDER`  会多花时间找难图，适合模糊、偏转的照片，干净的电子码不必每次都开。

![](assets/2026-11-01%20-%20ZXing%203.5%20%EF%BC%88%20Java%E7%89%88%20%EF%BC%89%20%E5%88%B0%E5%BA%95%E6%9C%89%E5%A4%9A%E5%BC%BA%20%EF%BC%9F/760c62eb6781fd35414d055581562dbe_MD5.jpg)

## 3.5.4 这次到底改了什么

相对 3.5.3，没有新码制。发布说明看着碎，用起来都是「以前会踩、现在少踩」。

**灰度图可以直接送进去。** 新增  `GrayscaleLuminanceSource` ，构造方法是  `GrayscaleLuminanceSource(width, height, pixels)` ，像素按行排列。图如果本来就是灰度，不必再包一层 RGB。 `RGBLuminanceSource`  改成了它的子类，并且补上了逆时针转 90 度。手机横拍的图，可以在亮度图上转，少写一遍图像旋转。彩色像素还会先检查数组长度是否等于宽乘高，对不上就早点失败，避免后面抛数组越界。

**一张图里有多个二维码时，结果更完整。**  `QRCodeMultiReader`  以前会丢掉符号标识  `SYMBOLOGY_IDENTIFIER` ，和单个  `QRCodeReader`  对不上。3.5.4 把这份元数据留了下来。对接 GS1、或者要区分同一张图里不同码的标识时，这个字段用得上。

**PDF417 少了两个闷坑。** 文本压缩模式  `Compaction.TEXT`  只接受码点 0 到 127 的字符，超出会抛明确异常。以前有机会生成一张看起来正常、内容却不对的码。另一个问题是指定行列范围时，内容明明放得下，却报  `Unable to fit message in columns` 。issue 1831 里那种「把最小列数调大就突然能画」的情况，尺寸推算已经修正。

**几种条码的识别更稳一点。** RSS Expanded 的读取去掉了一处低效的容器操作，批量扫的时候少做无用功。ITF 放宽了 3 倍模块宽度的误差上限，印刷略歪的交叉二五码更容易读出来。二维码估算模块数时，合法边长必须是「除以 4 余 1」。以前只自动修正差 1 的结果，差 2 就放弃；3.5.4 会向下减 2，拉回合法尺寸。三个定位角点构成等腰直角三角形时，畸变计算也修正了。

**邮箱解析更严。** 结果被当成邮箱时，格式检查收紧了，怪字符串不再轻易判成邮件地址。

这些都不是首页功能。常年跑批的人会在意：少一个越界，少一次 PDF417 死活画不出来，多个二维码时元数据还在。

```xml
<dependency>
    <groupId>com.google.zxing</groupId>
    <artifactId>core</artifactId>
    <version>3.5.4</version>
</dependency>
<dependency>
    <groupId>com.google.zxing</groupId>
    <artifactId>javase</artifactId>
    <version>3.5.4</version>
</dependency>
```

这一代按 Java 8 来用就行。版本号三个包保持一致，避免 core 和 javase 各写各的。

## 案例：生成一张门票二维码

下面这段会写出  `ticket-qr.png` 。纠错用 M，脏一点、褶一点也还有机会读回来。边距留 1 个模块，打印和展示都比较稳妥。字符集指定 UTF-8，中文才不会在生成阶段就乱掉。

```java
import com.google.zxing.BarcodeFormat;
import com.google.zxing.EncodeHintType;
import com.google.zxing.WriterException;
import com.google.zxing.client.j2se.MatrixToImageWriter;
import com.google.zxing.common.BitMatrix;
import com.google.zxing.qrcode.decoder.ErrorCorrectionLevel;
import com.google.zxing.MultiFormatWriter;

import java.io.IOException;
import java.nio.file.Path;
import java.util.HashMap;
import java.util.Map;

/**
 * 门票二维码生成示例。
 */
public class TicketQrWriter {

    /**
     * 把门票信息写成一张 QR 图。
     *
     * @param file 输出的 PNG 路径
     */
    public static void write(Path file) throws WriterException, IOException {
        Map<EncodeHintType, Object> hints = new HashMap<>();
        hints.put(EncodeHintType.CHARACTER_SET, "UTF-8");
        hints.put(EncodeHintType.ERROR_CORRECTION, ErrorCorrectionLevel.M);
        hints.put(EncodeHintType.MARGIN, 1);

        String content = "门票:A-1024,入场:2026-11-02 17:25:17";
        BitMatrix matrix = new MultiFormatWriter().encode(
                content,
                BarcodeFormat.QR_CODE,
                360,
                360,
                hints);
        MatrixToImageWriter.writeToPath(matrix, "PNG", file);
    }
}
```

换成  `BarcodeFormat.CODE_128` ，宽高改成细长条，就是物流单上常见的一维码。PDF417 用  `BarcodeFormat.PDF_417` 。如果明确指定了  `Compaction.TEXT` ，内容里出现中文或别的非 ASCII 字符，3.5.4 会直接告诉你不行。这种情况改用自动或字节压缩，或者先确认内容是不是纯英文和数字。

边距不要为了「图小一点」设成 0。码四周那圈空白叫静区，裁掉之后，生成成功，识别却经常失败。

## 案例：把图里的内容读回来

识别时我习惯把码制写死。全码制来回试也能工作，但业务里码的种类通常是知道的。

```java
import com.google.zxing.BarcodeFormat;
import com.google.zxing.BinaryBitmap;
import com.google.zxing.DecodeHintType;
import com.google.zxing.GrayscaleLuminanceSource;
import com.google.zxing.LuminanceSource;
import com.google.zxing.MultiFormatReader;
import com.google.zxing.ReaderException;
import com.google.zxing.Result;
import com.google.zxing.client.j2se.BufferedImageLuminanceSource;
import com.google.zxing.common.HybridBinarizer;

import javax.imageio.ImageIO;
import java.awt.image.BufferedImage;
import java.io.IOException;
import java.nio.file.Path;
import java.util.Collections;
import java.util.EnumMap;
import java.util.Map;

/**
 * 从图片中读取二维码。
 */
public class TicketQrReader {

    /**
     * 读取 PNG 里的二维码文本。读不到时返回 null。
     *
     * @param file 待识别的图片
     * @return 码内文本；图糊、静区被裁掉或码制不对时返回 null
     */
    public static String read(Path file) throws IOException {
        BufferedImage image = ImageIO.read(file.toFile());
        LuminanceSource source = new BufferedImageLuminanceSource(image);
        BinaryBitmap bitmap = new BinaryBitmap(new HybridBinarizer(source));

        Map<DecodeHintType, Object> hints = new EnumMap<>(DecodeHintType.class);
        hints.put(DecodeHintType.CHARACTER_SET, "UTF-8");
        hints.put(DecodeHintType.POSSIBLE_FORMATS,
                Collections.singletonList(BarcodeFormat.QR_CODE));
        hints.put(DecodeHintType.TRY_HARDER, Boolean.TRUE);

        try {
            Result result = new MultiFormatReader().decode(bitmap, hints);
            return result.getText();
        } catch (ReaderException ex) {
            // 没找到、校验失败、格式不对，都算这张图没有读出来
            return null;
        }
    }
}
```

二维码通常自带编码信息， `CHARACTER_SET`  对一维码更关键。多个二维码要一次拿全，可以改用  `QRCodeMultiReader` ，3.5.4 里每个结果的  `SYMBOLOGY_IDENTIFIER`  会保留在  `result.getResultMetadata()`  中。

图如果已经是灰度字节，走新类即可。数组长度必须等于宽乘高。

```java
/**
 * 用灰度像素解码，横拍时先逆时针转 90 度。
 */
public class GrayTicketDecoder {

    /**
     * @param pixels 按行排列的灰度值，0 为黑，255 为白
     * @param rotate 为 true 时逆时针旋转 90 度后再识别
     */
    public static LuminanceSource toSource(byte[] pixels, int width, int height, boolean rotate) {
        LuminanceSource source = new GrayscaleLuminanceSource(width, height, pixels);
        if (rotate) {
            source = source.rotateCounterClockwise();
        }
        return source;
    }
}
```

读失败在业务里单独分支就好，多半是图糊、反光、码制没配对，或者静区没了。把它记成系统异常，后面会很难查。
