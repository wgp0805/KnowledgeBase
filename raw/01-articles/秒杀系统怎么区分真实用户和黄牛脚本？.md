胖虎 Java专栏 *2026年8月20日 12:20*

大家好，我是胖虎。

前几天看到一个秒杀防刷的方案，思路是这样的：用户打开活动页，前端先调一个预检接口，服务端生成一个随机串，按时间戳算出的位置往里插一个标记字符，扔进 Redis 存 30 秒；前端本地用同一套算法算一遍；用户点"立即抢购"的时候把结果带上，服务端拿出来比一比，对不上就拒。

方向是对的。这类轻量校验在秒杀里确实比验证码实用得多——秒杀的时间窗口就那么十几秒，你多插一步人机交互，转化率立刻掉一截。

但我看到不少人把这一层当成"防刷方案"本身。它不是。它是整套体系里最外面、也是最容易被绕的一层，而且大部分实现里还漏了一个能让它彻底失效的细节。

今天把这套东西从头到尾捋一遍：每一层到底能防住谁、防不住谁，以及一个我觉得比所有技术细节都重要的原则—— **别让黄牛知道他被拦了** 。

这个方案的本质，是给每次下单请求附上一个"你确实打开过页面"的证明。

它有效吗？有效。但得先认清一件事： **任何跑在浏览器里的算法，都是混淆，不是加密。**

代码在用户机器上，F12 打开就能看，逻辑再绕也就是多花几个小时。黄牛团队里做逆向的人，扒一套前端算法是基本功。你把字段名从 `randomString` 改成 `result` 、从 `timestamp` 改成 `key` ——这确实有用，但用处是让对方多花二十分钟，不是让他放弃。

那它凭什么值得做？

因为它把作弊成本从 **零** 变成了 **有** 。

真正在秒杀流量里占大头的，不是那种能扒你 JS 的专业团队，是一堆拿 Postman 抓个包、写个 for 循环重放的散户脚本。这批人根本不看前端，直接照着抓到的请求怼。校验串一上，他们全军覆没。

所以给它的定位应该是： **过滤掉不看前端的批量工具，把对手筛成"愿意花时间逆向的那一小撮"。** 剩下那撮人，交给后面几层。

把它当成一道墙，它一定让你失望。把它当成一个筛子，它性价比极高——服务端就一次 Redis 读，几乎不花钱。

## 大部分实现漏掉的两个洞

原方案里有一句"仅执行一次 Redis 读操作"，这是对的——秒杀场景下每多一次 IO 都要算账。

但只读不删，这一层直接废掉一半。

**洞一：校验串必须是一次性的。**

你 GET 出来比对完就走了，那这个串在 30 秒有效期里可以被重放多少次？无数次。

黄牛正常打开一次页面，拿到一个合法校验串，然后在这 30 秒里用它发一万个请求——每一个都能通过校验。你辛辛苦苦加的这一层，对他来说只是"多调一次预检接口"。

正确做法是 **取出即失效** ，而且必须是原子的。Redis 6.2 之后有现成的命令：

```
// GETDEL：取值和删除在一个原子操作里完成
// 读和删之间没有任何其他客户端能插进来
String expected = 
            redis.getDel(
          "sk:token:" + uid);
if (expected == null || !
            expected.equals(req.getResult()))
           {
    return 
            Result.fail(
          "请刷新页面重试");
}
```

如果你的 Redis 还在 6.2 以下，用 Lua 保证原子性：

```
local v = 
            redis.call(
          'GET', KEYS[1])
if v then 
            redis.call(
          'DEL', KEYS[1]) end
return v
```

千万别写成 `GET` 之后再 `DEL` 两条命令。高并发下这两步之间就是竞态窗口，同一个串会被多个请求同时取到、同时通过。你以为自己防了重放，其实只是把重放次数从无限降到了几十次。

**洞二：校验串必须绑用户。**

如果 Redis key 是 `sk:token:{随机串}` 这种不带身份的设计，那黄牛的玩法是：拿一个正常账号疯狂调预检接口，攒一大把合法校验串，然后分发给一百个小号一起用。

key 里必须带 uid，服务端校验的时候只认"这个人自己领的那个串"。同时预检接口本身也要限流——不然攒串这个动作就变成了新的攻击面。

## 真正难伪造的信号，不在请求体里，在时间上

请求体里的东西，只要是客户端能算出来的，黄牛就能算出来。这是死结。

但有一类信号他很难伪造，因为伪造它意味着放弃他花钱买脚本的理由。

**人的操作是有抖动的。** 页面加载完，眼睛扫一下，手移过去，点击。这个过程从几百毫秒到几秒不等，而且分布是长尾的——有人 800ms，有人 3 秒，有人打开页面等了十分钟。

脚本不是这样。脚本要么请求间隔精确到恒定，要么死死对齐服务器开抢时间的某个毫秒——因为它存在的全部意义就是比人快。

关键就在这儿：

**黄牛想把行为信号伪造得自然，就必须引入随机延迟；一旦引入随机延迟，他就丢掉了速度优势；而速度优势正是他掏钱买脚本的原因。**

这是防守方少有的、天然占经济学便宜的地方。绝大多数对抗手段是"我加一层、他破一层"，成本对称；行为信号这一层不对称——他破解的代价是让脚本变得没意义。

具体能采什么：

页面从加载到提交的间隔、有没有真实的鼠标移动或触摸事件、请求到达时刻相对开抢时刻的偏移、同一账号历史几次抢购的时间模式。

有一点要说清楚： **这些信号一条都不能单独定罪。** 网速快的用户 300ms 提交完全正常，用键盘操作的用户没有鼠标轨迹也正常。它们的正确用法是加权算一个风险分，交给后面几层去用。

## 限流按 IP，等于给黄牛送人头

见过太多方案上来就 IP 限流。这条几乎没用，还容易帮倒忙。

黄牛的代理 IP 池按天算钱，几百块能拿到几万个动态 IP，比你写的规则多得多。而按 IP 限流第一个误伤的，是同一个公司出口、同一个学校 NAT、同一个运营商大客户后面的正常用户——他们对外看起来就是一个 IP 发了几百个请求。

真正稳的限流维度是：账号、设备指纹、手机号、收货地址、支付账号。

但账号能批量注册。所以真正的防线其实还要再往前移，移到 **准入** ：

注册满多少天、有没有历史订单、有没有实名、有没有绑定过支付方式、账户里有没有真实的行为轨迹。

大厂秒杀活动经常写"仅限注册满 30 天的用户参与"，看着像一句无关痛痒的规则，实际上它是整套防刷里性价比最高的一条。因为 **养号的时间成本，是黄牛唯一压不下去的成本。** IP 能买，设备指纹能改，脚本能写，唯独三十天就是三十天。

这一层几乎不花技术成本，效果比后面所有技术手段加起来都好。可惜讨论秒杀架构的时候很少有人提，因为它不够"技术"。

还有一个实现上的坑要提醒。用 Redisson 的 `RRateLimiter` 做分布式限流，它底层是 Lua 脚本，每次 acquire 走一次 Redis 往返——这本身没问题，问题在于 **限流器自己就是一个 Redis Key** 。

秒杀峰值下，全站请求都往同一个限流 Key 上打，这个 Key 会瞬间变成整个集群最热的热点 Key，把它所在的那个节点单独烤糊。你为了保护系统加的限流，成了第一个倒下的组件。

正确姿势是两级：

本地先限（Guava RateLimiter 或者信号量），按实例数把总配额粗略切一下，绝大部分超额请求在进程内就被挡掉，根本不出网；漏下来的那一小部分再走分布式限流做精确控制。

粗筛在本地，精算在远端。

## 别拉黑，让他赢一个假的

前面几层都是技术活。这一节是思路问题，也是我觉得整套体系里最重要的一条。

假设你的风控识别出一个高风险请求了。接下来怎么办？

大部分实现是返回一个明确的错误：「操作过于频繁」「请求异常，请稍后再试」「账号存在风险」。

这是最差的处理方式。

因为你给了对手一个 **免费的、可以无限次调用的检测器** 。

黄牛拿到这个报错之后会做什么？二分查找。改 UA 试一次，加 200ms 随机延迟试一次，换设备指纹试一次，降低并发数试一次——每一次他都能立刻知道自己有没有踩线。你花几个月设计的风控规则，会在几个小时内被摸得干干净净。

而且他摸清之后不会告诉你，会一直用。

正确的做法是： **让被标记的请求，走完全部正常流程，然后自然地失败。**

排队中——正常返回。库存扣减——进一个假的队列。最后给他一个「很遗憾，商品已售罄」。

页面表现和一个真的手慢了的用户一模一样。他不知道自己是被拦了还是没抢过别人，也就没法调参。

这个思路在反滥用领域有名字，叫影子封禁（shadow ban），或者焦油坑（tarpit）。核心只有一句： **不给对手任何反馈信号。**

用的时候有个边界要守住：这招只能用在高置信度的标记上。误伤了正常用户，人家是真的以为自己没抢到，客服那边你连解释都没法解释。中等风险的请求不要影子拦截，给它一个验证挑战——这就引出下一层。

## 验证码不是不能用，是不能对所有人用

「秒杀不用验证码，多一步交互就多一层流失」——这话对了一半。

对的那一半：不能让所有人过验证码。秒杀漏斗本来就窄，全员加一道交互，转化率能掉两位数。

错的那一半：现在的验证码早就不是"给所有人弹一个图"了。

业界标准做法是 **风险驱动** ：后台静默采集信号算风险分，绝大部分用户全程无感直接放行，只有分数超线的那一小撮才真的看到交互挑战。Cloudflare 的 Turnstile 走的就是这个逻辑——低风险访客自动通过，可疑流量才拿到一个非文字的点击挑战，官方数据是拦下上百万次自动化注册的同时，正常注册转化没有可观察的变化。

所以问题从来不是"要不要上验证码"，而是"验证码放在漏斗的哪一层触发"。

放在所有人面前，是灾难。放在风险分最高的 1% 面前，成本约等于零，效果直接。

## 最后一道防线，在下单之后

前面所有的判断都发生在同一个瞬间——用户点下按钮的那几十毫秒里。这个时间窗口能跑的规则极其有限，你不可能在这里做图计算、做聚类、查历史。

但订单一旦产生，情况就完全变了。

你有几个小时，甚至几天。这段时间里你可以做 **非常重** 的批量分析：

同一个收货地址下了多少单、同一栋楼的地址做模糊聚类之后有多少单、同一个设备指纹关联了多少账号、同一个支付账号付了多少笔、这批订单的下单时间分布是不是一根针。

这些计算在下单那一刻根本跑不动，在事后跑起来毫无压力。风控在这一层的召回率，比在下单瞬间高一个数量级。

拦截点也不止一个：支付前可以拦，发货前可以拦，甚至可以只做标记然后人工抽查。

而这一层最狠的地方在于，它直接打的是黄牛的现金流。

他的成本在抢到那一刻就已经全部付出去了——账号、代理 IP、设备农场、脚本开发、蹲点的人力。你在履约环节把单一拦，他的收益是零，成本一分不少。

抢到 ≠ 拿到货。这句话是黄牛最不愿意听到的。

## 我的分层

从上到下，按"成本低、效果好"排序：

**第 0 层，准入门槛。** 注册天数、历史订单、实名、支付绑定。技术成本几乎为零，效果最好，因为它攻击的是黄牛唯一压不下去的时间成本。

**第 1 层，前端校验串。** 一次 Redis GETDEL，绑 uid，一次性。挡掉所有不看前端的批量工具。

**第 2 层，行为信号打分。** 时间抖动、交互轨迹、请求偏移。不定罪，只算分。

**第 3 层，两级限流。** 本地粗筛 + 分布式精算。目标是保护系统，不是维护公平——别指望限流能防住黄牛。

**第 4 层，风险驱动验证。** 只对高分用户弹。

**第 5 层，影子拦截。** 高置信度标记走这条，不给任何反馈。

**第 6 层，事后追溯与履约拦截。** 召回率最高的一层，直接打现金流。

还有一条横穿所有层的要求，原方案里提到了，我很认同： **每一层的每一个参数，都必须能秒级开关。**

阈值、开关、白名单，全部放配置中心。因为秒杀出问题的时候，你没有时间发版。规则误伤了、限流卡死了、某一层被绕穿了，你需要的是三十秒内把它关掉，而不是走一遍发布流程。

这条不写进方案，前面六层设计得再漂亮，上线那天都是摆设。

## 最后

防刷这件事，目标从来不是"把黄牛挡在门外"。挡不住的——他有钱、有时间、有专门做这行的技术团队，而你只是把它当成众多需求里的一个。

真正的目标是 **让他这一单不赚钱** 。

黄牛的成本结构很清楚：账号、设备、IP、脚本、人力、时间。你设计的每一层，作用都不是"拦住"，而是"抬高其中某一项"。抬到超过他转手的差价，这门生意自己就黄了。

从这个角度重新看前面六层，你会发现最有效的那几层——注册天数、行为信号、履约拦截——恰恰是技术含量最低的。而技术含量最高的前端加密校验，反而是最容易被绕的。

这事挺反直觉，但它就是这样。

如果你手上正好有个秒杀要做，我的建议是先去把第 0 层和第 6 层补上，再回头抠前面那个校验串怎么写更巧妙。顺序反了，前面写得再精细也是白费。
