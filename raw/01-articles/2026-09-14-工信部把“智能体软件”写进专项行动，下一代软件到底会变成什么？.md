# 工信部把“智能体软件”写进专项行动，下一代软件到底会变成什么？

> **来源**: 人人都是产品经理  
> **链接**: https://www.woshipm.com/ai/6464485.html  
> **抓取日期**: 2026-09-14  
> **相关性评分**: 1.0

> 工信部“人工智能+软件”专项行动方案发布，智能体软件被定义为大模型与软件深度融合的新形态。当软件从等待点击按钮转向理解目标、调用工具、跨系统推进工作，产品经理的设计对象正从功能转向完整的工作流。本文从产品视角拆解下一代软件必须补上的四层能力，以及Agent时代产品作为入口的地位变化。

![](https://image.woshipm.com/2025/04/24/d0b84e68-20fd-11f0-b1a0-00163e09d72f.png)

9 月 11 日，工信部公开了《“人工智能+软件”专项行动实施方案》。我不打算在这里复述政策条文，更想借这件事谈一个产品问题：当软件不再只是等用户点按钮，而是开始理解目标、调用工具、跨系统推进事情，我们到底还在设计一组功能，还是已经在设计一项工作？

官方解读把“智能体软件”定义为“大模型与软件深度融合形成的新形态”，并提到感知、记忆、决策、交互和执行，以及应用功能聚合重组、跨系统协作网络。发布会上，软件生产方式、产品形态和服务模式的变化也被放到了一起。对做产品的人来说，这比“又多了一种 AI 产品”更值得看，因为它碰到的是软件到底围绕什么来组织。

今天的软件其实已经不缺 AI 功能。总结、生成、问答、搜索、助手，成熟产品都可以继续往里加。真正难的是，AI 加进去以后，产品是不是仍然按照原来的页面、菜单和功能来组织，还是开始围绕一项真实工作重新安排能力。

## 一、从功能表到一项工作，产品设计对象正在变

我做软件项目这些年，有一个场景很熟悉。需求会上经常是一串很具体的动作：加一个页面、加一个字段、加一个按钮，再接一个接口。每一项都没错，但项目做完以后，用户还是要自己记住事情做到哪一步，在几个系统之间来回切换，再判断下一步该找谁。

传统软件很擅长把现实工作拆成一个个确定的 Function。查询是一个功能，生成是一个功能，审批是一个功能，提交也是一个功能。产品经理围绕这些功能设计页面、交互、权限和流程，这套方法已经非常成熟。

大模型刚进入软件时，其实也没有改变这套逻辑。让 AI 总结一份材料，是增加一个功能；让 AI 写一份方案，是增加一个功能；在系统里放一个智能助手，仍然是在原来的产品结构里加一项能力。

变化真正开始变得有意思，是 AI 能围绕同一个目标连续做事。它先理解当前任务，找到相关材料，判断还缺什么信息，调用不同工具处理，再根据结果决定下一步；到了需要人承担责任的地方，把问题交还给人，确认之后再继续。

这时候，产品面对的已经不只是一个孤立的 Function，而是一项需要持续推进的 Work。

**Function 没有消失，但 Function 开始变成完成 Work 的能力。**

这句话并不是说所有产品都要改造成 Agent。它更像是在提醒产品经理：做需求时，除了问“用户要什么功能”，还要再往前问一层——用户真正要完成的是什么工作？这项工作持续多久？哪些状态需要跨时间保存？哪些动作会跨系统？什么地方必须由人确认？

工信部这次在谈工业软件时，也把“AI 辅助”和“AI 原生”作为两条不同路径来讨论。前者是在既有架构上叠加智能功能，后者则让模型进入软件核心能力，并进一步影响研发和运行逻辑。至少在这个场景里，“加 AI”和“重新设计软件”已经不是一回事。

## 二、Agent 不一定会把软件“吃掉”，但产品作为入口的地位会变

现在经常有人问，Agent 会不会最终取代传统软件。我不太相信这种“一把吃掉”的故事。合同系统里的合同事实、财务系统的账务规则、项目系统里的状态和权限，并不会因为出现一个通用 Agent 就自动失去价值。

真正可能变化的是入口。今天做一件事，我们通常先想应该打开哪个系统；但真实工作经常同时需要客户信息、合同、项目数据、企业知识和外部服务。系统边界和工作的边界，本来就不是一回事。

如果 Agent 能围绕当前工作去调用不同系统的能力，用户未必还要自己记住每一步该去哪个软件完成。对他来说，更自然的入口可能是“我现在要把这件事做完”。至于背后调用了 CRM、知识库还是项目系统，会逐渐退到第二层。

这也是“跨系统协作网络”这个表述值得产品经理留意的地方。它冲击的未必是产品本身，而是产品作为唯一入口的地位。

独立产品仍然会存在，也会继续承担自己的业务事实、规则和责任；但产品里的能力会越来越多地被新的入口调用。产品经理因此要多考虑一层：不仅是“人怎么使用这个功能”，还包括“Agent 怎样正确地发现、调用和约束这个能力”。

## 三、未来的软件，可能既要“给人用”，也要“给 Agent 用”

这次专项行动还有一条容易被技术讨论盖过去的线索：服务模式也在变化。发布会上，中国软件行业协会副理事长兼秘书长吕卫锋谈到，智能软件服务正在从产品销售向持续服务运营变化，并由出售产品向出售能力、出售结果拓展，“模型即服务”“智能体即服务”等新模式也在出现。

这里不能简单理解成，以后所有软件都要改成按结果收费。更现实的变化是，客户购买的对象可能不再只有“一套系统”。有些产品仍然以完整系统存在，有些能力则会通过 API、Skill、Agent 服务，或者更完整的智能应用服务链被调用。

这会反过来影响产品怎么拆。以前一个功能模块能不能独立复用，主要考虑内部架构；以后还要考虑它能不能被外部 Agent 安全调用，需要什么上下文，权限怎么判断，异常时怎样退出，结果又怎样回到原来的业务系统。

我觉得这里会出现一个很实际的“双入口”问题。人的入口关心页面、流程和体验；Agent 的入口更关心能力定义、上下文、权限、返回结果和错误边界。两套入口不是互相替代，而是很可能长期共存。

## 四、Agent 能做得越多，产品越要设计“什么时候不能做”

如果软件只是给答案，边界问题相对简单。Agent 一旦开始替人行动，问题就会变得具体。

还是拿投标准备来说。一个 Agent 可以读招标文件、提取评分项、找企业资质、生成技术方案；如果再给它工具，它还可以填写表格，甚至准备提交。但“技术上可以提交”和“业务上允许这次提交”，显然不是一件事。

所以我在看 Agent 产品时，会把五件容易混在一起的事拆开：能力（Capability）、系统权限（Permission）、业务授权（Business Authority）、正式效果（Effect）和责任（Responsibility）。一个能力存在，不代表当前 Agent 有权使用；有系统权限，也不代表这一次业务上已经授权；接口调用成功，也不意味着业务效果已经正式成立；即使结果已经生效，最终责任也不能自然推给 AI。

这些区别最后都会落成具体的产品设计：哪些动作只能给建议，哪些可以形成候选结果，什么情况下必须让人确认，授权是一次性的还是有时效的，环境发生变化以后旧授权是否仍然有效。

三部门今年 5 月发布的《智能体规范应用与创新发展实施意见》，已经明确提出要区分仅限用户本人决策、需要用户授权的决策和智能体可以自主决策的范围，并要求智能体执行操作不得超出用户授权。

所以我越来越觉得，Governance 以后不会只是后台里的一个权限管理页面。一个 Agent 产品设计得好不好，除了看它会不会做事，还要看它知不知道什么时候必须停下来。

## 五、从产品经理视角看，下一代软件至少要补四层能力

如果软件真的要从一次性响应，进一步进入真实工作的持续推进，我现在更愿意用四个很朴素的问题去检查一个产品：它认不认得清，接不接得上，推不推得动，最后兜不兜得住。

“认得清”，是系统知道现在处理的是哪项工作、面对什么对象，此刻哪些信息真正相关。它对应的是 Workspace 和 Context。一个 Agent 连自己当前处在什么工作里都不清楚，工具越多，做错事的可能性反而越大。

“接得上”，是一项工作跨时间以后仍然连续。昨天确认过的事实今天是否仍然有效，过去的经验和当前数据怎样进入这一次工作，哪些内容应该继续记住，哪些已经过期。这背后是 Knowledge 和 Memory。

“推得动”，意味着工作不是执行一次 Prompt 就结束。系统需要根据执行结果决定下一步，遇到异常能够调整，并让同一件事跨动作、跨系统甚至跨几天继续。这背后是 Work Loop。

“兜得住”，是权限、授权、业务效果和责任边界能够落到产品运行里。什么能自动做，什么必须让人确认，出了问题能不能还原当时发生了什么。这背后是 Governance 和 Responsibility Boundary。

这四层不是为了再造一套新名词。它们其实都在回答一个产品经理最熟悉的问题：这个产品到底能不能把用户的一件事情真正承接下来？

## 结语：真正要重新设计的，可能不是界面，而是软件围绕什么组织

“下一代软件”现在还没有统一答案，我也不认为所有软件都会变成同一种形态。传统业务系统不会突然消失，Function 也不会消失。

更可能发生的，是它们之间的组织关系变化：Function 越来越多地成为完成 Work 的能力；独立产品继续保存自己的数据、规则和业务事实，同时把部分能力提供给新的工作入口；Agent 开始参与真实工作，治理也进入每一次关键行动。

站在产品经理的位置看，这可能比“下一代界面是不是聊天框”更重要。界面还会变，Agent 的形态也会继续变，但有一个问题已经越来越难绕过去：我们到底还在设计一组功能，还是开始设计一个能够持续参与工作的产品？

工信部把“智能体软件”写进专项行动，并没有替整个行业回答这个问题。但至少说明，围绕这个问题的讨论，已经不只是少数 AI 产品团队内部的探索，它开始进入软件产业本身。
