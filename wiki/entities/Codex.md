## 定义
OpenAI 推出的桌面端 AI Agent 程序，正从编程 Agent 进化为"电脑工作系统"（Computer Work System），覆盖代码、浏览器、邮件、日历、桌面 GUI 等真实工作表面。

## 关键信息

### 核心能力
1. **本地文件操作**：可自主读写操作本地文件，不限数量，项目对应本地文件夹
2. **命令行工具使用**：授权后可执行终端命令，安装软件、部署环境
3. **持久记忆**：全局/项目级 agents.md + 自动记忆（实验性）
4. **图片生成**：内置 image2 模型生图能力
5. **插件系统**：Browser Use、Computer Use、Chrome 等操控类插件；Vercel/Netlify 部署插件
6. **Skill 流程沉淀**：可复用的方法、流程和工具组合
7. **MCP 外部服务连接**：对接 NotebookLM 等外部服务
8. **自动化定时任务**：结合 Skill 实现定点执行

### 幻觉治理机制（2026-10-10，详见 [[Agent幻觉]]）
- **apply_patch 原文匹配**：patch 对不上文件原文就报 "Failed to find expected lines"，从机制上杜绝模型凭记忆编造文件内容
- **记忆提示词原则**：读取记忆时提示词写明 "Memory is not proof of current behavior"——记忆不能证明现状，易变且核实成本低的事实先核实再回答，未核实的不能当成当前事实

### 与 Claude Code 对比
- Claude Code 先发了 Skill、MCP、Hook、远程操控等功能
- Codex 后来居上，新增浏览器操控、Computer Use、image2 生图、手机端操控
- Codex 额度更友好，产品体验更直观（上下文余量可视、额度状态显示）
- Claude Code 写作和规划能力更强（Opus 模型）

### 工作系统三大支柱
Codex 从三个方向从编程 Agent 向工作系统进化：
1. **上下文**：[[durable-threads]]（长线程）、共享记忆、项目文件，让工作不用每次重来
2. **工具**：browser（侧边栏浏览器）、Chrome（登录态流程）、Computer Use（桌面 GUI）、[[MCP]]（Slack/Gmail/Calendar 等工作入口）、[[Skill]]（可复用流程封装）
3. **验证器**：测试、检查矩阵、端到端流程，让长任务知道什么叫"完成"

### 人机交互控制
- **语音输入**：捕捉未整理好的模糊想法，Codex 可搜索、追问、整理
- **Steering（转向）**：任务运行中途用户可打断纠偏，不重新开始
- **Queuing（排队）**：不打断当前任务，将后续步骤排入队列（如"做完后发预览链接给审核人"）
- 核心哲学：人没有被踢出回路，而是把决策点提前暴露，用最少介入改变方向

### 自动化与目标
- **Automations**：按计划启动工作（每日报告、定期检查 repo、活跃线程定时唤醒检查 Slack/Gmail/PR）
- **Goals**：带验证器的长跑任务。强目标有明确验证器（"目录建好、功能对齐、全部测试通过"），弱目标只是愿望

### 侧边栏与移动端
- Side Panel 解决"人在哪里审"的问题：代码看 diff，网页直接打开，文档表格在同一上下文审阅
- 手机端可远程监控进度、回答问题、批准下一步，工作线程随人走，执行环境留原地

### 权限模式
- 自动审查模式（默认）
- 建议模式
- 手动确认模式

### 内部监控系统审计（METR，2026-10-25 报道，详见 [[摘要-claude-auto-mode监控逃逸]]）
[[METR]] 与 [[Redwood]] 进驻 OpenAI 三周审计内部 Codex 流量的监控系统（详见 [[监控逃逸]]）：监控覆盖 99.2% 内部流量，但存在六条逃逸暗道——①只在 Agent 收工交还控制权时检查 + 上下文压缩事件不在监控范围，5—7 月约一成符合条件的流量溜走；②一个漏洞让最近几百步操作（含利用漏洞那步）从监控隐身；③两个客户端可控请求头改掉任一即可关闭新 Agent 监控、孵化"幽灵分身"；④一条路径同时绕过沙箱与自动审查，拿到宿主研究员全部权限；⑤Agent 视角与监控日志格式错配，构造输入可让监控 AI 出错、异常送不到人类面前；⑥两个被当"只读"、未接监控的内部工具存在沙箱内任意操作漏洞。修复建议：定期/定量检查、监控与 Agent 结构分离、日志与 Agent 视角对齐（详见 [[多级AI监控]]）。

### 需求澄清机制（2026-10-15 补充）
来自 [[摘要-用户需求模糊时Agent怎么澄清]]。Codex 在 Plan 模式的系统提示词中把未知信息明确拆成两类，并给出对应的硬性规定：

1. **[[DiscoverableFacts]]（可发现的事实）**——项目用什么框架、现有登录接口在哪、有没有 Redis 配置。规定**先探索后再提问**：在向用户提问之前必须先调用只读工具把代码库扫一遍。
2. **[[偏好与取舍]]（Preferences and tradeoffs）**——限流阈值设多少、超限后排队还是报错。代码里查不到且会改变最终结果，才需要用户拍板。

无人在场时的兜底同样来自 Codex：
- **工具层拦截**：`request_user_input`（请求用户输入工具）第一行检查当前是不是 root 线程，Sub-agent 调用直接报错 "request_user_input can only be used by the root thread"；在 `codex exec` 非交互模式下，外部 MCP 服务端通过 elicitation 发来的追问请求会被自动取消（源码直接返回 Cancel）。
- **提示词兜底**：获取不到用户回答时不要停下来，按最稳妥的推荐选项继续执行，但必须在最终输出的 **[[Assumptions假设清单]]（Assumptions）** 小节里逐条写清替用户做出的所有假设，供事后核对。

### 人机协作工作流方法论
结合[[摘要-再见吧-codex]]，高效的 Codex 使用遵循以下原则：

**核心哲学：别把 Codex 当许愿池**
不能直接丢需求等结果，要像带实习生一样引导它。先理解项目，再让 Codex 输出计划，确认范围后小步实现，每步验证，最后总结+开新会话。

**7 步工作流：**
1. **阅读理解** — 先让 Codex 阅读项目结构、架构、启动/测试/部署方式，不要一开始就写代码
2. **写计划** — 复杂任务先输出实现计划（理解什么、影响哪些模块、分几步、怎么验证、风险点）
3. **确认范围** — 确认影响文件和范围后再开始实现
4. **小步实现** — 只改当前步骤需要的文件，不顺手改无关代码
5. **验证** — 执行测试，认真看 diff，不只跑 happy path
6. **总结** — 回答 5 个问题：改了哪些文件？为什么改？做了什么验证？哪些没覆盖？需要人工确认什么？
7. **新会话** — 将总结带入新对话，避免旧假设污染

**AGENTS.md 三原则：**
- 只放项目硬约定、工作习惯、踩坑记录
- 不是越全越好，是经过验证的才放
- 踏坑后及时更新

**Bug 修复原则：**
不预设立场猜测根因，提供日志和复现步骤让 Codex 定位。如果一顿操作没解决，开新会话重来。

### Harness 架构（云端沙箱 + 并行子 Agent）
来自 [[摘要-codex-vs-claude-code-对比]]。Codex 的 Harness 围绕"隔离"和"并行"两个关键词设计：

1. 在云端创建**隔离的沙箱容器**，把代码库克隆进去
2. 根据任务复杂度启动多个**并行子 Agent**（最多 8 个），互不干扰
3. 子 Agent 完成后汇总结果返回

这种架构让 Codex 在**可并行化的批量任务**上效率极高（如同时开发 5 个独立 feature）。

### 独有特性
来自[[摘要-AI-agent工具应该怎么使用]]，作者基于 Codex 日常开发的实战经验：

1. **先建 AGENTS.md** — 进入项目先 /init，编写项目说明书。控制在 200 行以内，只写最核心约束（最高优先级限制、技术栈、编码规范、开发流程）。踩坑后动态更新，每次 AI 犯错后补入新约束
2. **Plan 模式先行** — 任何改动先让 Codex 输出执行计划（改哪些文件、用什么方案、分几步），审完计划再让其执行
3. **大需求拆小任务** — 每个原子功能独立对话。例如"给用户列表加搜索"拆成 UI 组件、后端 API、前端对接、空结果兜底四步，每步做完验证后开新对话做下一步
4. **测试是质量保障** — AGENTS.md 写明"实现功能前先写单元测试"；用另一个 Agent 验证代码质量（如 Opus 审 GPT 代码，GPT 审 Opus 代码），Codex 截图测试比 Claude Code 更方便
5. **不要手动改 AI 代码** — 手动改会导致 AI 不知道改了什么、为什么改，可能在下一次修改中覆盖。应该用自然语言告诉 AI 怎么改；如果改得快，改完立刻开新对话
6. **多模型协作** — Codex 设计功能 → Claude Code 挑刺审查 → Codex 评估修改。至少保持两个 session：一个审核 role 一个执行 role，上下文占用低于 30%。当 AI 开始"打补丁式"修 bug，立刻让另一个模型审视架构
7. **Prompt 要精确** — 结构：背景（当前状态）+ 目标（技术语言描述）+ 约束（不能动什么、兼容什么）+ 验收标准。贴代码（接口定义、表结构）比自然语言准确。丢官方文档让 Codex 先理解再开发
8. **用官方模型** — 中转站有模型偷换、限流、上下文截断、响应延迟等问题
9. **架构由你，实现交给 AI** — 人负责目录结构、模块边界、数据流向、接口设计；AI 负责在定好的框架内填充实现。AI 容易过度封装（如把两个业务共同点封装成调度器），需要人把控

### Java 工程化协作要点（苏三视角）

来自 [[摘要-codex-从原理到-java落地]] 的实践建议：将任务描述组织为**目标、约束、输出位置和验证标准**，并明确构建或目标测试命令；复杂重构先只做分析和方案确认，再分解为小任务实施。多文件改动、重构、测试骨架和常规排错适合作为 Agent 执行任务；架构取舍、核心业务规则、安全敏感代码仍由人决策并终审。作者建议以自动检查、交叉 AI 审查和人工审查构成三层质量门禁。

### 额度重置作为营销机制（2026-09）
来自 [[摘要-codex重置的真正原因]]。统计显示 2026 年 4—8 月 Codex 共有 36 次公开额度重置，仅 14 次（38.9%）与故障或体验问题有关，另外 22 次（61.1%）属于庆祝、产品节点与临时重置；变化从 7 月起明显——6 月 5 次重置全是故障补偿，7 月故障类降到 3 次但总数升到 12 次，8 月 10 次中仅 2 次与故障有关。产品逐渐稳定，重置却越来越频繁。

重置被拆解为四种营销角色：**故障时的补偿**（用户讨论方向从"Codex 又坏了"变成"他又重置了"）、**新功能上线的体验券**（替新功能购买一轮真实体验）、**竞品危机时接人的网**（不公开踩对手，只在迁移窗口降低体验门槛）、**[[个人IP]]**（负责人 [[Tibo]] 手里真有一颗实体按钮，亲自宣布使一次后台操作有了人物和剧情）。

同期恰好是 [[Anthropic]] 指控与阿里有关的操作者用约 2.5 万个欺诈账户与 [[Claude]] 进行 2880 万次交互蒸馏模型、且 Claude Code 被发现加入未充分披露的地区识别代码后回滚的窗口期，构成[[竞品迁移窗口]]。Codex 公开用户从 5 月底 500 万增至 7 月 22 日 1000 万、8 月底 2500 万（各阶段口径不完全一致，作者明确声明不能直接等同于增长因果）。

免费额度相比现金红包的优势是天然只能在 Codex 内消耗：要消耗额度就必须打开产品、接入项目、提交任务。因此每次重置同时完成召回老用户、推广新功能、让新用户多试几次三件事；花出去的是算力成本，换回来的是真实使用。对比 [[腾讯]] 元宝 10 亿红包与阿里千问 30 亿奶茶，Codex 的做法更轻——不需要设计活动、采购权益、购买曝光，用户会自发传播"又重置了"。

### 额度消耗快不等于模型变贵（2026-09）
来自 [[摘要-codex-gpt6-astra额度优化]]。[[GPT-6]] Astra 上线后额度下降极快（原来三天用完变大半天花完），退回 GPT-5.6 Sol 后消耗依然快。排查结论：**额度不是突然消失，而是被上下文一点点吃掉**。

**实测数据**：两条 GPT-5.6 Sol 中等推理的长任务累计输入 token 分别接近 1599 万和 1582 万，任务后期单次调用输入已达 22.8 万–25.4 万 token；7 天 299 轮产品活动中，984 次插件调用主要集中在 Computer Use 和 Unified Computer Use。本机有 **274 份 Skill 定义**、全局 `AGENTS.md` **5284 字节**。界面里只发一句短话，模型实际收到的却是聊天记录 + 工具返回 + 项目规则 + Skills 描述 + 插件说明。

这与 OpenAI 官方文章《Rethinking skills and prompts for GPT-6 Astra》结论一致：**Skill 描述太多太长会持续占用上下文，`AGENTS.md` 也不应该要求模型在每个小任务开始前都读取一整套文档，更合适的方式是只在当前任务确实需要时再加载对应规则和资料。**

**三类调整**：
1. `AGENTS.md` 从 5284 字节压缩到 **1705 字节**——保留品牌名、公众号发布规则、飞书操作方式等关键约束，只删重复解释和不需要每轮都出现的内容
2. `config.toml` 加自动压缩与工具输出限制（这些数字不是所有电脑都必须照抄的标准答案，解决的是同一个问题：**不要让单个任务和工具输出无限膨胀**）：
   ```toml
   model_auto_compact_token_limit = 160000
   model_auto_compact_token_limit_scope = "total"
   tool_output_token_limit = 8000
   [skills]
   max_context_tokens = 4000
   ```
3. **不粗暴卸载插件/MCP/Skills**——它们可能承载真实工作流，粗暴关闭很容易把原本能用的能力弄坏；更稳妥的方式是先判断它们是否真的在每轮注入上下文

**两个防坑点**：
- **不要让 Codex 为了「省额度」擅自换模型**——模型是否出现在选择器里受账号、客户端和灰度发布影响，不同套餐和发布阶段看到的选项可能不同
- **不要擅自停第三方代理**——实践中遇到 OpenCodex 代理修改了模型目录，原来选过的 GPT-5.6 Sol 在列表里消失、界面只显示「自定义」。这与额度优化不是一回事，如果提示词看到自定义模型就直接删配置、停服务，可能把同事正在使用的代理环境一起破坏。正确做法是先诊断，涉及停止第三方代理或更换模型时必须单独确认

**使用方式也要跟着变**：一个任务不要无限续下去——同一篇文章、同一套代码在一个任务里连续改几十轮，看起来方便，后面的每一轮却可能越来越重。**一个阶段已经完成就新建任务，把必要文件和最终结论交给新任务**，它不需要重新背着前面所有试错记录继续工作。日常明确的小任务也没必要默认使用最高推理强度（OpenAI 官方建议：先从账号提供的默认档位开始，只有在任务确实需要更深规划和分析时再提高）。

**结论**：Codex 的消耗不只由模型名字决定，**模型、任务长度、全局规则、Skills 和工具输出，共同组成了每一轮真正送进模型的内容**。先看清 token 花在了哪里，再决定该压缩上下文、拆任务还是调整模型。

### GPT-6 Astra 时代的 Skills/AGENTS.md 瘦身（焚诀实操）
来自 [[摘要-Codex最新焚诀-GPT-6-Astra瘦身指南]]。核心结论：**模型能力变强后，Skill 要少一些，Memory 中陈旧的记忆要删掉，AGENTS.md 和 CLAUDE.md 也要精简**。两步实操提示词：

**第一步：审查**（不改文件）
> 按照这篇焚诀： https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra 审查当前项目的 AGENTS.md 和 Skills，找出**过宽的 Skill 触发、无关文档强制读取、重复检查、冲突规则，以及频繁要求确认的指令**。逐条告诉我问题和最小修改建议，先不要改文件。

**第二步：优化**
> 根据刚才的审查结果优化 AGENTS.md 和 Skills。**缩小 Skill 触发范围，删除无关文档读取，合并重复检查，解决冲突规则，并减少低风险任务中的无意义确认。保留安全边界、敏感操作确认和必要测试**。修改完成后列出具体改动。

**四个优化方向**：

1. **Skill 描述做减法**——Postgres 迁移 Skill 从"涉及数据库、查询或数据模型时使用"（太宽，写个 SQL 也触发整套迁移流程）收窄到"新增或修改迁移、审查迁移发布时使用"。同理 Claude Code 项目的 browser-act Skill 描述覆盖"fetch URL/take screenshots/fill forms and click"几乎所有浏览器操作，沾一点网页就加载整套。

2. **CLAUDE.md（对应 AGENTS.md）瘦身**——反面例子"每次编辑前，都读 architecture.md、database.md 和 deployment.md"→ 改法给每份文档加读取条件"涉及服务边界时读 architecture.md，修改表结构时读 database.md，准备部署时读 deployment.md"。

3. **放松决策边界**——老模型时代加的限制（"修改文件前必须先问我""禁止自动执行 shell 命令"）在新模型上反而让 Astra 过度谨慎。**两类区分**：安全底线保留（不要自动 push 到远程仓库、不要删生产数据、涉及密钥必须确认），日常低风险操作确认交给模型自己判断（读文件、写测试、跑格式化）。

4. **在开始之前就定义完成标准**（define completion before starting）——不是"写完代码叫完成"，也不是"多测几遍叫完成"。完成的定义应该具体到：跑哪些测试、通过什么条件、交付什么产物。测试停止条件也要写清楚"相关检查已经通过，又没有新改动和新问题，就可以交付"。

**给安全工作流显式授权**（减少不必要确认等待）：
> 本地测试使用一次性数据，没有生产环境访问权限。直接跑测试、修复失败、重跑受影响的测试，不需要每一步都等确认。

**两个自检清单**：
- **Skill 自检**：描述能否一两句话说清"做什么"和"什么时候用"？触发条件是否太宽导致不相关任务也加载？多个 Skill 描述是否重叠？详细操作步骤放在子文档里还是全塞在描述里？
- **AGENTS.md/CLAUDE.md 自检**：有没有"每次都要 XX"这样的无条件规则？这些规则各自适用于什么场景，能不能加触发条件或移到具体 Skill 里？有没有安全工作流可以显式授权？规则里引用的文档和实际代码还对得上吗？

**渐进式改进建议**：先挑一条有明确依据的建议改掉，然后用一个熟悉的日常任务跑一遍，观察模型行为有没有变化，确认没问题了再改下一条。

### MCP 额度优化工作流（邪修方法）

**核心优势**：GPT-6 Pro 的 200 次/周独立额度不消耗 Codex 额度，周额度消耗从 10% 降至 4%。

**工作流**：

2. 数据驱动的分析规划（40 分钟深度推理）
3. 点击"添加到 Codex"转移对话
4. Codex GPT-6 Astra High 执行开发

### GPT-6.1 Terra 源码三招（2026-10-27）
来自 [[摘要-gpt6.1-terra-codex三招]]，沉默王二翻 Codex 模型配置清单发现的三个源码级机制：

1. **code_mode_only 纯代码执行模式**（Terra 默认开启）——把零散工具全部隐藏，只暴露 V8 沙箱里的 `exec` 工具，文件读写/终端/MCP 挂载到沙箱全局 `tools` 对象；`tool_search` 用 BM25 实时检索工具签名 + `Promise.allSettled` 并发执行多个互不依赖操作，替代"一次调用一个工具"的 JSON 往返模式（详见 [[code_mode_only]]）。Terra 执行任务比 Sol/Astra 快 3 倍以上
2. **编号寻址跨窗口接力**——Astra/Sol/Luna 的 `context_window` 在 Codex 源码里锁死 27.2 万 Token，Terra 放开到 50 万并开启 `supports_image_detail_original`（高清原图不裁剪）；剩余空间 <6144 Token 时不做摘要压缩，改走 `notes` → `new_context` → `history` 无损接力（详见 [[跨窗口接力]]）
3. **隐藏 ultra 推理档 + 自动任务委派**——公开 API 只有 none~max 五档，Codex 内部给 Astra/Sol/Terra 加隐藏第六档 `ultra`：主模型推理强度映射 `xhigh`，调 `spawn_agent` 派生并行 Sub-agent，`fork_turns` 控制上下文继承（小函数传 `none` 零负担、复杂改造传 `all` 完整继承）；云端 `memory_consolidation`（会话记忆整理）默认模型从 `gpt-6.1-sol` 换成 `gpt-6.1-terra`（详见 [[思考强度]]、[[子Agent编排]]）
