## 核心摘要

苏三从 Java 开发实践角度将 [[Codex]] 描述为“规划—修改文件—执行验证—依据结果迭代”的工程 Agent，而不只是代码补全工具。文章建议把它优先用于多文件联动、遗留代码重构、常规 Bug 排查、单元测试骨架与有明确规则的技术栈迁移；架构选型、复杂核心业务和安全敏感代码则必须由人负责决策与终审。

在 Spring Boot 项目中，作者建议通过明确目标、技术栈/包路径约束、输出位置和验证标准来描述任务，并在需求中指定编译或目标测试。复杂改动先以只分析、不改文件的方式确认方案，再分解为小任务实施；生成结果仍应经过自动检查、交叉 AI 审查和人工业务审查。

文章把团队落地归纳为试点、推广、持续优化三阶段，并提出“提交者对 AI 生成代码负责”、禁止将敏感数据输入公共服务、关键交易/权限/加密代码必须人工审查等边界。文中涉及的模型代际、具体基准、效率比例、资源规格及成本数据均为作者叙述，应在实际决策前通过官方资料或本地评估复核。
