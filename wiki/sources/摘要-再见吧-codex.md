## 核心摘要
文章提出了一套高效的 Codex 使用工作流方法论，核心观点是"别把 Codex 当许愿池"——不能直接丢需求等结果，而要像带实习生一样引导它。作者总结了 7 步工作流（阅读理解→写计划→确认范围→小步实现→验证→总结→新会话），并深入讨论了 AGENTS.md 写法、Plan 模式、Bug 修复方法、"收工了"总结清单、以及 Skills/MCP 的最佳切入时机。

## 关键方法论

### 7 步工作流
1. **阅读理解**：先让 Codex 阅读项目结构、架构、启动/测试/部署方式
2. **写计划**：复杂任务先让 Codex 输出实现计划
3. **确认范围**：确认要改哪些文件、影响范围
4. **小步实现**：只改当前步骤需要的文件，不顺手改无关代码
5. **验证**：执行测试，认真看 diff，不只是 happy path
6. **总结**：让 Codex 总结改了什么文件、为什么改、验证了什么、还有什么需要人工确认
7. **新会话**：把总结带入新对话，避免旧假设污染

### AGENTS.md 最佳实践
只放三类内容：
- **项目硬约定**：不能动哪些目录、接口必须保留什么字段、日志必须保留敏感手段
- **工作习惯**：修改前先读相关文件、只做当前最小的改动、完成后自证验证
- **踩坑记录**：哪些地方容易出问题、已知坑点

### Plan 模式
复杂任务先让 Codex 输出：需要理解什么、影响哪些模块、分 3-7 步实现、每一步怎么验证、哪里容易出错。确认后再执行。

### Bug 修复原则
提供日志和复现步骤，让 Codex 定位。不预先给猜测（如"我觉得是异步问题"），避免带偏方向。如果一顿操作没解决，开新会话重来。

### "收工了"总结
每次结束回答 5 个问题：改了哪些文件？每个文件为什么改？改完后做了什么验证？哪些验证没覆盖？哪些地方需要人工确认？结论写入 AGENTS.md。
