## 核心摘要
文章面向经常用 [[TRAE]]、[[ClaudeCode]] 做设计与编程协作的开发者，分享"从 0 到 1 写好一个 Skill"的完整经验：不推荐完全手搓（耗时且门槛高），而是在 AI Coding 产品中给出完整的撰写指令让 AI 快速产出初版，把精力留给后续的检验与调优。

一份好的 Skill 撰写指令至少包含 5 点：**AI 身份**（站在设计专家/产品专家视角）、**Skill 用途**（调用方式、功能、用途）、**Skill 内容**（产出物的内容层级、引用内容）、**交付要求**（输出格式、注释样式）、**禁用事项或规则**（不要擅自添加功能或内容）。文中以"把 Figma 业务组件库做成 Skill"为例给出完整指令模板，并建议追加"如果有不明确的内容，你还可以再问我"来诱导 AI 反问边界问题。初版生成后可用其他 AI 工具（如豆包、Gemini）做交叉校验，找出语法错误与逻辑漏洞；但**后期质量检验和人工调优目前仍无法被 AI 完全替代，必须由人类亲自把控**。

人工调优分三个维度。**一、明确使用场景和触发条件**：Skill 用途描述必须回答"什么情况下 AI 应该自动使用这个 Skill"，并给出正误对照——❌"实现 Figma 设计稿转代码的技能" vs ✅"当用户需要将 Figma 设计稿进行高质量前端代码转换时触发"，以避免该触发不触发、不该触发乱触发。**二、了解 Skill 的结构和原理**：Skill 不是单个 markdown 文件而是完整文件夹，至少含 4 部分——SKILL.md 核心定义（Skill 系统的"CPU"，负责意图识别与指令分发，Markdown 本质是对信息进行约束）、References 参考规范（AI 的"错题本"，持续沉淀易错点）、Assets 物料资源（按需调用的固定知识）、Scripts 自动化脚本（承接确定性高的重复性任务）；References 与 Assets 共享同一核心逻辑——[[渐进式披露]]，不要把所有内容堆在一个文件里。**三、合理拆解任务和进行约束**：三个技巧——写法清晰（用 1、2、3 序号建立先后执行顺序：寻找参考→进行决策→输出内容）、有效描述（不要陈述显而易见的内容，多描述 AI 默认机制里没有的关键非客观规则，如"不要用 PingFang 字体""不要用红色渐变色"）、异常阻断（嵌入兜底逻辑，如"如果用户的需求在现有组件库中无法找到对应模式，必须停止生成并向用户提问，绝对禁止自行硬编码"）。

## 关键信息
- **核心结论**：Skill 搭建从来不是"一锤子买卖"，也不是单纯靠 AI 生成就能完成。AI 快速完成初版、节省前期时间，但核心的**场景定义、任务拆解、结构搭建、易错点沉淀必须由人工把控**
- **Markdown 的定位**：不是编程语言，其本质是"对信息进行约束"，把零散自然语言转化为机器能精准理解的结构化内容——散文改写成机器较好理解的议论文
- **易错点沉淀是长期复利**：很多 Claude Code 官方优质 Skills 都是从几行文字经过日积月累叠加易错点迭代完善的
- **跨工具校验**：把 Skill 包里的 markdown 内容发给另外几个 AI 工具做初步检验，是低成本查漏补缺的有效手段
- **示例**：Figma 组件库 Skill 要求"组件嵌套合理，颜色、文字、阴影等样式全部绑定样式变量"，且"每条规则清晰、可执行、可被 AI 直接理解并落地到设计稿"
