## 核心摘要

小哈学Java《如何做到无感刷新 Token？》（2026-10-28，首发掘金）从"系统页面突然闪退跳登录"的真实痛点切入，给出无感刷新 Token 的两条技术路线：**后端自动刷新**与**前端 token 续约**。

**关键内容**：
1. **痛点**：业务操作时突然闪退跳登录页，本质是 token 过期导致身份失效（系统用 Redis 存用户 ID 和 token 信息）
2. **方案一：后端自动刷新**（纯后端，单 token）——后端校验 token 时判断（过期时间 − 当前时间）是否小于约定值，若快过期则基于 token 内信息重新签发新 token 放到请求头返回；前端拦截请求头，发现新 token 与本地不一致就替换本地存储。附 JJWT 0.9.1 + Hutool 生成/解析 token 完整代码（HS256、getTokenExpirationDate 取过期时间）
3. **方案二：前端 token 续约**（前端主导，双 Token AT/RT）——前后端约定续约接口；前端发现 AT 快过期时向后端发送 token，后端延长过期时间。**AT/RT 区别**：AT 每个请求都携带、暴露机会多，故 TTL 短以**减少劫持风险**；RT 只暴露在 auth 服务中用来刷新 AT，TTL 长以**增加便利性**——"这是标准的安全处理，无需探讨合理性，好比 https 之于 http"
4. **边界场景（表单页长时间无请求）**：用户长时间填表不发请求，后端感知不到 token 过期，提交时 401。纯后端方案：前端保存表单到本地存储→跳登录→登录成功后返回原页回显；前端方案：监听 RT 过期时间、接近过期时主动/定期刷新 RT，或做类似草稿箱的表单保存

**定位**：与胖虎《一个 Token 就够了》的"为什么"视角互补，本篇更偏"怎么做"（后端代码实现 + 前端续约流程 + 边界兜底），两篇共同构成 [[摘要-jwt-双token续签设计]] 的姊妹篇。
