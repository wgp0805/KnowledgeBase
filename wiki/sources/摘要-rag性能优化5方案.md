## 核心摘要

苏三指出 **RAG 系统的核心壁垒不在于用了多昂贵的大模型，而在于对数据管道（Data Pipeline）的处理和检索的优化**。大模型本质上只是一个做阅读理解的机器，前面检索系统喂给它的参考资料若全是垃圾，它再聪明也答不对。照猫画虎搭的 RAG 跑测试数据还凑合，一接入生产环境让真实业务人员用，准确率就惨不忍睹，模型开始一本正经地瞎编乱造。

五个方案：

1. **别暴力切分，做好语义分块与元数据注入**——固定 500 token 一刀切用在生产环境是灾难：财务报表的表格正好被切两半，表头在上一块、数据在下一块，单独检索出的下半块毫无意义。生产做法是**结构化感知分块**：先用专门解析工具把文档还原为带结构化标记的 Markdown，按段落、标题层级、完整表格边界切分；再为每个文本块注入上下文元数据，如 `{"文件":"2023维修手册","章节":"发动机保养","内容":"该设备的维护周期为六个月"}`，否则检索出来也不知道说的是哪个设备。
2. **混合检索（双路召回）**——纯稠密向量检索不擅长业务专有名词。售后搜「设备报错 Error-0x9F4A 是什么原因」，`Error-0x9F4A` 这种无语义的纯字符编号做 Embedding 后特征被严重稀释，根本检索不到含该报错码的文档。解法是向量库做语义泛化召回 + ElasticSearch 等全文引擎做精确匹配召回，再用 RRF 交叉打分合并，彻底兜底「同义词找不到」与「专业词汇匹配不上」两个极端。
3. **引入重排（Rerank）**——很多团队为提高命中率把检索前 20 篇全塞进 Prompt，直接触发大模型著名的 "Lost in the Middle"：上下文过长且噪音多时模型会遗忘关键信息甚至被错误信息带偏产生幻觉，超长输入还大量消耗 Token、拉高延迟。标准解法是两阶段检索：粗排用便宜快速的向量检索 + BM25 召回 50 篇；精排用 Cross-Encoder 重排模型（如 BGE-Reranker）把「用户提问 + 候选文档」拼在一起同时输入神经网络打分，最后只挑得分最高的 3~5 篇喂给模型。
4. **提问预处理：Query 重写与扩展**——业务里用户提问往往极度口语化且缺上下文。多轮对话里先问「OA 系统怎么登录？」再问「密码忘了怎么办？」，直接拿后半句检索会召回一堆毫不相关的密码找回规则。解法是在检索前加一层提问预处理层，用轻量级、响应极快的小模型把历史聊天记录与当前提问结合，重写成标准检索词（如「OA 系统密码忘了怎么找回」）；还可顺手做 Query 扩展，让模型变异出三四个近义问题并发多路检索。
5. **动态评估**——传统 RAG 是单向流水线「提问→检索→生成」，检索一错生成必然是废话。更先进的架构让大模型兼任业务流的「裁判员」：检索结果回来后先跑一次轻量打分，判断这几篇文档里到底包不包含能回答问题的线索；包含则进入生成，不包含则主动放弃基于知识库生成——要么如实告知「知识库暂无记录」，要么触发外接搜索引擎去公网找答案，**决不允许强行拿着无关文档编故事**。
