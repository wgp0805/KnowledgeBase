## 核心摘要

本文是博客园 leikooo 翻译/转载的 Kyle Kukshtel（独立策略战棋游戏《Cantata》制作人、游戏数据编辑器 Depot 作者、15 年资深游戏工程师）在开发者大会演讲基础上的长文《Your Game Is A Harness》。核心论点：**LLM 在 Web 开发上近乎无所不能，却在游戏开发上几乎必然翻车，但这不是模型或游戏的先天缺陷，而是一个纯粹的上下文工程问题。**

原因链条：Web 栈有海量高质量开源项目供训练，且"一切皆代码"，文本即全部上下文；游戏的公开高质量源码少好几个数量级，且代码只是冰山一角——还有海量**非代码资产**（网格、材质、动画、关卡）对 LLM 完全不透明，任何依赖操纵这些黑盒资产的核心逻辑，都会让模型当场崩溃。社区由此得出"LLM 在游戏开发中没用"的结论。

破解思路：**把你的游戏本身做成 Harness**——把游戏里所有"暗物质"（状态、资源、物理、表现）转化为 LLM 能理解与操纵的具象载体，让游戏内部对模型处处透明、处处可寻址。通用 Harness（Claude Code、Cursor）的致命短板正在于此：它们无法与你的游戏内核对话，游戏对它们是一个焊死的黑盒。

作者给出八条可立即落地的工程架构原则：

1. **固定随机性**——启动时建立全局唯一随机种子源，所有随机调用走统一种子发生器，任何局面都能分毫不差地重现。
2. **视觉截图能力与图像差分**——先给引擎加 UI 层/玩法层渲染开关（验证 UI 时关掉动态 3D 背景）。但直接把修改前后两张大图丢给多模态模型**效果极差**：大图里的一切无关像素都是"上下文噪点"。正确做法是用图像差分（推荐开源命令行工具 **odiff**）只呈现真正变化的局部，并让工具把量化相似度（如 `85% similar`）打印到标准输出——LLM 对纯文本数值极敏感，可把它当作基准评估函数自主收敛。
3. **确定性状态与单一 Fat Struct 架构**——试金石是"完整保存并精确加载一个特定状态有多容易"。作者主张**Thing 驱动开发**：游戏里一切都是同一个结构体（基础数值 + `isAlive` + `Type` 枚举分支）。这带来唯一真理源，AI 每次都清楚该去哪里下刀，而 100 个继承类会瞬间塞爆上下文并让 AI 陷入"该继承哪个基类"的决策焦虑；同时序列化/反序列化变成单向直通管道，整场游戏无非一个 `List<Thing>`。
4. **可寻址状态与命令模式**——不再散落调用修改字段的裸函数，而是把每次变更封装为（理想情况下可序列化的）命令对象，排队交给统一处理器。收益：拿到初始快照 + 回放命令流即可 100% 复现 Bug（人和 AI 都能回放校验）；甚至可以在文本编辑器里手写 JSON 命令注入运行中的游戏实例，**全程无需编译**。
5. **外部化数据管理**——静态配置数据（`Type`/`attackDamage`/`walkSpeed`…）全部外部化为 JSON/配置表，与逻辑代码解耦，运行中秒级热重载。这是《Cantata》的标准管线：7 位非程序员成员用日常构建版 + 定制数据编辑器 Depot 做内容迭代。
6. **独立无头模拟黑盒**——把模拟逻辑完全剥离图形引擎，做成独立的无头纯代码动态链接库，引擎只是消费结果的哑客户端，两者通过 Command 通讯（与现代 Web 的客户端/服务端架构同构）。红利：网络模块、单元测试、**LLM/Agent 都能直接向纯逻辑内核注入指令**；可抛弃引擎、用最纯的命令行工具链在纯内存里秒级跑数千轮自动化测试。
7. **影响评估与纯文本性能分析**——Unity Profiler / Unreal Insights / dotMemory 这类图形工具是专为人类肉眼设计的，**AI 极其讨厌不可交互的图形界面**；推荐命令行性能分析利器 **samply**，把采样结果 Dump 到终端，Agent 就能自主采样→解析热点行号→改代码→重新采样验证，形成完全自治的性能调优内循环。
8. **闭环拼图：Agent 高速自主迭代飞轮**——上述工具与架构串联后，一个原本需要数分钟到数十分钟的 Agent 迭代轮次被压缩到**数秒之内**，因此可以覆盖到每一次微小改动，而不必等到积重难返才做一次昂贵的集成测试。

作者的原话收尾：**这并不是什么外部神秘工具，它就是你的游戏本身。** 这些原则即便完全抛开 AI，也是极佳的游戏工程实践。
