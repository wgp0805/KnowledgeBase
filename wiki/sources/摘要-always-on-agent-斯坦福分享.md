## 核心摘要

Lee Robinson 在斯坦福 CS146S 讲 Grok Bot 这类 always-on agent 的工程实现：从「模型 + 工具 + 循环」的最小 harness 出发，扩展成跑在云端服务器、可重启可恢复、有自己一台云端 Linux 电脑的常驻 agent，让干活时间从几小时几天拉长到几周甚至几个月。

人机关系的关键变化是**人在循环里的位置变了**：以前是你提示一次等一次、逐条批准命令；现在可以直接「引导」它（「去看看这个帖子」「对了，这事周四再做」），模型能像朋友听絮叨一样理解两句话相关。不可撤销的动作（发邮件、发消息）前有一层 auto review——本质是另一个 AI 模型在检查每条命令，Lee 认为这比人更安全，因为人要面对几百条 shell 命令会疲劳。

架构上是 **thin client / thick server**：客户端与服务器之间只有一个工具 `send to user`，跑 shell、读文件、调云端 agent、录屏、做演示全放服务端，客户端只负责决定怎么展示得更丰富。底层是一台 **Firecracker** 虚拟机（可快照、可重建、带 Chrome 与虚拟桌面），状态存数据库。

可靠性底座是 **job queue vs durable workflow** 的区别：普通队列崩溃后要重放一、二、三步会出很多问题，durable workflow 可以安全重试、失败后直接从第三步接着做，他们用的是开源工具 [[Temporal]]。消息优先级也有讲究——用户直接消息要能立刻打断当前 agent 循环，群聊/Slack 线程/后台例行任务排到队尾，短时间进来三四条可合并成一轮处理。

上下文工程上有三个关键设计：**动态工具发现**（每条消息只放工具名字，模型决定要用哪个再去文件读详细信息，省上下文也省成本）、**能力阶梯**（先试最便宜最可靠的办法：对话历史 → 插件/MCP/API → 网上搜 → 开浏览器搜 → 最后才动用整台桌面写脚本造东西，全失败才去打扰用户）、**prompt caching**（工具定义与系统提示保持不变以命中缓存，"缓存没命中其实就是系统里的一个 bug"）。

记忆分四层：每次必须带上的核心事实、按日期记录的过往对话日志、只活半小时的草稿式笔记、其余放文件里按需查。作者引用 Lee 的原则 "delete the product"——认定今天的模型是它们这辈子最差的时候，六个月后可能要把界面整个重做。

## 关键信息

- **开发者与 AI 关系四阶段**：复制粘贴 → 模型能改文件跑命令 → 编程 Agent 有专门应用但人仍是瓶颈（每条命令都要审）→ Agent 有自己的电脑、记忆，能在工作中学新技能
- **模型侧的六个前提**：长时遵循指令不糊涂（配合 compaction）、sub-agent 交接（近似无限上下文）、工具调用基本不再产生幻觉、computer use（无 API/MCP 的网站也能无头使用）、信息全存文件里（模型擅长用 Linux 命令搜文件）、演示一遍即可变成可复用 skill / 记忆 / routine（routine 类似 cron job）
- **一切皆电脑**：不为每个能力发明新机制，把一切都落到文件、命令和一台真正的电脑上
- **睡眠与唤醒**：服务器与那台电脑平时都睡着，消息或触发器才唤醒；需要浏览器时才启动虚拟机，用完再睡回去——因为让每个人的电脑一直开着既贵也没有那么多计算机
- **唤醒来源**：用户消息、Slack 消息、电话/会议、跑了几小时的后台任务要总结；SpaceX 常见情形是员工让 bot 去开会做记录再汇报
- **打扰启发式**：所有事件先进 router 去重再放进对话，配启发式规则判断要不要打扰用户——"同事每有一点进展就来找你说'快看我有进展了'你肯定烦，大多数任务一天一次状态更新就够了"
- **训练与产品的飞轮**：预训练 → 监督微调（让模型见过 harness 样子、知道自己有哪些工具）→ 强化学习（训练它在几百个技能里选对、点对位置）；内循环把 agent 出错变成 eval 修好再发布，外循环每几个月训新模型
- **未来 6-12 个月的四个难题**：跑一个月的 agent 怎么随模型月度发版评测、记忆算法、安全（收件箱邮件可能是钓鱼邮件、webhook 来路不明，防提示注入只是其中之一）、agent 何时该沉默何时该打扰
