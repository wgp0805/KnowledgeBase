# 摘要：10亿数据快速插入MySQL方案

## 核心摘要
本文以阿里终面题"10亿数据如何快速插入MySQL"为线索，系统拆解了从分库分表设计、存储引擎选择、批量写入策略、文件读取方式到分布式任务协调的完整方案。核心约束为10亿条每条1K的数据存放在HDFS/S3的100个文件中，要求有序导入MySQL。

## 关键要点
- MySQL单表推荐2000W以下：B+树3层索引约存2000W，4层性能下降，10亿数据需分100个表
- 批量写入优于单条写入，默认100条批量，InnoDB保证批量写入事务同时成功或失败
- 按主键id顺序写入最快，最好不创建非主键索引或表创建后再建索引
- 不能并发写同一个表：无法保证有序且批量阈值已增加并发度
- InnoDB关闭即时刷新磁盘策略（innodb_flush_log_at_trx_commit=0或2）后批量性能接近MyISAM
- MySQL单库并发写入瓶颈约5K TPS，需分库；HDD不支持并发写多表，SSD需动态配置
- 文件读取用BufferedReader逐行读取：Java NIO FileChannel虽快但不支持按行截断
- 放弃Kafka分离读写任务方案，最终合并读取和写入任务
- Redis记录任务进度保证断点续传和幂等，主节点轮询+分布式锁协调任务

## 详细内容

### 约束条件
- 10亿条数据，每条1Kb
- 非结构化用户访问日志，需解析后写入数据库
- 数据存放在HDFS或S3，被切分为100个文件
- 要求有序导入，尽量不重复
- 数据库是MySQL

### 单表容量分析
MySQL B+树索引叶子节点每页16K，每条1K则每叶子节点存16条。非叶子节点存主键（BigInt 8字节）+指针（6字节）=14字节，可存1170个指针。

| 层数 | 最大数据量 |
|------|-----------|
| 2 | 1170×16 = 18720 |
| 3 | 1170×1170×16 ≈ 2000W |
| 4 | 1170³×16 ≈ 256亿 |

2000W以下3层索引性能好，2000W以上4层性能差。设计单表容量1KW，10亿数据共100个表。

### 高效写入策略
- 批量写入：默认100条批量，动态可调
- 事务保证：InnoDB保证批量写入同时成功或失败
- 重试机制：写库失败重试N次，仍失败则单条写入，失败数据打印记录丢弃
- 顺序写入：按主键id顺序写入最快，非主键索引插入不顺序会导致性能下降
- 不建非主键索引：或表创建完成后再建索引

### 存储引擎选择
MyISAM比InnoDB插入性能好但无事务支持，重试会导致重复数据。InnoDB关闭即时刷新磁盘策略后批量性能也不错。

innodb_flush_log_at_trx_commit：
- =1（默认）：每次事务提交刷新磁盘，安全性最高
- =0或2：每隔1s刷新磁盘，crash可能丢1s数据

暂定InnoDB，线上对比两者插入性能。

### 分库设计
MySQL单库并发写入瓶颈约5K TPS。HDD不支持并发写多表（只有1个磁头需重新寻道），SSD不同厂商并发能力不同。

设计需支持：配置数据库数量、配置并发写表数量（HDD只让1张表顺序写）。不固定阈值，动态可调整。

文件读取并发度等于分表数量（100），读比写快，读并发无需超过100。

### 写入有序性
文件后缀+文件行号作为记录唯一键，同一文件内容写入同一个表。如index_90.txt写入database_9.table_0，index_67.txt写入database_6.table_7。每个表有序，整体有序通过库后缀+表名后缀实现。

### 文件读取方式对比
| 读取方式 | 3.4G文件耗时 |
|---------|-------------|
| Files.readAllBytes | OOM |
| FileReader+BufferedReader逐行 | 11秒 |
| File+BufferedReader | 10秒 |
| Scanner | 57秒 |
| Java NIO FileChannel缓冲区 | 3秒 |

FileChannel最快但不支持按行截断，缓冲区最后字节可能卡在一行中间。BufferedReader天然支持按行截断且性能不错（10G约30s），整体瓶颈在写入所以用BufferedReader。

### 任务协调
放弃Kafka分离读写任务方案（顺序被打乱、partition路由复杂）。最终合并：读取任务读一批数据写入一批。

任务表存储模型：bizId、databaseIndex、tableIndex、parentTaskId、offset、status。

并发控制：Redisson信号量限制并发度，但信号量无法解决超时续约问题。改用主节点轮询任务表：
- 情况1：执行中数量<并发度，选id最小待执行任务，Kafka发布消息，消费进程申请分布式锁处理
- 情况2：执行中数量=并发度，检查进行中任务是否有锁，无锁则重新发布
- 情况3：执行中数量>并发度，报警人工介入

主节点选取：Zookeeper+Curator。

### 任务可靠性
Redis记录任务进度，批量写入成功后INCRBY更新进度。任务中断后查询offset从断点继续。也可消费binlog每条新增则Redis+1。

### 总结要点
- 先确认约束条件再设计方案
- 从数据规模看需分库分表
- 从单库写入瓶颈看需分库
- 磁盘对并发写支持不同，并发需限制且动态可调
- InnoDB/MyISAM写入性能需线上对比
- 批量插入最佳阈值需反复测试（100/1000/10000）
- 合并读写任务，用Redis记录进度
- 主节点分配任务+分布式锁保证排他写入，Zookeeper+Curator选主
