## 核心摘要

小哈学Java 以滴滴二面题为切入点，系统讲解 ElasticSearch 和 MySQL 数据一致性的解决方案演进。核心观点：**ES 和数据库追求最终一致性，而非强一致性**（ES 是近实时引擎，写入后默认 1 秒才可见）。文章介绍 4 种方案的演进：同步双写（不推荐）→ MQ 异步 → Canal 监听 binlog（生产主流）→ 定时对账（兜底），并重点讲解版本号防乱序的实现技巧（ES 外部版本控制，类似 CAS/乐观锁）。生产最佳实践：binlog 订阅做主链路 + 版本号防乱序 + 定时对账做兜底。

## 关键信息

### 方案演进对比

| 方案 | 一致性 | 性能 | 业务侵入 | 复杂度 | 评价 |
|------|--------|------|----------|--------|------|
| 同步双写 | 差，容易不一致 | 差 | 高 | 低 | ❌ 基本不用 |
| MQ 异步同步 | 最终一致 | 好 | 中 | 中 | ✅ 常用 |
| 监听 binlog（Canal/Debezium） | 最终一致 | 好 | 无 | 高 | ✅ 生产主流 |
| 定时对账补偿 | 兜底 | - | 低 | 低 | ✅ 必备兜底 |

### 问题本质：分布式双写困境
- MySQL 和 ES 两个存储系统无法用本地事务覆盖
- 先写 MySQL 再写 ES：ES 写失败导致搜索数据陈旧
- 先写 ES 再写 MySQL：MySQL 回滚导致搜索到不存在的数据
- 强一致分布式事务（如 Seata XA）代价过大，搜索场景不值得

### 同步双写的问题
- **耦合高**：业务代码混着搜索逻辑，索引结构一改所有写入处都要改
- **性能差**：接口响应被 ES 写入拖长，ES 抖动影响业务
- **依然不一致**：第二步失败无法自动补救

### MQ 异步同步的坑
- **消息丢失**：MySQL 更新成功但未发 MQ，应用挂了导致变更丢失
  - 解法：本地消息表（事务内插记录 + 定时任务补发）或 RocketMQ 事务消息
- **消息乱序**：并发消费导致旧数据覆盖新数据
  - 解法：按业务 ID 路由的顺序消息 + 版本号控制

### Canal 监听 binlog（生产主流）
- **原理**：Canal 伪装成 MySQL 从库，接收 binlog 增量数据
- **优势**：业务零侵入，binlog 天然保序，断点续传
- **架构**：MySQL → Canal → MQ（削峰） → 消费写入 ES
- **国外方案**：Debezium + Kafka，思路相同

### 版本号防乱序（核心技巧）
- 每条数据带单调递增版本号（可用 MySQL 更新时间戳或 version 字段）
- 写入 ES 时使用外部版本控制（`VersionType.EXTERNAL_GTE`）
- 旧版本消息到达时 ES 自动拒绝，实现"免疫"而非"预防"

### 兜底方案
- **定时对账**：低峰期比对 MySQL 和 ES，以数据库为准修复 ES
- **全量重建**：索引结构大改或脏数据过多时，从 MySQL 全量刷新索引 + 别名切换

### 记忆口诀
> 双写不可靠，异步入 MQ；binlog 最稳，版本防乱序；对账做兜底，最终一致就好。
