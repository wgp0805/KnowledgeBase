## 核心摘要

本文讨论在 GPT-5.6、Kimi K3、Fable-5 等"强模型"原生能力已具备规划/子 Agent/Review/测试能力的时代，[[Superpowers]]（强制完整流水线）与 [[MattPocock]] 的 Matt Skills（轻量可组合工具集）两套 AI 编程工作流该如何选型。核心论点：强模型时代无脑常驻全套重流程会带来"流程税"（Token 开销、重复调度、约束推理空间），应转向"给定目标，AI 自主推理，人关键节点补强"的新范式，按任务风险分层加载 Skill。

## 关键信息

### 两套工作流核心哲学对比

| 维度 | Superpowers | Matt Skills（mattpocock-skills） |
|------|-------------|--------------------------------|
| 定位 | 完整、强制的全流程开发框架 | 轻量化、可组合的工具零件集 |
| 理念 | 把软件工程方法论封装成 Skill，强制 AI 走完整链路 | Process over Prompt，控制权留给开发者，按需启用 |
| 关键机制 | brainstorm / 强制计划 / TDD / Review / 红线阻止跳流程 | grill-me / to-spec / to-tickets / implement，可单独调用 |
| 特点 | 流程闭环、纪律强、Token 消耗大、流程重 | 轻量、模块化、人主导、不强制全套 |
| 需求分析 | 强制触发头脑风暴，必须输出完整计划（小任务易过载） | 需求模糊时手动调用 grill-with-docs，明确时直接跳过规划 |

### 强模型时代：过度详细流程反而降低效果的三个原因

1. **模型原生能力已具备规划/子 Agent/Review/测试**：早期模型弱需外部规则"按住"AI；强模型本身就会做需求分析、任务拆解、自测、评审，外层再套完整强制流程会产生**重复调度、重复规划**的冗余开销
2. **小任务场景的流程税**：简单修改、小 bug 修复强制全流程会消耗大量 Token，拉长对话链路，简单事情复杂化
3. **流程约束模型推理空间**：过于死板的步骤限制会抑制强模型自身的创造性推理，固定步骤模板反而束缚最优路径

> 注意：不是 Superpowers 本身不好，而是**不再适合作为默认常驻配置**，不能所有任务无脑全套开启。

### 场景选型建议

| 场景 | 推荐工作流 | 理由 |
|------|-----------|------|
| 全新复杂项目、高风险模块、核心业务重构（支付/权限/数据迁移） | Superpowers（按需加载，任务结束关闭） | 需要严格 TDD、完整审查、强工程纪律 |
| AI 编程新手 | Superpowers | 框架强制约束 AI，避免抢跑漏步骤 |
| 需要完整可追溯工程留痕、严格 TDD 交付 | Superpowers | 流程兜底质量 |
| 大多数日常开发（bug 修复、小功能迭代、原型验证） | Matt Skills | 轻量按需，保留人的主导权 |
| 开发者希望自掌流程控制权 | Matt Skills | 需要时才调用 grill/to-spec/to-tickets |
| 使用 GPT-5.6 / Kimi K3 / Fable-5 等强模型 | Matt Skills | 利用模型原生能力，Skills 当工具零件按需调用 |
| 快速原型验证 / 简单小修改 / 遗留老代码局部改动 | 不建议无脑全套 Superpowers | 流程税高，老项目测试不全强制 TDD 易卡住 |

### 强模型时代分层工作流参考

1. **简单小修改**：直接交给模型原生能力，不加载额外 Skill
2. **需求模糊、需要梳理规格**：启用 Matt Skills 的 `grill-with-docs` 等模块深挖需求、输出文档
3. **高风险重构 / 核心模块开发**：按需加载 Superpowers，启用 TDD、Review 完整流程

### 范式转变

- **旧范式**：给 AI 写死每一步操作，强制按固定脚本执行
- **新范式**：告诉 AI 目标，让 AI 自主推理完成；人只在关键节点介入补强

> 核心认知：工具是补充，不是必须全套常驻。理解人与 AI 协作范式的变化，比死记某一套工作流更重要。
