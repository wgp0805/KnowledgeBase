## 核心摘要

小哈学Java 用字节码分析 + 双模式基准测试验证民间传言"Java 中使用 try catch 会严重影响性能"，结论：**该说法不成立**。未发生异常时，try catch 几乎零开销；真正的性能杀手是**频繁抛出异常**。与既有 [[摘要-try-catch-异常边界]]（胖虎，异常边界与设计视角）互补，本篇是性能实测视角。

## 关键信息

### 原理：JVM 用异常表实现 catch
- 显式抛异常由 `athrow` 指令支持，运行时异常（如除零、NPE）由 JVM 自动抛出
- **catch 语句不由字节码指令实现**（上古时代的 jsr/ret 指令早已舍弃），而是通过方法体中的**异常表（Exception table）**：`from~to` 圈定 try 范围，命中 type 对应异常则跳 `target`
- 未发生异常时指令直接 goto 到 try 之后返回，**所谓损耗几乎不存在**；多出的 goto 跳转在几百行方法里占比微乎其微（传言可能源于认识停留在上古时代）

### 编译器优化背景（测试设计依据）
- 前端编译（javac）偏代码结构优化；后端编译（JIT：C1/C2、AOT：jaotc）优化执行效率
- 分层编译：解释模式（`-Xint`，编译器不介入）/ 编译模式（`-Xcomp`，热点探测阈值 Client 1500、Server 10000）/ 混合模式
- 测试思路：**一组禁用全部编译优化看原始开销，一组拉满即时编译看是否影响 JIT**

### 实测结果
- **解释模式**（`-Xint -XX:-BackgroundCompilation`）：百万次循环、每圈 try catch，影响极小；唯一可见差异是"每圈多个 try catch"时千万次计算差 5~7 毫秒——goto 指令占比过大放大了问题，真实少量使用时可忽略
- **编译模式**（`-Xcomp -XX:CompileThreshold=10 ...`）：难分胜负，波动在微秒级；亿级计算波动毫秒级，**JIT 连解释模式下 goto 过多的问题都顺带优化了 → try catch 不会影响即时编译**
- **异常本身昂贵**：百万次调用对比"正常判断取值" vs "每次都触发空指针异常被捕获"，后者明显慢——可怕的不是 try catch 而是业务不熟练

### 结论与使用建议
- 未发生异常时，给代码包上 try catch 不会造成性能影响，**平时写代码最优先考虑程序的健壮性**，不确定就放心用
- 真正要避免的是**用异常做流程控制**（每次都抛异常再捕获）
- 文中保留的未验证猜想：try catch 是否影响指令重排序（多线程下可能类似内存屏障的分割效果），作者明确标注为个人推测、本文只讨论单线程
