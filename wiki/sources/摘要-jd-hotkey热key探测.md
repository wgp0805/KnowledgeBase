## 核心摘要

苏三（2026-10-27）拆解京东开源热 key 探测框架 JD-hotkey。引子案例：秒杀商品详情页平时 QPS 几百，活动开始瞬间冲到几万，Redis 集群 CPU 打满（所有请求砸同一个秒杀商品 key）、Tomcat 线程池堵死（每个请求都在等 Redis 返回）——做了缓存也被打穿，因为**缓存解决"重复查询"，解决不了"突发流量集中打在一个 key 上"**。核心论点：热 key 是"突发"的而不是"预设"的，**热 key 的核心矛盾不是"缓存"，是"探测"**——先知道谁热了，才能决定把谁推进本地内存。架构四步：Client 查 Redis 前调 `JdHotkey.isHotKey(key)` 攒批每 500ms 上报 Worker → Worker 滑动窗口计数（如"2 秒内 20 次算热"）判定 → 长连接推送到订阅该应用的**所有** Client 放进本地 Caffeine → 业务方自己去 Redis 查一次 value 用 `smartSet` 塞进本地（框架只指路不存 value，探测与缓存解耦）。性能：约 30 万 QPS 探测，protobuf 序列化后 36 万+ 稳定 CPU 60%，压测 5 小时+ 无异常；1 台 Worker 撑 1000 台业务服务器。大促期间热 key 探测出的本地缓存占应用总访问量 50%+，减轻 Redis 层一半以上负担。优点：轻量不绑 Redis、解耦灵活、集群判定全量一致（不存在 A 机热 B 机不热）、毫秒级推送、成本低、京东 2020 年 618/双 11 验证（日探测数十亿 key，捕获大量爬虫刷子）。缺点：要部署 Etcd+Worker+Dashboard、业务代码需显式调 isHotKey、框架不保证 value 永远在本地、阈值需按业务调优。适用：秒杀/大促商品详情、爬虫刷子识别、热接口熔断、Redis 热 key 本地缓存；小流量内部系统不推荐。
