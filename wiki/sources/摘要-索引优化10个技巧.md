## 核心摘要
苏三把日常调优与面试中最常用的索引优化技巧收敛为 10 条：从"选高选择性列"到"更新统计信息"，覆盖建索引（选择性、最左前缀、覆盖索引、前缀索引）、写 SQL（避免函数与运算、OR 改 IN/UNION、深分页改写）以及运维（清理冗余索引、ANALYZE/OPTIMIZE）三个层面。文章反复强调的底层逻辑只有一条：**B+Tree 的威力来自"有序"**，任何破坏有序性（函数包裹、隐式类型转换、左模糊、跳过最左列）或让回表收益低于全表扫描（低选择性、结果集过大）的写法都会让索引失效。作者最后给的行动建议是：建索引前先 `EXPLAIN`，建完后定期清理无效索引——"索引是把双刃剑，用得好是屠龙刀，用不好就是自残剑"。

## 关键信息

### 十条技巧速查
| 技巧 | 核心要点 | 优点 | 缺点 / 注意 |
|------|----------|------|-------------|
| 高选择性列 | 唯一值占比高 | 过滤快 | 状态类字段慎用 |
| 最左前缀 | 联合索引从左连续匹配 | 命中率高 | 顺序错误即失效 |
| 覆盖索引 | 索引包含查询所需全部列 | 免回表 | 占用更多空间 |
| 避免函数 | 不对索引列做运算 | 索引可用 | 写法需调整 |
| 索引下推 ICP | 索引层先过滤 | 减少回表 | 依赖版本 |
| OR 改 IN/UNION | 避免 OR 的两侧不对等 | 可能走索引 | 看具体优化器 |
| 前缀索引 | 只索引前 N 个字符 | 节省空间 | 不能排序 / 覆盖 |
| 清理冗余索引 | 删除重复与无用索引 | 提升写入 | 需定期巡检 |
| 深分页优化 | 延迟关联 / 游标分页 | 减少扫描 | 复杂度增加 |
| 更新统计信息 | 让优化器估准 | 选对索引 | 大表避开高峰 |

### ① 高选择性列
- 选择性 = `COUNT(DISTINCT col) / COUNT(*)`，越接近 1 越好
- 低选择性（性别 ≈ 0.5）：索引树虽浅，但每个键值对应海量行，回表代价甚至超过全表扫描，优化器会**主动放弃索引**
- 业务必须过滤低选择性字段时，把它放在**联合索引末尾**做二次筛选：`INDEX(user_id, status)` 而非 `INDEX(status)`

### ② 最左前缀法则
- `INDEX(a,b,c)` 本质是按 a 排序、a 相同再按 b、b 相同再按 c 的 B+Tree
- `WHERE b=1 AND c=2` 完全用不上；`WHERE a=1 AND b>2 AND c=3` 中 c 用不上（范围截断）
- 建索引原则：**等值查询列放最左，范围查询列放最右**

### ③ 覆盖索引免回表
- InnoDB 二级索引叶子存的是**主键值**，取完整行必须再走聚簇索引 —— 这次随机 IO 叫**回表**，极其昂贵
- 索引已含查询所需全部列时无需回表，即覆盖索引；速度可提升数倍到数十倍
- 代价：索引空间变大、写维护成本上升。适合高频固定字段组合（个人信息、订单简要列表）

### ④ 避免函数与表达式
- `WHERE DATE(create_time) = '2026-01-01'` 不走索引 → 改为区间：`>= '2026-01-01 00:00:00' AND < '2026-01-02 00:00:00'`
- 隐式类型转换等同函数：`phone = 13800000000`（phone 是 VARCHAR）失效 → 加引号
- 列参与运算：`price * 0.8 > 100` 失效 → 移到右侧 `price > 100 / 0.8`
- 原理：B+Tree 按**列原始值**排序存储，任何函数运算都破坏排序规则

### ⑤ 索引下推 ICP
- MySQL 5.6 引入，默认开启（`optimizer_switch` 中 `index_condition_pushdown=on`）
- 例：`INDEX(name, age)` + `WHERE name LIKE '张%' AND age = 25`
  - 无 ICP：先按 name 找出所有主键，**全部回表**再过滤 age
  - 有 ICP：在索引层同时判断 age，只对同时满足两个条件的记录回表

### ⑥ OR 改 IN / UNION
- 低选择性列上的 `status = 1 OR status = 2` 可能直接全表扫描
- 改 `IN (1,2)` 通常能走索引；或改 `UNION`（无重复时用 `UNION ALL` 更快）
- 原理：`IN` 是被优化器特别处理的等值集合，`OR` 则拆成多个独立查询再合并，成本容易被低估

### ⑦ 前缀索引
- 长字符串列（`VARCHAR(255)`）整列建索引体积大且拖慢写入，可只索引前 N 字符：`INDEX idx_email_prefix (email(10))`
- 长度选择：对比 `COUNT(DISTINCT LEFT(email,N))/COUNT(*)`，取**接近 1 的最小 N**
- 硬限制：**不能用于 `ORDER BY` / `GROUP BY`，也无法成为覆盖索引**

### ⑧ 清理冗余与无用索引
- 冗余：`INDEX(a)` 与 `INDEX(a,b)` 并存时前者多余；`INDEX(a)` 与 `INDEX(b,a)` 对 `WHERE a=1` 都可命中，保留其一
- 查未使用：`performance_schema.table_io_waits_summary_by_index_usage` 中 `COUNT_READ` 长期为 0 的可考虑删除
- 查冗余：`sys.schema_redundant_indexes`

### ⑨ 深分页优化
- `LIMIT 100000, 10` 需扫描 100010 行再丢弃前 100000 行
- **延迟关联**：先用覆盖索引只查主键，再回表取整行
  ```sql
  SELECT * FROM orders t1
  JOIN (SELECT id FROM orders ORDER BY id LIMIT 100000, 10) t2 ON t1.id = t2.id;
  ```
- **游标分页**：适合只增不减的数据，`WHERE id > last_id ORDER BY id LIMIT 10`

### ⑩ 分析表与统计信息
- 优化器依据统计信息选索引，统计陈旧就会选错
- `ANALYZE TABLE orders;` 手动更新；`OPTIMIZE TABLE` 重建表、整理碎片（适合大批量删除后）
- MySQL 8.0 默认持久化统计信息，且表数据变化超 10% 自动更新，但**批量导入/删除后仍建议手动执行**
