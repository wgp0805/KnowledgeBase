## 核心摘要
小哈学Java 转载（原 expectfly.com）的分布式定时任务方案选型文。先把定时任务与消息中间件的边界讲清（时间驱动 vs 事件驱动、批量 vs 逐条、实时 vs 非实时、系统内部 vs 系统解耦），再分单机（Timer / ScheduledExecutorService / Spring 定时器）与分布式（Quartz / TBSchedule / elastic-job / Saturn / xxl-job）两条线盘点框架，最后重点把 elastic-job（E-Job，当当，Zookeeper 协调）与 xxl-job（X-Job，大众点评徐雪里，数据库协调）在集群部署、任务不重复、日志追溯、监控告警、弹性扩缩容、并行调度、高可用、失败处理、动态分片九个维度上逐项对照，给出选型结论。

选型结论：**X-Job 侧重业务实现简单与管理方便，学习成本低、失败与路由策略丰富，适合用户基数相对少、服务器数量在一定范围内的场景；E-Job 关注数据本身，增加弹性扩容与数据分片思路以最大化利用分布式服务器资源，学习成本相对高，适合数据量庞大、部署服务器数量较多的场景。**

## 关键信息
- **定时任务 vs 消息中间件可互换的场景**：发货成功发短信既可定时轮询也可发 MQ 消费；不可互换的四条边界——①时间驱动/事件驱动（爬外部网站价格每小时一次只能时间驱动）②批量处理/逐条处理（月度结算话费只能批量）③实时性/非实时性（VIP 升级不需实时）④系统内部/系统解耦（调度一般在系统内部，MQ 用于跨系统）
- **单机方案**：Timer（异常未检查会中止线程）、ScheduledExecutorService（无绝对日期时间）、Spring 定时框架（单机优先考虑）
- **分布式方案谱系**：Quartz（Java 事实标准，关注任务非数据，缺分布式并行调度）、TBSchedule（阿里早期，代码陈旧用 Timer 非线程池、作业类型单一、文档缺失）、elastic-job（当当，Zookeeper 协调，支持分片与云）、Saturn（唯品会，基于 elastic-job v1，可部署到 Docker）、xxl-job（2015 徐雪里，轻量、开发迅速、学习简单、易扩展）
- **E-Job vs X-Job 九维度对照**（社区/集群部署/任务不重复/日志追溯/监控告警/弹性扩缩容/并行调度/高可用/失败处理/动态分片）：X-Job 集群仅需每个节点配置一致、调度中心靠 DB 区分集群；E-Job 重写 Quartz 的 DB 分布式功能改用 Zookeeper + Curator 实现注册中心。X-Job 多节点靠 Quartz DB 功能防重复、靠 DB 锁保证一次调度只触发一次；E-Job 把任务拆 n 个任务项各服务器执行、新节点加入或下线在下次任务前触发重分片。X-Job 失败默认告警可配多邮箱；E-Job 靠事件订阅自行实现监控告警。X-Job 分片广播以执行器为维度支持动态扩容增分片；E-Job 支持多种分片策略（平均分配/哈希奇偶决定 IP 升降序/轮转）且可自定义，分片由主节点分配
- **和 Quartz 对比的痛点**：调用 API 不人性化、需持久化 QuartzJobBean 到数据表侵入性强、调度逻辑与业务耦合同一项目性能受限、关注任务非数据无定制化流程
- **附：订单超时自动确认收货的其他方案**：每天半夜筛选次 日可确认订单每 10 分钟执行一次；客户端下次上线时运算；延迟/定时消息投递（ActiveMQ broker 端定时调度、RabbitMQ 设置 x-message-ttl 超时变死信后经 DLX 重新 publish 到另一 Exchange 再消费）
