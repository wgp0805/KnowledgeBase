## 核心摘要

叶小钗用自己 20 篇管理文章做「管理数字分身」，验证 LLM Wiki 范式：不再把原始文档粗暴切块塞进向量库，而是先用 LLM 把材料「编译」成结构化、语义互联、可溯源的 Markdown 知识页，再让 Agent 按需检索。实测回答质量明显好过向量切分方案，代价是响应偏慢。

文章给出 LLM Wiki 的三层架构：**原始数据层**（Raw，只读不可变，LLM 只能读不能改，保证溯源）、**规则约束层**（Schema，即 AGENTS.md/CLAUDE.md，规定目录结构、编译流程、元数据与冲突处理）、**知识编译层**（Wiki，按摘要/实体/概念/比较/概述/综合理解组织，每页带 YAML 头与关系链接）。人机分工是：人定规则、供原始数据、做价值审核与关键裁决，LLM 负责知识编译层的维护更新。

检索侧定义了渐进式下钻流程：先搜索引与摘要定位可能有用的页面 → 不够就打开页面读全文 → 还缺就顺着页面中的关联页继续查 → 需要精确引用/代码细节时回原始文档 → 来源说法不一致时比较时间、范围与出处并说明差异。

结论明确 LLM Wiki 不是 RAG 的银弹：**LLM Wiki 是编译时产物，RAG 是运行时手段**。知识体量变大后 index.md 持续膨胀、检索与编译 Token 消耗同步上升，必须用 BM25 关键词索引 + 向量语义重排来兜底。作者同时强调人的判断权不能交出去——LLM 并不知道哪些信息重要、哪些结论值得保留，全自动编译质量必然不高，信息筛选与知识编译两个环节必须有人参与审核（Karpathy 本人也是单篇摄入、全程参与）。

## 关键信息

- **产出量化**：20 篇文章编译出 20 份知识摘要 + 13 个实体页 + 128 个概念页
- **落地载体**：腾讯开源的 [[WeKnora]]（需源码本地部署），新建知识库时选「Wiki 知识库类型」，提取粒度选标准，内置规则集对应 Schema 层
- **图谱 ≠ 知识图谱**：展示的是知识页面之间的**引用链接关系**，粒度很粗，没有层级/属于/包含等图谱语义，也不存在逻辑链
- **核心工作流**：先知识编译 → 再知识检索 → 最后知识治理
