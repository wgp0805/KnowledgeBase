## 核心摘要
苏三（公众号「苏三说技术」）用两个真实生产场景横评三款国产多模态模型：**Step 3.7 Flash、MiniMax M3、Qwen3.6-flash**。场景一为「流程图→业务逻辑还原」（Claude Code 内使用），场景二为「电子发票→结构化 JSON 提取」（业务系统 API 调用）。作者不看跑分榜，坚持"同一提示词、同一图片、同一参数，唯一变量是模型"，从**质量、速度、成本**三维度评估生产可用性。

## 关键结论
- **质量**：三款模型在两个场景下都能给出可用结果，稳定性都达标；只有 Qwen3.6-flash 在流程图任务把 10 步合并为 9 步（合并了步骤 3、4），但整体逻辑仍正确。
- **速度**：Step 3.7 Flash 在两个场景都最快（流程图 15s / 发票 5.6s）。
- **成本**：Step 3.7 Flash 综合最便宜（流程图 ¥0.0246 / 发票 ¥0.0060 一张），MiniMax M3 最贵（流程图 ¥0.0688）。
- **场景选型建议**：作者综合推荐 Step 3.7 Flash 作为 Agent 或业务 API 的首选测试对象——质量稳定、速度更快、Token 更省，最符合"生产可用"要求。

## 场景一：流程图→业务逻辑（Claude Code 里 @图片 提取）
微信小程序登录鉴权 10 步流程图，用 `@图片.png 获取图片中流程逻辑` 直接让模型看图产出方案。

| 维度 | Step 3.7 Flash | MiniMax M3 | Qwen3.6-flash |
|------|---------------|-----------|---------------|
| 步骤识别 | 10 步（完全吻合） | 10 步（完全吻合） | 9 步（合并步骤 3、4） |
| API 时间 | 15s | 20s | 19s |
| Token 消耗（in/out/cacheR/cacheW） | 728 / 1.1k / 54.4k / 0 | 27.9k / 1.2k / 228 / 0 | 251 / 1.9k / 0 / 28.6k |
| 换算价格 | ¥0.0246 | ¥0.0688 | ¥0.0483 |

## 场景二：电子发票→结构化 JSON（API 方式）
提示词要求提取 12 个字段（发票类型/号码/日期/金额/税率/税额/项目/买卖方纳税人识别号与开户行）。

| 维度 | Step 3.7 Flash | MiniMax M3 | Qwen3.6-flash |
|------|---------------|-----------|---------------|
| 结果正确性 | 完全正确 | 完全正确 | 完全正确 |
| API 时间 | 5.6s | 6.1s | 7.38s |
| Token 消耗 | 802 / 607 / 0 / 0 | 1686 / 530 / 1672 / 0 | 1165 / 843 / 0 / 0 |
| 换算价格 | ¥0.0060 | ¥0.0086 | ¥0.0075 |

作者点出：**票据结构化信息提取一张不到 1 分钱**，多模态在此场景相比传统 OCR（机械识别、误差大、需人工确认）优势明显——它不仅能识别信息，还能"思考"字段归属。

## 方法论亮点
- **横评守则**：只有模型变量，其余参数（提示词、图片、配置、工具）全部对齐；每次调用记录耗时和 Token；不看跑分榜、只看真实任务。
- **生产可用性三维评估**：质量（一次是否可用、是否要追问）→ 速度（是否适合 Agent 高频调用）→ 成本（Token 单价 + 人工重跑投入）。
- **上线前必做**：一个模型不能覆盖所有场景，最终仍要拿自己的业务样本再跑一轮。
