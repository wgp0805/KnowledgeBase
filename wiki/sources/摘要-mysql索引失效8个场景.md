## 核心摘要
[[小哈]] 整理的 MySQL 索引失效八大场景实战讲义，建立在 `student` 表演示表（联合索引 `sname,s_code,address` + 主键 + `height` 普通索引）之上，用 EXPLAIN 执行计划逐一验证。核心结论：**大部分"索引失效"其实是 MySQL 优化器认为查询范围过大、全表扫描更划算**，而不是 SQL 写法本身有问题；真正确定会失效的是违反最左匹配、对索引列使用函数/计算、左模糊 like、OR 两侧只有一侧有索引。

## 关键信息

### 八类失效场景
| 场景 | 是否必然失效 | 根因 |
|------|------|------|
| 违反最左匹配原则 | 是 | 联合索引 B+ 树按最左字段排序，缺首列则后续列全局散列 |
| `select *` | 否 | 走辅助索引后需回表取全部列，多一次 B+ 树查询；范围过大才退化为全表扫描 |
| 索引列使用函数 | 是 | 索引存的是原始值，不是函数计算后的值（MySQL 8.0 起可用函数索引规避） |
| 索引列做计算 | 是 | `b-1=6` 改变了索引值，MySQL 未实现自动改写为 `b=6-1` |
| `like '%xx'` 左模糊 | 是 | 前缀通配导致无法二分定位；右模糊 `like 'xx%'` 走 range 但级别低 |
| OR 两侧仅一侧有索引 | 是 | 优化：两侧都加索引即可走索引 |
| `in` / `not in` 取值范围过大 | 否 | in 一定走索引，但结果集超过约 30% 时优化器改全表扫描 |
| `order by` | 否 | MySQL 权衡"走索引 + 回表" vs "全表扫描 + 排序"，常选后者 |

### 最左匹配的本质
- 联合索引排序是**先按第一字段排序，第一字段相同才按第二字段排**，因此 `B=2` 这类条件无法利用索引
- MySQL 优化器会**自动调整等值条件的顺序**，`s_code=1 and sname='x'` 依然能匹配 `sname,s_code`
- 范围查询（`>`、`<`、`between`、`like`）会**终止后续字段的匹配**：`sname='x' and s_code>1 and address='上海'` 中 `address` 用不到索引
- MySQL 8.0 的**索引跳跃扫描（Index Skip Scan）**可部分打破该原则：当第一列唯一值较少时，缺失首列也可能走联合索引

### 其他要点
- 不推荐 `select *` 的真实理由：解析成本、字段变动与 resultMap 不一致、无用字段占用网络与 join buffer
- 不应建立在经常变更的字段上：索引结构要跟着改，消耗性能
- 连接查询先查驱动表、再用结果逐条查被驱动表，缓冲池越大 IO 越少
