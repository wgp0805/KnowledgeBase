## 核心摘要

沉默王二（二哥）拆解「多个 Agent 同时改一个文件」这个鹅厂面试题，结论是 **Claude Code 用空间换安全，Pi 用时间换安全**，两种做法都只管住了单个工具层面的文本写入，管不住跨进程覆盖和代码逻辑层面的语义冲突。

**Claude Code 的办法是给每个 Agent 一整个仓库。** 启动时加 `--worktree <名字>`，Claude 会在 `.claude/worktrees/` 下建独立工作目录、切一条 `worktree-<名字>` 分支；这个目录由 git worktree 出来，有自己的文件与分支，但和主仓库共享同一份提交历史。想让 Sub-agent 也享受隔离，在它的 frontmatter 里加 `isolation: worktree` 即可；若无改动，Claude Code 会自动清理该目录。

**光建目录不够——Agent 完全可以用一条绝对路径把文件写回主仓库**，所以 Claude Code 加了四道检查：①**文件编辑**——Edit、Write、NotebookEdit 三个工具，只要目标路径落在主仓库里，直接拒绝；②**命令在哪里执行**——Bash 命令如果在主仓库里执行则拒绝；③**git 重定向**——想用 `git -C`、`--git-dir` 把 git 指回主仓库则拒绝；④**命令形态**——一段命令文本如果 Claude Code 无法确认里面执行的 git 会留在 worktree 里（比如命令名是运行时算出来的）也拒绝。**明确的漏洞**（官方文档也写了）：这些检查看的是编辑的目标路径、命令在哪里执行、命令文本本身，**没有跟踪 shell 命令实际写入了哪些文件**——用 `cp` 或重定向把内容往主仓库里写，这几道检查拦不住。一句话：**Claude Code 没有解决冲突，它只是让冲突暂时不可能发生。**

**Pi 没有 worktree，它靠时间。** Pi 的多个 session 共享同一个工作目录，没做文件系统隔离，命令行参数表里也没有 worktree 相关开关。它内部有一个**文件变更队列**，实现为模块级 Map，同一文件上的写入操作串成 Promise 链，前一个做完才轮到下一个，不同文件可并行。队列的 key 会先做一次路径解析、再做一次真实路径解析，所以**两个软链接指向同一个文件也会排进同一个队列**。更关键的是 edit 工具：把「检查文件是否存在 → 读取当前内容 → 匹配 oldText → 写回结果」四步全部放在队列里完成，同一进程里十个并行 edit 也会老实排队。**但这个队列有漏洞：bash 工具没有引用它**——模型用 `sed` 改写文件、用重定向写文件、执行 prettier 格式化都不排队，甚至和同进程的 edit 也不互斥。

**两种做法各自漏掉什么**：Pi 的队列是模块级 Map，只在同一进程内共享——两个终端各开一个 pi 指向同一仓库，内存里根本看不见对方，后写的仍会直接覆盖先写的，无任何提示。而且 write 工具的实现里**连读都不读**，建好父目录就把内容写进去，无条件覆盖；edit 工具看起来安全一点（要求 oldText 能匹配上），但这是文本匹配的副产物而非版本校验——外部改动若恰好落在 oldText 覆盖的那几行，匹配失败的报错是「找不到要替换的文本」，模型只会当成自己的 oldText 写错了，意识不到文件已被其他 Agent 改过；若外部改动落在 oldText 以外，匹配照样成功，两边基于不同基线各改各的，结果静默写回，双方改动都生效。Claude Code 的 worktree 则把冲突**延迟到合并那一步**，git 该报冲突还是会报，只不过需要人来处理。

**更麻烦的是语义冲突**：Agent 张三把一个函数的返回值从字符串改成对象，Agent 李四在另一个 worktree 里没看到这个改动，照着旧的返回值类型写了一段调用代码。合并时这两处改动在**不同的文件**里，git 一个冲突都不报，可 merge 到一起运行起来就有问题。

实践建议：如果现在就在用多个 Agent 执行任务，先把任务按目录分好，别让两个 Agent 同时碰同一个文件；真要碰，就串行，一个改完另一个再上。
