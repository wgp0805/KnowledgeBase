## 核心摘要
在系统提示词或 `AGENTS.md`/`CLAUDE.md` 里放秒级时间戳会让前缀缓存（Prefix Caching）失效，首字延迟飙升、账单翻 10 倍。根因是推理引擎按 Token 序列从第 0 号开始严格前缀匹配（Radix Tree），系统提示词位于前缀树的根节点，一旦混入每秒变化的数字，根节点哈希块就会改变，排在后面的工具定义和历史对话全部失联，每一轮都要重新 Prefill。正确做法是固定内容放开头、日期降级到按天/按月、跨天或规则改动就追加到对话末尾。

## 关键信息

### 四问四答（面试题式拆解）
1. **为什么系统提示词加时间戳会让工具定义和历史对话缓存失效？**（答案 B）——Prefix Caching 按 Token 序列构建前缀树，必须从第 `0` 号 Token 开始逐块匹配；系统提示词在根节点，混入秒级时间戳后根节点哈希块改变，后面全部失联，每轮都要重做 Prefill。
2. **AGENTS.md/CLAUDE.md 怎么放进上下文？**（答案 B）——移出系统提示词，放进带 `<system-reminder>` 标签的第一条用户消息；系统提示词只放不变的全局指令，随项目和会话变化的信息统一进用户消息。
3. **跨过凌晨零点第一条消息的日期过期了，怎么在不破坏缓存前提下更新？**（答案 C）——保持第一条消息的旧日期不动，只在跨天那一轮的对话末尾追加一条新消息。
4. **中途切 Plan 模式或改 AGENTS.md，怎么保住前缀缓存？**（答案 B）——固定提示词顺序，把改动后的内容追加到对话末尾，靠 `in-history` 模式在历史对话末尾追加新的系统提示词。

### 三家 Harness 的落地做法
- **DeepSeek Harness**：第一次请求时把 `AGENTS.md`/`CLAUDE.md` 作为第一条用户消息发出去并算出文件内容哈希值，文件没改就不再重复处理；系统提示词分段后排序（不变身份说明最前、工具说明中间、易变本地路径最后）；支持 `in-history` 模式时系统提示词存为消息列表第 `0` 号节点，中途切 Plan 模式也不改写 `0` 号节点，而是在已缓存历史末尾追加一条新的 `system` 消息，以最新一条为准，直到上下文压缩才合并回 `0` 号节点。
- **Claude Code**：先砍掉时分秒只保留年月日，会话启动时用 `memoize` 算一次塞进第一条 `<system-reminder>` 用户消息，整个会话期间不再改动；联网搜索工具提示词只放当前年月，一个月才更新一次缓存；跨天时保留第一条消息旧日期不动，只在对话末尾追加一条 `<system-reminder>` 消息告知新日期。
- **Codex**：把当前日期放在用户消息的环境信息里，每轮对比上一轮内容，日期没变就什么都不做，跨天才在末尾追加一条新消息。

### 量化数据（Manus 团队公开）
- 对话型 Agent 输入与输出 Token 比例约 `1:1`；需要处理长程任务的 Agent，因多步循环多次调用工具，比例高达 `100:1`。
- 主流模型缓存读取价格只有未命中的十分之一——系统提示词里放秒级时间戳会让账单贵 **10 倍**。
