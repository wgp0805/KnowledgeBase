# 重复消费解决方案

## 问题根因

无论直接使用 RocketMQ SDK 还是通过 Spring Cloud Stream 封装，重复消费问题都**不可避免**。根因在消息队列的投递语义层面：

```
消费者收到消息 → 执行业务逻辑 → 落库成功 → 发送 ACK 前宕机/网络断开
                                                             ↓
                                        Broker 没收到 ACK → 重新投递
```

RocketMQ 保证 **At Least Once**（至少一次），不保证 Exactly Once。Spring Cloud Stream 只是 Binder 层封装，底层 ACK 机制不变。

## 方案一：唯一消息 ID + 去重表（最通用）

每条消息携带全局唯一 ID，消费前查去重表。

```sql
CREATE TABLE msg_duplicate (
    message_id VARCHAR(64) PRIMARY KEY,
    create_time DATETIME DEFAULT NOW(),
    KEY idx_create_time (create_time)
);
```

**关键**：业务落库与写入去重表必须在同一个本地事务中。

```java
@RocketMQMessageListener(topic = "order-topic", consumerGroup = "order-group")
public class OrderConsumer implements RocketMQListener<OrderMessage> {
    @Override
    public void onMessage(OrderMessage message) {
        String msgId = message.getMsgId();
        if (duplicateMapper.existsById(msgId)) {
            return; // 已处理
        }
        // 本地事务：业务 + 去重表
        doBusiness(message);
        duplicateMapper.insert(new DuplicateRecord(msgId));
    }
}
```

Spring Cloud Stream 版本：

```java
@Bean
public Consumer<OrderDTO> processOrder() {
    return order -> {
        String dedupKey = "mq:consumed:" + order.getMsgId();
        Boolean isNew = redisTemplate.opsForValue()
                .setIfAbsent(dedupKey, "1", 24, TimeUnit.HOURS);
        if (Boolean.FALSE.equals(isNew)) return;
        doProcess(order);
    };
}
```

## 方案二：数据库唯一约束（最简单）

适用于新增类业务，业务表本身有天然唯一键。

```java
try {
    orderMapper.insert(order); // order_no 上有唯一索引
} catch (DuplicateKeyException e) {
    log.warn("重复消息已跳过: {}", order.getOrderNo());
}
```

零额外代码，但仅适用于 insert 场景。

## 方案三：Redis SETNX（高性能）

```java
String dedupKey = "dedup:" + msg.getMsgId();
Boolean first = redisTemplate.opsForValue()
        .setIfAbsent(dedupKey, "1", 24, TimeUnit.HOURS);
if (Boolean.FALSE.equals(first)) return;
doProcess(order);
```

**坑**：SETNX 成功与业务执行有时间差，业务失败时 key 已写入 → 消息丢失。Lua 脚本或用方案一兜底。

## 方案四：乐观锁 / 版本号（适合更新操作）

```sql
UPDATE goods_stock
SET stock = stock - #{quantity}, version = version + 1
WHERE goods_id = #{goodsId} AND version = #{oldVersion} AND stock >= #{quantity};
```

影响行数为 0 → 版本已变或库存不足，不重试。

## 方案五：状态机（适合订单流转）

```sql
UPDATE t_order SET status = 'PAID'
WHERE order_id = #{orderId} AND status = 'UNPAID';
```

状态单向流转，where 条件天然防重复。

## 方案六：分布式锁（防并发重复）

```java
RLock lock = redisson.getLock("lock:order:" + order.getOrderId());
if (!lock.tryLock(5, 10, TimeUnit.SECONDS)) return;
try { doProcess(order); } finally { lock.unlock(); }
```

## 生产环境推荐：多层联合防护

| 层级 | 方案 | 作用 |
|------|------|------|
| 消费前 | SETNX / 分布式锁 | 快速拦截，防并发 |
| 消费中 | 唯一约束 + 乐观锁 | 数据库级兜底 |
| 消费后 | 去重表 | 长期防重 |

## 方案选型速查

| 场景 | 方案 | 复杂度 |
|------|------|--------|
| 通用 | 消息ID + 去重表 | 中 |
| 纯新增 | 数据库唯一约束 | 低 |
| 高并发 | Redis SETNX | 低 |
| 更新操作 | 乐观锁/版本号 | 中 |
| 有状态流转 | 状态机 | 中 |
| 多实例并发 | 分布式锁 | 中 |
