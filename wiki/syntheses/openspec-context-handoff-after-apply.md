# OpenSpec apply 后上下文耗尽：交接包与新窗口重建

> **核心问题**：模型上下文窗口只有 200k（由公司侧固定、不可调），一轮 `/opsx:apply` 把窗口吃满之后，业务还要继续改。是否只能在这个窗口里反复压缩上下文？压缩带来的"跑偏"有没有办法规避？

**一句话结论**：压缩是止血手段，不是执行策略。正确做法是让 apply 会话"用完即弃"——把必须保留的状态**外置成文件**，新窗口只加载那一小份，并加一道"复述校验"闸门。

## 一、问题界定：不是窗口太小，是阶段没切

200k 其实不算小。真正的问题是把**三种性质完全不同的信息**塞进了同一个会话：

| 信息类型 | 占比（apply 结束时） | 可丢弃性 |
|---|---|---|
| explore 阶段的需求讨论、方案推演 | 大 | 全部可丢，结论已在 proposal/spec |
| 四份规划工件的生成与修订过程 | 大 | 可丢，文件在磁盘上 |
| 源码探索、试错、报错排查 | 大 | 大部分可丢，结论应落到 handoff |
| **实际改了什么、为什么这么改、坑在哪** | 小 | **必须保留** |

apply 结束时的典型状态是：**90% 可丢，10% 致命**。而压缩的动作是"把 100% 压成 30%"，既没保住那 10%，还让剩下 30% 真假难辨。

正确动作不是"把 90% 压小一点"，而是"把 10% 抽出来落盘，剩下 90% 连窗口一起扔掉"。

## 二、为什么"疯狂压缩"必然跑偏

三个机制性原因，不是运气问题：

1. **压缩是模型自主摘要**。它不知道你接下来要改哪块业务，只能按"什么看起来重要"来选择保留项。而"某个字段在拦截器里拿不到、所以改用了注解"、"这段为什么没用现有工具类"这类实现层决策，在摘要视角下恰恰是细节，最容易被砍。
2. **摘要的摘要会累积失真**。第一次压缩还能保住七成，第二次、第三次压缩后基本等于换了个陌生同事接手项目——但他说话依然自信。这就是 [[ContextRot]] 的典型形态。
3. **压缩结果不可审计**。落盘的 `handoff.md` 可以 diff、可以改；压缩后的摘要你无从核对它删了什么。

量化参照：行业实践口径是**上下文利用率维持在 40% 以下，接近阈值立刻处理**。200k 窗口的健康工作区间大约只有 80k~100k。也就是说，正常流程压根不该让它涨到"必须压缩"的临界点。

## 三、底层模型：checkpoint-rebuild 的 OpenSpec 落地

这套做法并不是新发明，它就是 [[checkpoint-rebuild]] 的工程化落地版：

- **Checkpoint**：在窗口到达上限前的固定位置，把结构化状态写入磁盘（这里由主 Agent 直接写 `handoff.md`，规模小，不必派 writer [[Subagent]]）
- **Rebuild**：切断当前窗口，用已持久化的文件作为种子重建新窗口
- **Cycle**：一个 change 的 apply 就是一个 cycle，逻辑会话是 cycle 的链

配套机制可参照：[[SessionStart]] hook 在新会话启动时自动注入交接包，[[PreCompact]] hook 在压缩前抢救关键信息。这两者能把"靠自觉"变成"靠机制"。

### 关键认知：交接包你早就有了

实现完 apply 后，很多人潜意识觉得"东西都在对话里"。其实磁盘上已有全套精简快照：

| 文件 | 它就是什么 |
|---|---|
| `opsx/changes/<change>/tasks.md` | **断点账本**，`[x]` 勾到哪里就是推进到哪里 |
| `opsx/changes/<change>/design.md` | 技术决策 + 理由（为什么这么选） |
| `opsx/changes/<change>/specs/spec.md` | 本次要实现的行为边界（Given/When/Then） |
| `opsx/specs/`（`/opsx:sync` 之后） | **系统当前现状的唯一准确描述**，新窗口最省最准的入口 |
| `opsx/archive/` | 历史基线与决策理由 |

新窗口不需要对话历史，只需要这几个文件。**你以为必须靠记忆保留的东西，八成已经在里面了。**

## 四、三会话切分：apply 吃饱就死是设计好的

| 会话 | 内容 | 上下文预算 |
|---|---|---|
| 会话 A（规划） | `/opsx:explore` → `/opsx:propose` → 人工审阅四件套 | 20k~40k |
| 会话 B（实现） | `/opsx:apply`（+ 逐项 `/tdd`） | 可吃满 200k，**用完即弃** |
| 会话 C（业务变更） | 新窗口，读交接包 + 3~5 个文件，复述确认后动手 | 目标 ≤ 40k |

会话 B 的唯一职责是**把代码落地 + 把状态写回磁盘**，它不需要"记得"任何东西。把这一点接受下来，整个焦虑就消失了。

`/opsx:archive` 之后再次改业务，走 [[delta-spec]] 增量变更（explore → propose → apply → sync → archive），详见 [[openspec-archive-modify-and-token-tradeoff]]。每个 change 天然就是会话边界。

## 五、apply 之前就要约定：逐项叫停 + 定期 checkpoint

OpenSpec 的 `/opsx:apply` 默认是**连贯执行**的：一口气按 `tasks.md` 写完所有条目、不会主动停下来。这本身就是上下文炸弹。

所以在启动 apply 时就把纪律写进指令：

```text
/opsx:apply
要求：
1. 每完成一项任务停下来等我确认，不要一口气写完所有条目。
2. 每完成 3 项任务，把当前进度、已做的关键决策、踩到的坑
   追加写入 opsx/changes/<change>/handoff.md（不要贴代码）。
3. 遇到需要偏离 design.md 的实现决策，先说明再动手。
```

叫停不是为了 TDD 纪律（那是 [[TDD]] 的事），而是为了**在上下文还健康的时候拿到 checkpoint**。而且 `tasks.md` 的 `[x]` 本身就是断点记录——哪怕上下文全丢，读一遍就知道推到哪了。**勾选账本永远比压缩摘要可靠。**

## 六、交接包模板：handoff.md 五要素

在 apply 收尾时（或上下文过半时）下达这条指令：

```text
现在写 opsx/changes/<change>/handoff.md，只写下面五项，不要贴代码：
1. 本次改了哪些文件，每个文件一句话职责
2. 关键实现决策与理由（design.md 没写死的部分、以及踩过的坑）
3. 未完成 / 妥协 / TODO
4. 下次改动的切入点：文件名 + 类名/方法名 + 行为边界
5. 本次新增或改变的行为，对应哪条 spec 条目
```

成品通常 100~300 行、2k~5k token。新窗口只喂它 + `opsx/specs/` 相关片段，20k 内就能重建出完整工作语境——**信息密度远高于一个 200k 的压缩摘要**。

为什么这五项恰好是这五项：①职责地图替代"读遍所有文件"；②决策理由替代"猜它为什么这么写"；③未完成清单防重复劳动；④切入点把"重新理解项目"压缩成"打开三个文件"；⑤行为映射保证 spec 与代码不脱节。

## 七、新窗口开场：复述校验（防跑偏的核心闸门）

跑偏的本质是"它以为的现状"和"真实现状"有偏差。所以新会话第一条消息**不要让它动手**：

```text
只读不改。先做三件事：
1. 读 opsx/changes/<change>/handoff.md
2. 读 opsx/specs/<capability>/spec.md
3. 只读这几个文件：src/.../XxxService.java、XxxController.java、XxxMapper.java

然后用 10 行以内复述：
- 这块业务当前的行为是什么
- 我这次要改的边界在哪（改什么、明确不改什么）
- 你有哪几处不确定 / 需要我确认

我确认之后你再改代码。
```

它复述错了，你立刻纠正——纠错成本几百 token；等它写了两百行代码再发现理解错了，成本是一次返工 + 又一次上下文耗尽。这一步比任何压缩手段都管用。

## 八、token 战术清单（能省 30%~50%）

- **禁止 Agent 把文件内容回显到对话里**。"把相关代码贴出来"是纯浪费，要它给你 `文件:行号 + 一句话说明`
- **大文件先要结构地图**（类/方法 + 行号），再由你指定看哪段；配合 offset/limit 分段读
- **探索丢给子代理**（如 Claude Code 的 explore / Task 子代理），只把结论 + 文件路径带回主上下文，见 [[Subagent]]
- 用 grep/glob 精确定位，禁止整目录读取；避免 [[DiscoveryLoopTax]]（反复翻找文档的无效消耗）
- **改动超过 4 个文件就拆 change**——OpenSpec 本来按 change 分片，别在一个 change 里塞三件业务
- 优先读 `opsx/specs/` 而不是 archive 全文：前者是当前基线，后者是历史堆积

## 九、压缩在什么时候才是对的

只有一种情况合理：**会话里全是探索噪音，但你只差 1~2 步收尾**。而且压缩前必须先落盘：

```text
先把刚才确认的三条结论写进 handoff.md，确认写好了再压缩上下文。
```

这样压缩丢掉的都是可丢的东西。**压缩的正确用法是"丢可丢的"，不是"指望它保住必须留的"。**

同时要认清 [[上下文压缩]] 与 [[长上下文陷阱]] 的边界：能塞进窗口 ≠ 能稳定使用，长窗口里的中段信息本来就容易被忽略，靠"塞满 + 压缩"维持的会话质量是持续下降的。

## 十、常见坑

| 坑 | 后果 | 对策 |
|---|---|---|
| 在 apply 会话里直接改业务 | 上下文临界，压缩后决策丢失，返工 | 强制开新会话 |
| 让 Agent 一次性写完 tasks 全部条目 | 中途无法 checkpoint，爆炸式占用 | apply 前约定逐项叫停 |
| 只靠压缩、不写 handoff | 第二次压缩后基本等于换人接手 | 40% 利用率就准备交接 |
| 新会话直接下指令改代码 | 理解偏差要等写错才发现 | 先做只读复述校验 |
| 手改 `opsx/archive/` 里的归档文档 | 丢失"为什么改"的痕迹，spec rot | 走 delta spec |
| 一个 change 塞多件业务 | 会话被迫超长，改动互相牵扯 | 按能力边界拆 change |

## 十一、固化后的执行清单

1. 本轮 apply 收尾时，先写 `handoff.md`（五要素），再关会话
2. 开新窗口，先做"只读 + 复述校验"，确认理解一致才动手
3. 业务变更走 delta change，不手改归档文档
4. 下次 apply 前就约定"逐项叫停 + 每 3 项写 handoff"
5. 上下文过 50% 就开始准备交接，不等到 90%
