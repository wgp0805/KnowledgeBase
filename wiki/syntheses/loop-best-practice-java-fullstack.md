# Loop 最佳实践（Java 全栈版）

> 适用技术栈：Spring Boot 3/4 + Maven + Vue 3 + MySQL/PostgreSQL
> 项目形态：单体应用、前后端分离、同一仓库（monorepo）
> 本地开发：不使用 Docker，直接本地运行
> 目标读者：希望用"循环"把"读一篇技术文章 -> 跑通一个 demo"压缩到十几分钟内的 Java 全栈开发者

## 二、核心概念澄清：三种循环机制

Claude Code 里"循环"这个词被滥用，实际有 **三种截然不同**的东西，混用是新手第一大坑：

### 2.1 三种循环对比

| 维度 | ① `/loop` 定时命令 | ② STATE.md 开发循环 | ③ ScheduleWakeup 动态循环 |
|------|-------------------|--------------------|-----------------------|
| **本质** | 固定间隔重复同一任务 | 状态驱动的逐步推进 | AI 自决定下次何时唤醒 |
| **语法** | `/loop 5m <提示词>` | 对话中说"开始开发循环" | `/loop <提示词>`（不带间隔）|
| **间隔** | 固定（5m/30s/1h）| 无固定间隔，人驱动或自动 | AI 自己选（60~3600s）|
| **状态** | 不保持，每轮独立 | 持久化在 STATE.md | 依赖 STATE.md 或对话 |
| **适合** | 编译/测试/监控等重复检查 | 读文章实现/TDD/多步骤开发 | 等异步任务、轮询外部状态 |
| **取消** | 按 `Esc` | 说"暂停" | 按 `Esc` |

### 2.2 该用哪种？决策树

```
你要做的事是"重复检查同一个东西"吗？
├─ 是 → 任务是"等待外部状态变化"吗？
│       ├─ 是（等 CI/等部署/等迁移）→ ③ ScheduleWakeup 动态
│       └─ 否（定时编译/定时测试）   → ① /loop 定时
└─ 否 → 是"多步骤逐步推进"吗？
        ├─ 是（读文章实现/TDD）→ ② STATE.md 开发循环
        └─ 否 → 大概率不该用循环，直接让 AI 做一次就行
```

### 2.3 循环的本质：一个状态机

不管哪种循环，本质都是同一个状态机：

```
[启动] → [读取状态] → [执行一轮] → [更新状态] → [判断是否达标]
                ↑                                    │
                └─────── 未达标，等间隔 ──────────────┘
                                                     │
                                              达标 → [停止]
```

**关键洞察**：循环的可靠性 = 状态机的可靠性。状态机崩了，循环就跑飞。后面所有原则都围绕"让这个状态机不崩"展开。

## 三、循环设计的五大原则（源自生产五大坑）

这是整篇指南的"宪法"。[[摘要-loop-engineering-pitfalls]] 里阶跃星辰陶炳哲总结的五大坑，每一条都是循环跑飞的直接原因。把它们转成设计原则：

### 原则 1：目标必须可验证

> ❌ "把这个功能做好"
> ✅ "所有单元测试通过、`mvn compile` 无报错、Diff 不超过 500 行"

**为什么**：循环需要一个**机器能判断的停止条件**。模糊目标让 AI 永远停不下来，或在没达标时就声称完成。

**Java 全栈的可验证目标模板**：
```
完成标准（全部为真才算完成）：
- mvn compile -q 退出码 0
- mvn test -q 退出码 0，失败数 = 0
- npm run build 退出码 0
- git diff --stat 显示改动行数 ≤ N
- 手动验证清单：[列出 3~5 个可点击/可调用的验收点]
```

### 原则 2：状态必须落地

> ❌ "我记得改到哪了"（在对话里）
> ✅ 进度写在 `STATE.md`，磁盘上

**为什么**：AI 对话是"失忆"的——`/compact` 一次、关窗一次、上下文超限一次，对话里的记忆全没了。状态文件在磁盘上，下次循环从上次停下的地方继续。

**落地规范**：见第四章。

### 原则 3：必须有停止规则

> ❌ "一直跑直到做完"
> ✅ "最多 10 轮；连续 3 轮无进展就停；单轮 token > 50k 就停"

**为什么**：没有刹车的循环会在暗坑里疯狂燃烧 token——一个编译错误修不好，循环会无限重试。停止规则要在循环启动前写死。

**停止规则三件套**：
- **最大轮数**：硬上限（如 10 轮），到点必停
- **无进展阈值**：连续 N 轮状态没变化 → 停，升级给人
- **单轮预算**：单轮 token 超阈值 → 停，说明卡住了

### 原则 4：生成与验证硬隔离

> ❌ 让同一个 AI 既写代码又检查自己对不对
> ✅ builder 写代码（有 Write/Edit 权限），checker 只读（只有 Read/Grep/Bash 跑测试）

**为什么**：自己检查自己 = 没检查。这是人类也不会做的事，AI 更不会。

**在 Claude Code 中的落地**：用**子 Agent**做隔离——主 Agent 当 builder，开一个子 Agent 当 checker（独立上下文、只读权限）。见第八章 8.3。

### 原则 5：失败信息原样转发

> ❌ checker 说"有 3 个测试失败"，builder 自己猜是哪 3 个
> ✅ 把 checker 的完整报告（哪些测试、什么错误、堆栈）原样塞给 builder

**为什么**：模糊报告让 builder 瞎猜，浪费整整一轮循环。失败信息越完整，修复越快。

## 四、STATE.md 设计规范

STATE.md 是循环的"记忆"，设计得好循环就稳，设计得差循环就乱。

### 4.1 为什么需要状态文件

| 信息存哪 | 优点 | 缺点 |
|---------|------|------|
| 对话里 | 即时、自然 | `/compact` 就丢，关窗就忘 |
| STATE.md 文件 | 持久、可恢复 | 要主动维护 |
| Git 提交信息 | 有历史 | 太重，不适合每轮记录 |

**结论**：进度和决策放 STATE.md，git 提交只记"阶段性成果"。

### 4.2 状态文件标准结构（六段式）

```markdown
# 开发循环状态

## 1. 目标
[一句话目标] + [可验证的完成标准，见原则 1]

## 2. 已完成
- [x] 步骤1: ...  (2026-07-23 14:30, commit: abc1234)
- [x] 步骤2: ...  (2026-07-23 14:45)

## 3. 待完成
- [ ] 步骤3: ...
- [ ] 步骤4: ...

## 4. 当前焦点
正在做：步骤3 - 编写 UserService
预计产出：UserService.java + UserServiceTest.java

## 5. 阻塞项 / 待决策
- 无
（或：- [阻塞] H2 和 MySQL 语法不一致，待用户确认是否切 Testcontainers）

## 6. 循环元信息
- 已执行轮数: 5
- 上一轮结果: 成功（测试通过 12/12）
- 下一轮动作: 实现步骤3
```

**六段缺一不可的原因**：
- `目标`：让每轮循环知道"往哪走"（防跑偏）
- `已完成`：避免重复劳动
- `待完成`：知道还剩什么
- `当前焦点`：本轮只做这一件事（防贪多）
- `阻塞项`：把"卡住"的事显式化，而不是在循环里死磕
- `循环元信息`：轮数和上一轮结果是"停止规则"的判断依据

### 4.3 状态演进策略

每轮循环对 STATE.md 的操作是固定的四步：

```
读 → 做 → 验证 → 写
```

1. **读**：读 `当前焦点`，明确本轮做什么
2. **做**：只做这一件事
3. **验证**：跑对应的检查命令（编译/测试）
4. **写**：更新 `已完成`/`待完成`/`当前焦点`/`循环元信息`

**铁律**：一轮只推进一个焦点。哪怕提前做完了，也不要顺手做下一件——更新状态，等下一轮。这样每轮可回溯、可回滚。

### 4.4 状态文件反模式

| 反模式 | 症状 | 后果 |
|-------|------|------|
| 巨型 STATE.md | 文件几百行，什么都往里塞 | AI 读取成本高，该看的信息被淹没 |
| 对话式记录 | "然后我做了 X，接着用户说 Y..." | 噪音大，不可结构化检索 |
| 不更新已完成 | 已完成的事还挂在待完成 | 重复劳动 |
| 当前焦点含多个任务 | "本轮做 A 和 B 和 C" | 贪多嚼不烂，循环失控 |
| 阻塞项不显式 | 卡住了但没记下来 | 循环死磕，烧 token |

**治理**：STATE.md 控制在 **80 行以内**，超过就说明该归档已完成项到 git/文档了。

## 五、CLAUDE.md 循环规则配置

CLAUDE.md 是循环的"宪法"（[[CLAUDEmd]]），让 AI 知道项目结构和循环铁律。一个配置良好的 CLAUDE.md 能让循环少问 80% 的问题。

### 5.1 完整配置模板（Java 全栈版）

将以下内容加进项目根目录的 `CLAUDE.md`：

```markdown
## 构建与测试命令

### 后端（Maven）
- 编译（跳测试）: `mvn compile -q -DskipTests`
- 编译+单元测试: `mvn test -q`
- 单测指定类: `mvn test -Dtest=UserServiceTest -q`
- 单测指定方法: `mvn test -Dtest=UserServiceTest#testCreate -q`
- 打包（跳测试）: `mvn package -DskipTests -q`
- 启动应用: `mvn spring-boot:run`

### 前端（Vue 3）
- 目录: `frontend/`
- 安装依赖: `cd frontend && npm install`
- 开发模式: `cd frontend && npm run dev`
- 构建: `cd frontend && npm run build`
- 类型检查: `cd frontend && npm run type-check`
- 单测: `cd frontend && npm run test`

### 数据库
- MySQL: localhost:3306，库名 app_db
- PostgreSQL: localhost:5432，库名 app_db
- 迁移工具: Flyway，迁移脚本在 src/main/resources/db/migration/

## 循环铁律（每次循环必须遵守）

1. 一轮只做 STATE.md「当前焦点」里的一件事
2. 做完先跑验证命令，过了再更新 STATE.md
3. STATE.md 更新四段：已完成/待完成/当前焦点/循环元信息
4. 编译失败 → 先修编译，别碰别的
5. 测试失败 → 报告「哪几个测试+错误+堆栈」，别只说"有失败"
6. 连续 2 轮没进展 → 停下来，把阻塞写进 STATE.md，问我
7. 单轮改动 > 200 行 → 停下来问我，可能走偏了

## 项目结构约定

- 后端代码: src/main/java/
- 测试代码: src/test/java/（包路径与 main 对应）
- 前端代码: frontend/src/
- API 契约: 后端 Controller 暴露的 REST 路径，前端用 axios 调用
- 不要把前端文件放进 src/main/resources/static/（我们是前后端分离，不走静态资源）
```

### 5.2 权限与安全配置

循环跑起来后，AI 会频繁执行命令。用 `deny` 把不该碰的东西锁死（比 Hook 更安全，deny 后文件对 AI"不可见"，见 [[ClaudeCode]] 权限章节）：

```markdown
## 权限边界

### 绝对禁止（deny）
- 不得执行 git push、git push --force（人工操作）
- 不得修改 pom.xml 的版本号和依赖（除非我明确同意）
- 不得删除数据库或执行 DROP/TRUNCATE
- 不得修改 .env / application-prod.yml

### 默认允许
- 读文件、搜索代码
- 运行 mvn compile / mvn test
- 修改 src/main/java 和 src/test/java 下的代码
- 修改 frontend/src 下的代码
- 更新 STATE.md
```

### 5.3 为什么 CLAUDE.md 要短

[[摘要-claude-code-best-practice-最新版]] 的硬指标：CLAUDE.md 控制在 **60 行以内，硬上限 300 行**。能从代码推断的不要写进去，只放"AI 可能猜错或不知道的信息"（构建命令、测试命令、分支规范、权限边界）。太长会挤占上下文，反而让循环变笨。

## 六、模板详解

每个模板包含：背景、前置条件、完整命令、配套文件、预期行为、进阶变种。

### 模板 1：读文章 -> 技术落地循环

**背景**：你看到一篇技术文章（如《Spring Boot 4 + Vue 3 集成 WebSocket 推送》），想在 15 分钟内跑通一个最小 demo。

**前置条件**：已配好第五章的 CLAUDE.md；项目能 `mvn compile` 通过。

**第一步：喂文章 + 建计划**

把文章内容贴给 AI，说：

```
请阅读这篇文章，做三件事：
1. 提取核心实现要点（技术栈、关键步骤、易踩的坑）
2. 创建 STATE.md，把"从零跑通 demo"拆成 6~8 个可验证步骤
   （每步必须能用一条命令验证：编译过/测试过/页面能打开）
3. 填好 STATE.md 的「目标」「完成标准」「待完成」三段
然后等我确认计划，不要直接开始写代码。
```

**为什么先停一下**：让 AI 先出计划，你扫一眼是否合理（步骤太碎？漏了数据库？）。计划错了，后面循环全是无用功。这一步对应 [[计划模式]] 思想——先对齐再动手。

**第二步：确认后启动循环**

```
计划 OK。开始开发循环：
- 从「待完成」第一项开始
- 每完成一步：跑验证 → 更新 STATE.md → 停下问我"是否继续"
- 我说 y 执行下一步
- 连续 2 轮卡住就停下问我
```

**配套 STATE.md（文章落地专用版）**：

```markdown
# 开发循环状态

## 1. 目标
按文章《XXX》实现 WebSocket 推送 demo
完成标准：
- mvn compile -q 退出码 0
- mvn test -q，WebSocketConfigTest 通过
- npm run build 退出码 0
- 启动后访问 http://localhost:8080 能看到推送页面
- 手动验证：后端推消息 → 前端实时显示

## 2. 已完成
- [x] 1. 阅读文章，提取要点 (2026-07-23)

## 3. 待完成
- [ ] 2. pom.xml 加 spring-boot-starter-websocket 依赖
- [ ] 3. 编写 WebSocketConfig 配置类
- [ ] 4. 编写 WebSocketHandler 处理类
- [ ] 5. 编写 Vue 前端页面 + WebSocket 连接逻辑
- [ ] 6. 编写 WebSocketConfigTest 单测
- [ ] 7. 跑 mvn test 确认测试通过
- [ ] 8. 跑 npm run build 确认前端通过
- [ ] 9. 启动应用，手动验证推送链路

## 4. 当前焦点
步骤2：加依赖

## 5. 阻塞项
- 无

## 6. 循环元信息
- 已执行轮数: 0
- 上一轮结果: -
- 下一轮动作: 执行步骤2
```

**第三步：切无人值守（可选）**

跑两三轮确认 AI 靠谱后：

```
切换到无人值守：自动执行剩余步骤，不用每步问我。
每轮汇报：做了什么、验证结果、下一步。全部完成或卡住时叫我。
```

**进阶变种**：文章里有多个独立特性时，拆成多个 STATE.md（`STATE-websocket.md`、`STATE-jwt.md`），循环一个跑完再跑下一个，避免一个大状态文件失控。

### 模板 2：编译检查循环（后端）

**背景**：你在重构一段复杂 Java 代码，希望每改几行就有反馈，而不是写完一大坨才发现编译炸了。

**纯监控模式（只报不修）**：

```bash
/loop 3m 运行 mvn compile -q -DskipTests 2>&1 | tail -30
只报告：编译通过 / 失败（贴前 5 条错误）。
不要改任何代码。
```

**监控+修复模式**：

```bash
/loop 3m 运行 mvn compile -q -DskipTests，如果失败：
1. 读取报错，定位文件和行号
2. 只修编译错误（不重构、不加功能）
3. 重新编译验证
4. 报告：改了哪个文件的哪几行 + 验证结果
如果连续 2 轮修不好，停下问我。
```

**间隔选择参考**：

| 改动幅度 | 推荐间隔 | 理由 |
|---------|---------|------|
| 小修小补（改方法体）| 2~3m | 改完很快就想知道对不对 |
| 中等改动（新增类/方法）| 3~5m | 留出编码时间 |
| 大重构（动多个文件）| 5~8m | 改动多，频繁检查反而打断思路 |

**进阶：跳过测试的快速反馈链**

```bash
# 最快：只编译不测试，不加 -q 反而能看到完整进度
/loop 2m mvn compile -DskipTests 2>&1 | tail -15
```

**坑**：`-q` 会把 Maven 的进度也吞掉，有时你想看到"正在编译哪个模块"，就去掉 `-q` 加 `tail`。

---

### 模板 3：测试循环（后端）

**背景**：改完一个 Service，想让测试自动跑、失败自动修。

**标准模式（跑全部测试）**：

```bash
/loop 5m 运行 mvn test -q 2>&1 | tail -40
解析结果：
- 全过 → 报告"测试全绿，N 个通过"
- 有失败 → 报告「失败测试列表 + 每个的错误信息 + 堆栈」
不要自动改代码，先让我看。
```

**修复模式（失败自动修）**：

```bash
/loop 5m 运行 mvn test -q，如果失败：
1. 读取失败的测试类和被测类
2. 判断：是测试写错了，还是被测代码有 bug
3. 修复后只重跑该测试类：mvn test -Dtest=失败的类名 -q
4. 报告：判断结论 + 改了什么 + 重跑结果
连续 2 轮修不好同一个测试 → 停下问我。
单轮 token > 30k → 停下，可能卡死循环了。
```

**指定模块/类（省时间）**：

```bash
# 多模块项目，只跑某个模块（-am 连带构建依赖模块）
/loop 3m mvn test -pl user-service -am -q 2>&1 | tail -20

# 只跑最近改的测试类
/loop 3m mvn test -Dtest=UserServiceTest -q 2>&1

# 只跑某个测试方法
/loop 3m mvn test -Dtest=UserServiceTest#testCreate -q 2>&1
```

**关键技巧**：
- 加 `-q` 减少 Maven 日志噪音，只留测试结果摘要
- 用 `tail -20` 只看尾部（失败摘要总在最后）
- 跑全量测试太慢时，循环里只跑相关测试类，提交前再手动跑全量

### 模板 4：TDD 循环（红-绿-重构）

**背景**：你想严格按 TDD 节奏开发一个功能——先写失败的测试，再写最小实现让它过，最后重构。

**TDD 的循环本质**：这是一个**嵌套循环**——外层是"功能点"循环，每个功能点内是"红-绿-重构"三层小循环。

**配套 STATE.md（TDD 专用）**：

```markdown
# TDD 循环状态

## 1. 目标
实现 UserService.createUser() 的参数校验
完成标准：
- 新增测试覆盖：空用户名、非法邮箱、重复用户名 3 个场景
- mvn test -Dtest=UserServiceTest -q 全过
- 生产代码无 if 校验堆砌（用 @Valid 或 Validator）

## 2. 功能点清单（外层循环）
- [ ] 功能点A: 空用户名校验
- [ ] 功能点B: 非法邮箱校验
- [ ] 功能点C: 重复用户名校验

## 3. 当前功能点的 TDD 阶段（内层循环）
- 当前功能点: A
- 阶段: RED（正在写失败测试）

## 4. 当前焦点
为功能点A写测试：createUser 传空用户名应抛 IllegalArgumentException

## 5. 循环元信息
- 已执行轮数: 0
- 上一轮结果: -
```

**启动命令（带确认）**：

```bash
开始 TDD 循环，目标见 STATE.md。
对每个功能点严格执行 RED -> GREEN -> REFACTOR：
- RED: 写测试，跑 mvn test 确认它失败（且因预期的原因失败）
- GREEN: 写最小实现让测试过，跑确认通过
- REFACTOR: 优化代码，再跑确认仍通过
每个阶段做完更新 STATE.md 并问我是否继续。
```

**无人值守 TDD**：

```bash
开始 TDD 循环，无人值守模式。
自动跑完所有功能点的 RED-GREEN-REFACTOR。
每完成一个功能点汇报一次。全部完成或卡住时叫我。
卡住的判定：同一功能点同一阶段连续 2 轮失败。
```

**TDD 循环的关键纪律**（防 AI 偷工）：
- **RED 必须真失败**：AI 有时会写一个"永远通过"的假测试糊弄。要求它跑测试，确认是 `失败` 且失败原因 = 预期原因。
- **GREEN 必须最小**：AI 容易过度实现。要求它只写让测试过的最小代码，不提前做下一个功能点。
- **REFACTOR 必须重跑**：重构后测试必须仍绿，否则回滚重构。

### 模板 5：前后端联合编译循环

**背景**：你同时改了后端 Controller 和前端页面，想确保两端编译都通过，且 API 契约没断。

**基础版（两端编译）**：

```bash
/loop 5m 检查前后端编译：
1. 后端: cd 项目根 && mvn compile -q -DskipTests 2>&1 | tail -15
2. 前端: cd frontend && npm run build 2>&1 | tail -15
3. 两端都过 → 报告"前后端编译均通过"
4. 任一端失败 → 报告哪端失败 + 错误，只修失败那端，不要动通过的那端
```

**进阶版（带 API 契约校验）**：

前后端分离最大风险是"后端改了路径/字段，前端没跟上"。加一层契约检查：

```bash
/loop 5m 执行三层检查：
1. 后端编译: mvn compile -q -DskipTests
2. 前端构建: cd frontend && npm run build
3. 契约一致性:
   - 用 Grep 扫后端 Controller 的 @RequestMapping/@GetMapping 路径
   - 扫前端 axios 调用的 URL
   - 对比：前端调了但后端没有的路径 → 报告
   - 后端有但前端没调的路径 → 只报告，不算错
任一编译失败 → 先修编译
契约不一致 → 报告清单，问我怎么对齐
```

**前端目录不在 frontend/ 时的适配**：
把命令里的 `frontend` 换成你的实际目录（`web/`、`src/main/frontend/`、`ui/` 等）。

### 模板 6：ScheduleWakeup 动态循环

**背景**：你要等一个**外部异步事件**（数据库迁移跑完、CI 流水线结束、一个文件被生成）。用固定间隔太傻——可能等 10 分钟结果 30 秒就好了，白白轮询 20 次；也可能设太短太吵。让 AI 自己决定何时再查。

**Claude Code 的动态模式**：`/loop` **不带间隔**时进入动态模式（底层 ScheduleWakeup），AI 会根据情况自己安排下次唤醒（60~3600 秒后）。

**场景 A：等数据库迁移完成**

```bash
/loop 等 Flyway 迁移完成。
每轮：
1. 查询 flyway_schema_history 表，看是否有 success=0 的记录或未执行的新版本
2. 没跑完 → 报告进度，安排 60 秒后再查
3. 跑完且无失败 → 报告"迁移完成，N 个版本执行成功"，停止循环
4. 跑完但有失败 → 报告失败详情，停止循环，问我
```

**场景 B：等 CI 流水线**

```bash
/loop 等 GitLab CI 跑完。
每轮用 gh 或 gitlab-cli 查 pipeline 状态：
- running → 安排 120 秒后再查
- success → 报告"CI 通过"，停止
- failed → 报告失败 job，停止，问我
```

**场景 C：等一个文件被生成**

```bash
/loop 等 target/report.pdf 生成。
每轮检查文件是否存在 + 大小 > 0：
- 不存在 → 30 秒后再查
- 存在且非空 → 报告"文件已生成，大小 X KB"，停止
```

**动态模式 vs 固定间隔的选择**：

| 特征 | 用动态 | 用固定间隔 |
|------|-------|----------|
| 完成时间不确定 | ✅ | |
| 完成时间可预估且固定 | | ✅ |
| 想省 token（少轮询）| ✅ | |
| 要做定时巡检（每 5 分钟看一眼日志）| | ✅ |

### 模板 7：分诊+修复循环（Triage + Fix）

**背景**：你接手一个老项目，跑一次 `mvn test` 几十个失败，不知道从哪下手。这是 [[LoopEngineering]] 里 loop-triage Skill 的思想。

**分诊阶段（先别修，先归类）**：

```bash
分诊当前所有编译错误和测试失败：
1. 跑 mvn compile + mvn test，收集全部错误
2. 按根因分类，比如：
   - 依赖缺失（缺 jar）
   - 语法错误（分号、括号）
   - API 不兼容（Spring 版本变了）
   - 测试数据问题（H2 不支持某语法）
   - 环境问题（端口占用、连不上库）
3. 每类列出：数量 + 1~2 个代表例子
4. 按"修复成本/影响面"排序，给我一个修复优先级清单
先不要改代码，等我看清单。
```

**修复阶段（按优先级逐类修）**：

```
按清单顺序修复，每修一类：
1. 只改这一类的问题，不顺手修别的
2. 修完跑一次 mvn test 看这类是否清零
3. 更新 STATE.md：已修复类、剩余类、当前焦点
4. 报告：修了什么、还剩什么、是否触发新错误
连续修 2 类都没进展 → 停下问我。
```

**为什么分诊和修复要分开**：[[摘要-loop-engineering-pitfalls]] 第二条——失败信息要原样转发。分诊产出的是"结构化的全貌"，修复基于这个全貌动手，而不是边修边重新发现错误。

---

### 模板 8：数据库迁移验证循环

**背景**：改了数据库结构（加字段、改类型、加索引），要确保迁移脚本本身没问题，且迁移后数据完整性没破。

**迁移前预检 + 执行 + 验证**：

```bash
/loop 执行数据库迁移并验证：
1. 预检: 用 Grep 扫 src/main/resources/db/migration/ 新增的 V*__*.sql
   - 检查有没有 DROP TABLE / TRUNCATE（危险操作，停下问我）
   - 检查 ALTER 改类型的字段是否有默认值（避免 NOT NULL 卡老数据）
2. 执行: mvn flyway:migrate
   - 失败 → 报告 + 停下，不要自动回退
3. 验证（迁移成功后）:
   - 统计关键表行数，和迁移前对比（不该异常减少）
   - 跑 mvn test 看持久层测试是否还过
4. 全过 → 更新 STATE.md，报告"迁移完成 + 数据校验通过"
任一步异常 → 停下问我，不要自作主张回退
```

**安全铁律**（写进 CLAUDE.md）：
- 迁移脚本的 `DROP`/`TRUNCATE`/`DELETE FROM` 必须人工确认
- 不允许 AI 自动 `flyway:undo`（Flyway 社区版不支持 undo，强退会留烂摊子）
- 迁移前先备份或确认有快照（本地非 Docker，`pg_dump` / `mysqldump` 备一份）

## 七、Java 全栈测试分层与循环

循环里跑测试，要知道跑的是哪一层。盲目 `mvn test` 跑全量集成测试会让循环卡几分钟。

### 7.1 测试金字塔（Spring Boot）

```
        /\
       /  \   端到端测试（@SpringBootTest 全量启动）
      /----\   少而慢，循环里尽量少跑
     /      \
    / 切片测试 \  @WebMvcTest / @DataJpaTest / @JsonTest
   /----------\  中等，测某一层，循环主力
  /            \
 /  纯单元测试   \ 不起 Spring，毫秒级，循环高频跑
/----------------\
```

### 7.2 各层测试的循环命令

| 层 | 注解 | 循环命令 | 速度 | 用途 |
|----|------|---------|------|------|
| 单元 | 无 Spring | `mvn test -Dtest=UserServiceTest -q` | 毫秒 | 纯逻辑，循环高频 |
| Web 切片 | `@WebMvcTest` | `mvn test -Dtest=UserControllerTest -q` | 秒 | Controller 层 |
| JPA 切片 | `@DataJpaTest` | `mvn test -Dtest=UserRepositoryTest -q` | 秒 | Repository 层 |
| 全量集成 | `@SpringBootTest` | `mvn test -q`（全跑）| 分钟 | 提交前手动跑 |

**循环策略**：开发中循环只跑**切片测试**和**单元测试**（快），提交前手动跑一次全量集成。

### 7.3 测试隔离策略（不用 Docker 的本地开发）

不用 Docker 时，测试隔离靠 H2 内存库或 Testcontainers（Testcontainers 需要 Docker，你本地不用，所以用 H2）：

**H2 内存库方案**（`application-test.yml`）：

```yaml
spring:
  datasource:
    url: jdbc:h2:mem:testdb;MODE=MySQL;DB_CLOSE_DELAY=-1
    driver-class-name: org.h2.Driver
  jpa:
    hibernate:
      ddl-auto: create-drop
  flyway:
    enabled: false  # 测试用 JPA 自动建表，不走 Flyway
```

**坑**：H2 和 MySQL 语法有差异（`MODE=MySQL` 能缓解但不全等）。涉及 MySQL 特有语法（如 `ON DUPLICATE KEY UPDATE`）的测试，H2 会报错。这时要么改写 SQL，要么那几个测试用 `@Tag('mysql-only')` 标记，循环里跳过它们，手动跑。

PostgreSQL 项目同理，H2 设 `MODE=PostgreSQL`。

**写进 CLAUDE.md**：

```markdown
## 测试隔离
- 单元/切片测试用 H2 内存库（application-test.yml）
- 循环里只跑 -Dtest=指定类，不跑全量
- 标记 @Tag("db-specific") 的测试循环跳过，手动跑
- 提交前手动跑一次 mvn test 全量
```

## 八、循环编排模式

把单个模板组合起来，就是"编排模式"。理解这几种模式，能应对没见过的复杂场景。

### 8.1 单任务循环

最简单：一个循环干一件事。

```
/loop 3m mvn compile -q
```

适合：编译检查、测试监控。问题是没有"修复"环节，失败只是报告。

### 8.2 分诊+修复模式（Triage + Fix）

[[LoopEngineering]] 的 loop-triage + minimal-fix 组合。

```
分诊 → 出清单 →（人工确认）→ 逐项修复 → 验证
```

适合：接手老项目、一堆失败不知道从哪下手（模板 7）。

### 8.3 生成+验证模式（Builder + Checker）★ 重点

这是 [[摘要-loop-engineering-pitfalls]] 第一条"生成与验证硬隔离"的落地。用**子 Agent**做隔离：

```
主 Agent（builder）：有 Write/Edit 权限，写代码
  ↓ 调用
子 Agent（checker）：只读权限，独立上下文，跑测试、审查代码
  ↓ 返回
主 Agent 收到完整报告 → 决定下一步
```

**在 Claude Code 里的实现**（用 Task 工具开子 Agent）：

```
写完 UserService 后，开一个子 Agent 做独立验证：
- 子 Agent 只读，不能改代码
- 任务：审查 UserService 的代码质量 + 跑 UserServiceTest
- 返回：问题清单（每条带文件:行号）+ 测试结果
把子 Agent 的完整报告贴给我，我来决定改不改。
```

**为什么有效**：
- checker 独立上下文，不会被 builder 的"我已经写好了"思路污染
- checker 只读，物理上无法篡改代码来自圆其说
- 报告完整转发，builder 不靠猜

### 8.4 渐进信任模型（L1 → L2 → L3）

[[LoopEngineering]] 的三级模式，是"何时放手让 AI 自动跑"的策略：

| 级别 | 行为 | 何时用 |
|------|------|--------|
| **L1 报告模式** | 只报告不修代码 | 刚接手项目/不熟悉 AI 时，建立信任 |
| **L2 分诊+小修** | 自动修简单问题，复杂的升级给人 | 跑了几轮确认 AI 靠谱后 |
| **L3 无人值守** | 近乎全自动，达标才停 | 重复性高、边界清晰的任务 |

**渐进路径**：
1. 新项目/新 AI：L1，每轮人工看报告
2. 跑 3~5 轮无误：升 L2，让它修小问题
3. L2 连续 5 轮无人工干预：升 L3，无人值守
4. L3 出现一次跑偏：降回 L2，复盘原因

**绝不跳级**：直接上 L3 容易翻车，因为还没建立"哪些错误 AI 会犯"的认知。

## 九、循环的停止与恢复

### 9.1 停止规则设计清单

每个循环启动前，在 STATE.md 或命令里写死这三类刹车：

```markdown
## 停止规则（写死，不可被循环自行放宽）
- 最大轮数: 10
- 无进展阈值: 连续 2 轮「待完成」无变化 → 停
- 单轮预算: 单轮 token > 50k → 停
- 达标即停: 完成标准全满足 → 停，不要"顺便再做点别的"
```

**为什么"达标即停"要强调**：AI 有"过度服务"倾向，达标后想"再优化一下""再加个测试"，结果引入新问题。达标必须立刻停。

### 9.2 失败升级机制

循环里遇到搞不定的事，要会"升级"而不是死磕：

```
升级阶梯：
1. 单轮失败 → 重试 1 次（可能是偶发）
2. 连续 2 轮失败 → 停下，把问题写进 STATE.md「阻塞项」
3. 阻塞项累积 3 个 → 整个循环暂停，向我汇报全貌
```

**升级时要带什么**：不要只说"卡住了"，要带：
- 卡在哪一步
- 试过什么方法
- 报错原文
- 你的判断（缺信息？权限？还是真 bug？）

### 9.3 中断恢复

循环被 `Esc` 或关窗打断后，怎么接着跑：

```
恢复命令：
读 STATE.md，从「当前焦点」继续执行开发循环。
先跑一次验证确认当前状态，再推进下一步。
```

**为什么 STATE.md 要记"循环元信息"**：恢复时 AI 能看到"已执行 N 轮、上一轮结果"，不会从零开始，也不会重复跑已完成的事。

## 十、Token 预算与上下文管理

循环是 token 大户，不管理会烧钱烧到限流。

### 10.1 循环的 token 消耗模式

| 因素 | 消耗 | 应对 |
|------|------|------|
| 每轮重读大文件 | 高 | 用 Grep/Glob 定位，不要整文件 Read |
| STATE.md 越长越大 | 中 | 控 80 行内，已完成项及时归档 |
| 失败信息太长 | 中 | `tail -20` 截断，只留摘要 |
| 上下文累积 | 高 | 每 5~6 轮 `/compact` |

### 10.2 上下文膨胀应对

[[ClaudeCode]] 的硬指标：上下文 50% 手动 `/compact`，60~70% 性能明显下降。

**循环里的上下文纪律**：
- 每 5~6 轮主动 `/compact`，用 `focusing on 当前焦点和未完成项`
- `/compact` 后让 AI 重读 STATE.md 找回状态（状态在文件里，不在对话里，所以不丢）
- 单轮输出超长（比如贴了整个堆栈）→ 当轮就 `/compact`

### 10.3 预算控制（loop-budget 思想）

[[LoopEngineering]] 的 loop-budget Skill 思想：给循环一个总预算，超了就停。

**在命令里写死预算**：

```bash
开始开发循环，预算上限：本次最多跑 8 轮 / 消耗 50 万 token。
每轮报告：已用轮数、估算已耗 token。
接近预算 80% 时：停止新增步骤，只收尾当前步骤。
超预算 → 立刻停，汇报进度。
```

## 十一、常见坑与对策（扩充版）

### 坑 1：编译输出太多看不到关键错误
**对策**：`-q` + `tail`：
```bash
/loop 3m mvn compile -q 2>&1 | tail -30
```

### 坑 2：测试跑太久循环卡住
**对策**：只跑相关测试类：
```bash
/loop 3m mvn test -Dtest=UserServiceTest -q 2>&1
```

### 坑 3：前端 node_modules 不存在
**对策**：循环前先 `npm install`，并写进 CLAUDE.md：
```markdown
- 前端构建前若 node_modules 不存在，先 cd frontend && npm install
```

### 坑 4：循环跑偏（在做无关的事）
**对策**：`Esc` 或"回到 STATE.md 当前焦点，不要做其他"。根因是 STATE.md「当前焦点」没写清或含多任务——回去修 STATE.md。

### 坑 5：上下文膨胀变笨
**对策**：每 5~6 轮 `/compact focusing on 当前焦点和待完成项`，然后让 AI 重读 STATE.md。

### 坑 6：AI 自己检查自己（不可靠）
**对策**：用子 Agent 做独立验证（8.3 模式），builder 和 checker 分离。

### 坑 7：循环停不下来
**对策**：启动前写死停止规则（9.1），最大轮数 + 无进展阈值 + 预算上限三道刹车。

### 坑 8：达标了 AI 还继续"优化"
**对策**：命令里明确"达标即停，不要顺便做别的"。这是 AI 过度服务的典型表现。

### 坑 9：失败信息被 AI 概括成"有错误"
**对策**：要求"报告失败测试名 + 错误信息 + 堆栈原文，不要概括"（原则 5）。

### 坑 10：H2 和 MySQL 语法不一致导致测试假失败
**对策**：标记 `@Tag("db-specific")`，循环跳过手动跑；或改写 SQL 用兼容语法（7.3）。

### 坑 11：循环里改了不该改的（pom 版本、git push）
**对策**：CLAUDE.md 里 `deny` 锁死（5.2），比 Hook 更彻底。

### 坑 12：循环改了一堆文件不知道改了啥
**对策**：每轮结束要求"git diff --stat 汇报改动文件和行数"，单轮超 200 行停下确认。

## 十二、反模式：什么时候不要用循环

循环不是银弹，这些场景用了反而更糟：

| 反模式 | 为什么不该用 | 该怎么做 |
|-------|------------|---------|
| 一次性任务用循环 | "写个 hello world"没必要循环 | 直接让 AI 做一次 |
| 需要人判断的决策 | "这个架构选哪个"AI 没法循环出答案 | 先人工决策，再用循环执行 |
| 无明确停止条件的任务 | "把代码质量搞好"永远停不下 | 先定可验证目标（原则 1） |
| 高危不可逆操作 | 循环里 DROP TABLE / git push --force | 人工做，循环里 deny |
| 跨多个无关项目 | 状态机太复杂必崩 | 拆成多个独立循环 |
| 紧急修 bug | 循环启动成本高于直接修 | 直接让 AI 修，验证一次 |

**判断标准**：如果一件事能在一次对话内做完且验证通过，就别上循环。循环的价值在于"多轮迭代 + 状态保持"，单轮能搞定的用循环是浪费。

## 十三、完整实战案例

### 案例 1：从文章到可运行 demo（端到端）

**情境**：周五下午看到一篇《Spring Boot 3 + Vue 3 + SSE 实现服务器推送》的文章，想在下班前跑通 demo。

**执行**：

1. **配 CLAUDE.md**（5 分钟）：把第五章模板贴进项目，改好路径和数据库配置。

2. **喂文章建计划**（2 分钟）：
   ```
   读这篇文章，按模板1的流程建 STATE.md，拆成可验证步骤，先给我看计划。
   ```

3. **确认计划启动 L2 循环**：
   ```
   计划 OK。L2 模式开始：自动修简单步骤，复杂的停下问我。
   每 3 步跑一次 mvn compile 确认没炸。
   ```

4. **切 L3 无人值守**（跑顺后）：
   ```
   切 L3，自动跑完，达标即停。每完成一步汇报。
   ```

5. **收尾验证**：
   ```
   跑一次全量 mvn test + npm run build + 手动验证推送页面。
   ```

**预期产出**：一个能跑的 SSE demo + 一份记录了每步决策的 STATE.md。

### 案例 2：给老项目补测试

**情境**：接手一个没测试的老 Spring Boot 项目，想补上关键路径的测试。

**执行**：

1. **分诊**（模板 7）：
   ```
   分诊项目：列出核心 Service 和 Controller，评估每个的测试优先级（按调用频率和业务关键度）。
   ```

2. **建 STATE.md**：把高优先级类列进「待完成」，每个类是一个 TDD 循环。

3. **逐个 TDD**（模板 4）：对每个类跑 RED-GREEN-REFACTOR，L2 模式，复杂逻辑升级给人。

4. **每补完一个类**：跑该类测试 + 汇报覆盖率变化。

5. **全量验证**：补完 5~8 个核心类后，手动跑一次全量 `mvn test`。

**避坑**：别让 AI 一次性补所有测试——状态文件会失控，且容易写出"为覆盖率而测试"的废测试。一个类一个循环。

## 十六、关键概念速记

| 概念 | 一句话 |
|------|-------|
| 三种循环 | `/loop` 定时 / STATE.md 开发 / ScheduleWakeup 动态 |
| 五大原则 | 目标可验证 / 状态落地 / 有停止规则 / 生成验证隔离 / 失败原样转发 |
| STATE.md 六段 | 目标 / 已完成 / 待完成 / 当前焦点 / 阻塞项 / 元信息 |
| 循环四步 | 读 → 做 → 验证 → 写 |
| 三级信任 | L1 报告 → L2 小修 → L3 无人值守 |
| 测试分层 | 单元（毫秒）/ 切片（秒）/ 集成（分钟），循环只跑前两层 |
| 编排模式 | 单任务 / 分诊+修复 / 生成+验证（builder/checker） |
| 三道刹车 | 最大轮数 / 无进展阈值 / 预算上限 |
