## 定义

异常处理是 Java 在运行期检测、传播、捕获错误的机制。Java 通过 `try`/`catch`/`finally`/`throw` 语法组织，但**编译后在字节码层面，catch 不是靠跳转指令实现，而是靠方法体附带的「异常表（Exception table）」**——这一点是理解"try catch 是否影响性能"的关键。

## 关键信息

### 异常表机制

`javap -verbose` 查看编译产物，方法末尾有 `Exception table`：

```
Exception table:
from    to    target  type
0       5     8       Class java/lang/Exception
```

- `from`~`to`：try 块覆盖的指令区间
- `target`：命中异常后跳转的指令地址（catch 块起点）
- `type`：捕获的异常类型

**无异常时**：执行流直接从 try 块末尾 `goto` 跳过 catch 块返回——**没有查表、没有额外开销**，性能损耗几乎不存在。所以"try catch 严重影响性能"是上古认知（早期用 jsr/ret 指令实现）。

### 真正影响性能的是"抛异常"本身

- 抛出异常需要**构造异常对象、填充栈轨迹（fillInStackTrace）**，这才是开销大头
- 实测：百万次"未抛异常的 try catch" vs "每次必抛异常"，后者显著更慢
- 结论：**try catch 语法几乎零成本；异常对象创建与栈回溯才有成本，应避免用异常做常规流程控制**

### 与 JIT 优化的关系

- 解释模式（`-Xint`）下，多个 try catch 带来的多个 goto 跳转有微量开销（千万次差 5~7ms），原因是 goto 指令占比过大；代码量大时占比降低，影响趋于合理
- 编译模式（`-Xcomp`）下，JIT（C2）可把多 try catch 的 goto 开销一并优化，亿级计算也难分胜负 → **try catch 不影响即时编译**
- 可读性启发：多个小 try catch 合并为一个大 try catch 是否更优，暂无定论（涉及指令重排序的屏障猜想未证实），实践中按"捕获范围最小化 + 语义清晰"原则写即可

### 工程建议

- 优先保证程序健壮性，该捕获就捕获
- 不要用异常做正常控制流（如用 NumberFormatException 判断字符串是否为数字）
- 捕获后要么处理、要么带上下文重抛，避免 `catch { }` 空吞
- `finally` 里的代码在 JIT 优化后同样几乎无额外成本
