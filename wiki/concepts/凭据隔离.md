## 定义

凭据隔离是 Agent 安全中的**兜底手段**：不指望「审查模型一定能拦住恶意调用」，而是从工程上保证**就算 Agent 被注入并执行了恶意命令，它手里也拿不到可用的密钥**。

核心思路是**把「密钥的存在」和「密钥的可用」拆开**——模型上下文里只有引用名，真正解析发生在模型触达不到的边界之外。

## 关键信息

### 两道具体措施

**一、配置文件只存环境变量的引用名称**

不存明文密码，只存形如「这个字段读哪个环境变量」的引用；真正用到时再由**凭据服务**按需解析。密钥因此不会落到模型上下文、不会落到日志、也不会落到 Agent 生成的代码里。

**二、子进程启动时默认擦除**

Agent 要启动 Bash 终端、外部扩展或子进程时，框架先**基于父进程环境做一遍清洗**：

- 变量名里包含 `KEY`、`PASSWORD`、`SECRET`、`TOKEN` 的敏感项 → 抹掉
- **所有 `DSH_` 开头的变量** → 抹掉

效果：**就算注入骗 Agent 执行了打印环境变量的命令，子进程里也没有宿主机的 API Key 和云服务密钥**。这是「默认擦除」而非「按需保留」——白名单式放行，失败方向是安全的。

### 为什么它属于「第三道兜底」

[[自动审查模式]] 是模型判断，会看走眼。凭据隔离**不依赖任何判断**，是确定性的工程约束。它与 [[沙箱]]（限制能碰什么文件）、[[审批设计]]（限制高危操作能否执行）共同构成「审查失手之后」的三层兜底：

| 兜底 | 限制的维度 |
| --- | --- |
| 凭据隔离 | 能拿到什么秘密 |
| [[沙箱]] | 能碰哪些文件与网络 |
| [[审批设计]] | 高危操作能否真的执行 |

三者叠加后，一次成功的注入即使骗过了审查员，也需要同时突破「没密钥、没文件权限、没人批准」三重门。

### 局限

- 环境变量擦除只覆盖**通过环境变量传递**的秘密；写在磁盘配置文件里的明文密钥不受保护
- 子进程擦除依赖变量**命名规范**（含 `KEY`/`SECRET`/… 或 `DSH_` 前缀）；命名不规范的秘密会被漏掉
- 凭据服务本身成为新的信任中心，它一旦被攻破，隔离即失效
