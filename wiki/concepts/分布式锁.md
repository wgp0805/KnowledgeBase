## 定义
分布式锁是分布式环境下保证跨进程、跨节点互斥访问共享资源的机制。当多个服务实例并发操作同一资源（库存扣减、定时任务触发、配置更新）时，用分布式锁确保同一时刻仅一个执行。

## 关键信息

### 三大实现路线
| 实现 | 机制 | 优劣 |
|------|------|------|
| Redis | `SET NX PX` + Lua 释放；Redlock 多节点 | 性能高，但锁失效边界依赖 TTL，CAP 取舍 |
| Zookeeper | 顺序临时节点 + Watch | 强一致（CP），可靠但延迟高 |
| 数据库 | 唯一索引 / 行锁 / `for update` | 简单，性能与扩展性最弱 |

### 工程要点
- **锁释放必须校验持有者**：释放时用 Lua 原子比对 value（随机 token），防误删他人锁
- **续期（看门狗）**：长任务需后台线程续 TTL，防业务未完锁先过期
- **可重入**：同一线程多次获取用计数器
- **Redlock 争议**：Martin Kleppmann 与 antirez 论战，对一致性敏感场景慎用 Redis 锁

### 幂等场景中的用法：锁 + 幂等表双保险（2026-10 补充）
分布式锁本身**不保证幂等**——它只保证同一时刻一个执行者，串行化之后"第二个请求"仍会依次执行。所以幂等场景必须叠加业务幂等检查：

```java
RLock lock = redisson.getLock("lock:stock:" + cmd.getProductId());
if (!lock.tryLock(3, 5, TimeUnit.SECONDS)) return fail("处理中，请稍后");
try {
    if (repo.existsByRequestId(cmd.getRequestId())) return ok("已扣减"); // 幂等检查
    repo.deductStock(cmd);
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}
```

- **`tryLock(waitTime, leaseTime)` 的两个时间**：最多等多久（防无限阻塞）、持锁多久自动释放（防死锁）
- **幂等键放业务表加唯一索引**，而不是只靠锁：锁防并发，唯一索引防重放
- **`isHeldByCurrentThread()` 不可省**：避免阻塞超时后误删别人的锁
