## 定义
异常边界（Exception Boundary）指程序在发生异常时，"失败应该停在哪里"的语义划定。它决定了 `try catch` 相对于 `for` 循环的位置：核心判断标准不是性能，而是**这次循环里某一条失败后，后面的数据还要不要继续跑**。

- 不能继续（整批是一个整体）→ `try catch` 放**循环外面**
- 可以继续（每条相互独立）→ `try catch` 放**循环里面**

## 关键信息

### 放外面：一条失败，整批停止
适用于强一致、后续步骤依赖前序步骤的场景：订单状态迁移（PAID→SHIPPING→写物流→发通知）、批量转账等。语义是"一批任务是一个整体，失败就停"。
```java
try {
    for (UserDTO user : users) {
        saveUser(user); // 任一条抛异常，循环立即中断
    }
} catch (Exception e) {
    log.error("批量导入用户失败", e);
}
```

### 放里面：一条失败，后面继续
适用于每条独立的场景：批量导入、批量发短信/推送、消息消费、爬虫、批量调第三方接口。好处是能给出结构化结果（成功 N 条 / 失败 M 条 / 每条失败原因 / 行号），远比一句"批量任务失败"有用。
```java
for (UserDTO user : users) {
    try {
        saveUser(user);
        result.addSuccess(user.getUsername());
    } catch (DuplicateKeyException e) {   // 可预期业务失败，记录后继续
        result.addFail(user.getUsername(), "用户已存在");
    }
}
```

### 分寸：能处理 vs 不能处理
即使放里面，也不是所有异常都该继续。单条数据问题（手机号格式错、唯一键冲突、参数非法）可继续；系统级问题（数据库连不上、连接池打满、表结构不对）继续跑只会制造更多失败日志，应 `throw` 中断，交上层重试/告警。

## 三个易踩的坑

1. **事务被错误提交**：`@Transactional` 方法里 catch 住异常只打日志不外抛，Spring 会认为方法正常结束而提交事务。要回滚就抛运行时异常、配 `rollbackFor` 或 `setRollbackOnly`，别吞。
2. **大事务里无法单条独立提交**：循环里 catch 看似"单条失败继续"，但所有操作仍在同一大事务里；某些数据库异常会把当前事务标记为 rollback-only，最终提交时抛 `UnexpectedRollbackException`。需将单条处理拆到独立事务方法（`@Transactional(propagation = REQUIRES_NEW)`），且注意**自调用 `this.importOne()` 会绕过 Spring 代理导致 @Transactional 失效**，应通过其他 Bean 或代理对象调用。
3. **异常当流程控制**：正常路径下 `try catch` 本身不是性能瓶颈（编译后只是字节码异常表覆盖范围不同），真正贵的是**频繁抛异常**（创建异常对象 + 填充调用栈）。用 `Integer.parseInt` 抛 `NumberFormatException` 判断字符串是否为数字就是反例——可预判的错误应提前用普通校验判断（但高频循环里也别滥用复杂正则）。

## catch 的纪律
- catch 不是垃圾桶：能修复就修复，能降级就降级，能记录就记录，不能处理就往上抛。
- 别随便 catch `Throwable`（会吞掉 `OutOfMemoryError` 等 Error），`Exception` 也别无脑吞。
- 多 catch 时**子类异常放前面，父类异常放后面**，否则父类先捕获，子类分支永远走不到。

## 一句话总结
`try catch` 放里面，是为了单条失败继续跑；放外面，是为了整体失败一起停。
