## 定义
Elasticsearch 中 `from + size` 分页在翻页越深时，各分片与协调节点需加载、排序的数据量暴涨的现象。默认 `index.max_result_window=10000` 参数拦截超过 10000 条的分页请求。

## 关键信息

### 根因：分布式架构
- **两阶段查询**：
  - **Query 阶段**：协调节点广播请求到每个分片，各分片返回 `from + size` 条文档元数据（`_id` 与排序值），而非用户想要的那 N 条
  - **Fetch 阶段**：协调节点对来自所有分片的数据做全局归并排序，找到目标区间后回各分片取完整文档，前面 `from` 条全部丢弃
- **开销公式**：协调节点开销 = `from + size` × 分片数
- **示例**：翻到第 10 万页（from=1000000, size=10），5 个分片时协调节点要处理 500 万条元数据做归并排序

### 为什么默认上限是 10000 而不是 100 万
10000 是官方在"常见分页需求"与"集群安全"之间取的保守经验值，需要控制在堆内存能轻松扛住的范围。

### 四大解决方案
| 方案 | 原理 | 适用场景 | 能否跳页 | 实时性 |
|------|------|----------|----------|--------|
| `from + size` | 各分片取 from+size 条，协调节点汇总排序 | 浅分页（前 10000 条以内） | ✅ | ✅ 实时 |
| `scroll` | 首查生成数据快照，用 scroll_id 游标遍历 | 离线批量导出、全量扫描 | ❌ | ❌ 快照非实时 |
| `search_after` | 用上一页最后一条的排序值定位下一页 | 实时深度翻页 | ❌ | ✅ 实时 |
| `PIT + search_after` | 轻量级时间点视图 + 游标 | ES 7.10+ 官方推荐 | ❌ | 视图内一致 |

### 四种场景选型
- 浅分页 → `from + size`
- 全量导出 → `scroll`（7.10 起 deprecated）
- 实时深度翻页 → `search_after`
- 讲究一致性 → `PIT + search_after`

### 调大 max_result_window（不推荐）
```
PUT /order/_settings
{ "index.max_result_window": 1000000 }
```
本质是拆闸门，OOM 风险不变。真有硬跳页需求应走离线任务预排序、secondary 查询或产品限制。

### 记忆口诀
浅翻 from + size，导出用 scroll，实时深翻 search_after，要一致性加 PIT，调大窗口是自欺。

## 对照：MySQL 的深分页（2026-10-29 补充）
同一个问题在关系库里以 `LIMIT offset, size` 的形式出现，根因不同——**不是分布式归并，而是"扫描后丢弃"**：

- `LIMIT 100000, 10` 需要扫描 100010 行，然后扔掉前 100000 行
- 三种解法：
  | 方案 | 写法 | 特点 |
  |------|------|------|
  | 延迟关联 | 子查询先用覆盖索引取主键，再 join 回表取整行 | 保留跳页能力，需一次额外 join |
  | [[游标分页]] | `WHERE id > last_id ORDER BY id LIMIT 10` | 性能恒定，但**不能跳页** |
  | 限制翻页深度 | 产品层只允许看前 N 页 | 最省事，很多场景够用 |
- 关键差别：MySQL 的瓶颈是 **offset 越大扫描越多 + 回表**；ES 的瓶颈是 **from+size × 分片数 的全局归并**。所以 MySQL 有"延迟关联"这种保留跳页能力的解法，ES 只能靠 `search_after` 或 `PIT` 放弃跳页
