## 定义
上下文保留决策是用 [[Jev]] 对 Agent 历史中的工具调用做**"保留价值判断"、而非"改写总结"**的上下文压缩模式，源自 GitHub 项目 fast-jev-compaction。核心转变：**上下文压缩可以从"总结旧历史"改成"判断保留价值"。**

## 关键信息

### 为什么传统 summary 有问题
传统 summary 省 token，但会**改写事实**。原始测试日志 `FAIL order-export.test.ts / Timeout of 5000ms exceeded / at exportOrders(orderExport.ts:42:19) / Expected authorization header to be preserved.` 被摘要成"之前订单导出测试失败了"——关键细节全丢：哪个测试失败、5000ms 是什么阈值、具体定位、authorization header 说明问题不只是性能还牵涉鉴权约束。**上下文压缩最怕的不是删掉废话，而是把关键事实改写成一句"差不多"。** 因为 Agent 下一步不是"理解大意"，而是要继续执行动作。

### 三层断裂（为何通用 LLM 做不好高频压缩）
1. **生成成本和判断需求不匹配**："这段日志还要不要留"是判断题不是作文题。为了回答它调用一次大模型读完整上下文、生成解释、再被代码解析，链路太重
2. **摘要会破坏可复核性**：工具结果是后续定位问题的证据（文件路径、错误码、栈信息、命令参数都是精确内容）。对文章/会议纪要是可接受的改写，对代码修复风险更高
3. **置信度没有进入代码分支**：通用大模型可以说"我有 80% 把握"，但通常只是文本自我描述，不一定是校准概率

### 核心约束
**用户文本不改写、助手文本不改写**——用户文本里通常有原始需求和硬约束，助手文本里有已承诺的计划和正在执行的思路，这两类被摘要改写后容易变味。工具结果不同：占空间最大、最容易过期、很多内容可以重新读取或重新执行。所以只处理 tool_use + tool_result 配对。

### 两个 Noul 拆出三种动作
Jev 的核心使用原则是**一个问题只做一个判断**。不要问"这个工具调用和工具结果是否还重要？如果重要请决定是否截断"（混了多个判断），要拆成两个 Noul：
- **keepCall**：这个工具调用本身（连同输入）还重要吗？
- **keepResult**：这个工具结果全文还需要保留吗？

两个概率进入决策树：
| 动作 | 条件 | 处理 |
| --- | --- | --- |
| **keep** | keepResult ≥ 阈值 | 调用和结果都完整保留 |
| **drop_result** | keepResult < 阈值 且 keepCall ≥ 阈值 | 保留调用，截断结果 |
| **drop_call** | 两者都低 | 调用和结果一起删除 |

这个三分法不像 summary 那样改写事实，而是在"留多少"上做选择。

### 工程细节
- **state 构造**：不把完整工具结果发给 Jev，只变成短说明（`ok, 4213 chars (omitted)` / `error, 830 chars (omitted)`）。完整文件内容不进入，只保留工具名和输入；工具输入截断保留；用户文本保留但长文本可能 abridge；最近消息优先保留。**压缩器不需要读完整历史，它只需要知道哪些历史值得继续被读到**
- **fitState 逐级降级**：预算不够时先削弱细节再删除内容，先处理旧消息再处理最近消息——full → inputs≤200 → inputs≤60 → texts abridged → old messages collapsed → old calls compacted → old messages left out → old calls merged。若线上某类会话经常落到 old messages left out，说明不是 Jev 判断问题，而是 state 预算本身太紧
- **pinned 保护**：首条消息和最近 N 条消息不参与删除，避免刚发生的上下文被过早裁掉
- **分批请求**：每个请求都带相同 state，把工具调用问题拆批；可 Promise.all 并发
- **失败回退**：Jev 请求失败→回退到内置 summary 或不压缩；返回格式异常→丢弃本轮压缩；压缩收益不足→保留原 transcript；低置信度→保守保留不激进删除

### 实测结果
修复订单导出超时会话，4 个工具调用被分成三类：list_dir（drop_result，0.54/0.00）/ read_file 含 getAuthToken（keep，0.59/0.69）/ execute_command 测试失败含 authorization header（keep，0.75/1.00）/ 无关 legacy 文件（drop_call，0.47/0.00）。字符数 **10029→852（压缩 91.5%）**，工具调用数 4→3，删除 1 个无关调用，保留关键文件和失败日志。

### 可借鉴的工程模式
**模型可以替换，决策协议要稳定。** 先把接口抽象出来，真实模型只是一个 asker：有 API key 走真实 Jev，没 key 走本地启发式 mock 方便离线演示。这样后面想换官方 Jev、本地复现模型、普通 LLM 适配器，都不需要改主流程。

### 选型对照
| 方案 | 优点 | 缺点 | 适合位置 |
| --- | --- | --- | --- |
| LLM + JSON Schema | 表达能力强，能解释复杂理由 | 仍逐 token 生成，成本和延迟高 | 低频复杂判断 |
| Tool Calling | 能和工具系统集成 | 决策仍依赖生成式模型 | Agent 主流程动作 |
| 传统分类器 | 便宜、可本地部署 | 标签变化不灵活，语义泛化弱 | 稳定标签+大量数据 |
| **Jev** | 输出封闭，概率可用，适合高频 | 不能生成，复杂推理弱 | **高频局部判断** |

判断标准：输出选项能提前枚举吗→Jev；需要自然语言解释→LLM；高频调用→Jev；错误可兜底→Jev；长期稳定且有大量标注→传统分类器；需要跨文件多步推理→不适合 Jev 单独承担。
