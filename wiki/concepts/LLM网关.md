## 定义
LLM 网关（LLM Gateway）是统一管理多个大模型调用的中间层，负责模型路由、负载均衡、自动降级、Token 计费与监控，使业务代码与具体模型厂商解耦。

## 核心能力
- **多模型路由**：按 Agent 类型路由到不同模型（如视觉任务→qwen-vl-max，文本任务→qwen3-max，预测任务→deepseek-v4-flash）
- **多厂商主备**：Qwen / DeepSeek 双厂商，主备切换
- **自动降级**：主模型失败自动切换备模型
- **Token 计费**：每次调用真实记录 Token 消耗，喂给监控大盘
- **零代码切换**：切换模型、调整 Key 无需改动业务代码

## 架构位置
```
业务 Agent → LLM 网关（路由/降级/计费）→ 模型厂商 API
```

编排层（如 AgentScope）不直连大模型，通过适配器复用 LLM 网关的统一能力，实现编排层与模型层彻底解耦。

## 同类实践：客户端侧网关（2026-10-27 补充）
- 企业侧网关（本页主体，Agent 编排层配套）与个人/客户端侧网关（[[Magpie]]）共享同一思想：Agent 不直连模型厂商，在中间层完成路由、降级与用量观测
- magpie 的差异化在**多账号额度调度**：多家供应商同名模型自动组成路由组（`auto/<模型ID>`），请求开始前按额度与重置时间智能排序账号（智能/按顺序/轮流/最少使用/重置前用完五策略），配合 [[会话保持]] 四档不丢 prompt 缓存优势；并支持按 token 长度/是否带图/是否 reasoning/Agent 来源/时段/文件夹分流，检测到死循环时打断该条回复交回可重试错误

## AI Gateway 四大能力全景（2026-11-10，详见 [[摘要-为什么越来越多人用ai-gateway]]）

苏三视角的完整拆解，把"为什么需要网关"讲得最透：

**直接调模型的四大灾难**：① 协议不统一（OpenAI `tool_calls` / Anthropic `tool_use` / Gemini `functionCall`，系统提示位置与流式增量结构各异）② 故障处理零散（各家重试/降级/429 逻辑不一致）③ 成本不可见（多供应商账单格式对不上）④ 安全管控分散（限额/脱敏/审计无法统一）。

**网关对应四能力**：
1. **协议归一化**——业务只说 OpenAI Chat Completions 一种话，网关双向翻译
2. **模型路由**——固定 → 规则 → 成本 → Fallback/熔断 四层次（详见 [[模型路由]]）
3. **虚拟 Key 管理**——应用拿虚拟 Key 调网关，网关映射真实供应商 Key；可单独吊销、追踪各应用成本、设部门预算
4. **可观测性**——**Token 消耗 / 成本归因 / 首 Token 延迟是新的 QPS**，传统按 QPS 限流在 AI 场景近乎无效

**落地方案**：[[LiteLLM]]（最广泛使用的开源 AI Gateway，Thoughtworks 已归入"平台"类别）。

**代价**：多一层多一个故障点（需高可用）、供应商特有功能可能被抹平（`drop_params` 静默丢弃）、自托管有 CVE 运维成本；单模型简单应用属过度设计。
