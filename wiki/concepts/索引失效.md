## 定义
索引失效指 SQL 没有按预期使用索引、转而全表扫描的现象。关键认知：**"失效"多数不是 SQL 写错了，而是 MySQL 优化器估算全表扫描成本更低**（WHERE 查询范围过大、返回结果集过大时优化器主动放弃索引）。真正确定会失效的只有少数几类写法。

## 关键信息

### 必然失效（写法问题）
| 场景 | 根因 | 规避 |
|------|------|------|
| 违反最左匹配 | 联合索引缺首列，后续字段全局散列 | 调整索引列顺序，或按最左前缀建索引 |
| 索引列套函数 | 索引存原始值而非函数计算后的值 | MySQL 8.0 函数索引；或把计算改写为等值 |
| 索引列参与计算 | `b-1=6` 改变了索引值 | 改写为 `b=7`（目前 MySQL 未自动改写） |
| `like '%xx'` 左模糊 | 前缀通配无法二分定位 | 右模糊 `xx%` 走 range；左模糊考虑全文索引/ES |
| OR 两侧仅一侧有索引 | 非索引列导致优化器放弃索引 | 两侧都加索引，或改 UNION |

### 可能失效（优化器选择）
- **`select *`**：会走索引，但辅助索引过滤后仍需回表取全部列，多一次 B+ 树查询。不推荐的真实理由是解析成本、字段变动与 resultMap 不一致、无用字段占网络与 join buffer
- **`in` / `not in`**：一定走索引，但结果集超过约 30% 时优化器改全表扫描
- **`order by`**：MySQL 权衡"走索引 + 回表"与"全表扫描 + filesort"，常选后者——这种情况下全表扫描反而是更优解

### 判断方式
用 `EXPLAIN` 看 key/rows/type：`ref` 与 `range` 级别相差很大，全表扫描时 rows 等于表总行数。

### 与"优化技巧"的正反对照（2026-10-29 补充）
本页记录"哪些写法会失效"，[[索引优化]] 记录"怎么建、怎么写、怎么维护才不失效"，两页互为反面与正面：

| 失效写法 | 对应优化技巧 |
|----------|--------------|
| 索引列套 `DATE()` 等函数 | 改写为区间查询 |
| `phone = 13800000000` 隐式转换 | 加引号 |
| `price * 0.8 > 100` 列参与运算 | 运算移到右侧 |
| `OR` 两侧仅一侧有索引 | 两侧建索引 / 改 `IN`、`UNION` |
| 违反最左匹配 | 等值列在左、范围列在右 |
| 低选择性列单独建索引 | 放到联合索引末尾 |
| `like '%xx'` 左模糊 | 右模糊 / 全文检索 |

另有一个容易搞混的点：**ICP（[[索引下推]]）不是让"失效"变"有效"**，而是让范围截断后剩下的索引列在索引层先过滤，减少回表次数——`Extra` 显示 `Using index condition`。
