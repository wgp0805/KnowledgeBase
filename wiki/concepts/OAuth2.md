## 定义
OAuth2 是一种三方授权协议，允许用户在不提供账号密码的情况下，通过信任的应用进行授权，使其客户端可以访问权限范围内的资源。**OAuth2 是授权协议不是认证协议**——它只告诉服务端"客户端被允许访问哪些资源"，本身不提供任何用户信息。

## 核心模型：四角色
| 角色 | 职责 |
|------|------|
| **Resource Owner**（资源拥有者） | 拥有该资源的最终用户，有访问资源的账号密码 |
| **Resource Server**（资源服务器） | 受保护资源所在服务器，正确访问令牌即可访问 |
| **Client**（客户端） | 请求访问资源的客户端，携带访问令牌访问资源 |
| **Authorization Server**（认证服务器） | 负责认证客户端身份，认证成功后发放访问令牌 |

## 关键信息

### 三大特点
- **简单**：服务提供者与应用开发者都易于理解与使用
- **安全**：不涉及用户密钥等信息，更安全更灵活
- **开放**：任何服务提供商都可实现，任何开发商都可使用

### 三大应用场景
1. **原生 app 授权**：app 登录请求后台接口，所有请求带 token 信息
2. **前后端分离单页面应用**：前端请求后台数据，需要 OAuth2 安全认证
3. **第三方应用授权登录**：QQ、微博、微信、GitHub 等

### 四大授权模式
任何模式申请令牌前，第三方应用都必须先到系统备案说明身份，获取两个身份识别码：`client_id` 和 `client_secret`。

| 模式 | 流程 | 适用场景 |
|------|------|----------|
| **Authorization Code（授权码）** | 用户→认证服务器→授权码→后端换令牌 | 正宗模式，最安全，客户端-后端分离 |
| **Implicit（隐藏式）** | 直接拿访问令牌，跳过授权码 | SPA 无后端场景 |
| **Password（密码）** | 客户端直接拿用户名密码换令牌 | 仅高信任场景 |
| **Client Credentials（客户端凭证）** | 仅 client_id+secret 换令牌，无需用户授权 | 服务间调用 |

### 授权码模式详细流程（最常用）
1. 客户端将用户导向认证服务器的授权页面
2. 用户在认证服务器页面登录并授权
3. 认证服务器返回授权码给客户端（GitHub code 10 分钟过期，QQ 也是 10 分钟）
4. 客户端将授权码传递给后端服务
5. 后端服务用授权码请求认证服务器获取令牌
6. 令牌返回给客户端

### 优缺点
**优点**：
- 客户端不接触用户密码，服务器端更易集中保护
- 广泛传播并被持续采用
- 短寿命和封装的 token
- 资源服务器和授权服务器解耦
- 集中式授权，简化客户端
- HTTP/JSON 友好，易于请求和传递 token
- 考虑多种客户端架构场景
- 客户可以具有不同的信任级别

**缺点**：
- 协议框架太宽泛，各种实现的兼容性和互操作性差
- 不是一个认证协议，本身并不能告诉你任何用户信息

### 三方登录数据库设计三方案
| 方案 | 描述 | 适用场景 |
|------|------|----------|
| **直接注册到 user 表** | 授权成功后把第三方用户信息注册到本站 user 表（密码后端自动生成用户不知） | 无注册功能/简单场景 |
| **增加映射表** | QQ、手机号、邮箱等都映射到本站注册的 id，查映射关系找到注册 id 登录 | 多登录方式并存 |
| **建立独立 oauth 表** | 一对一多关系，每个第三方 openid 一列，用户表 + 授权信息表分离 | 最规范，推荐 |

### 实战示例：GitHub OAuth 登录
- **三个核心 URL**：
  - `https://github.com/login/oauth/authorize` — 认证服务器
  - `https://github.com/login/oauth/access_token` — 令牌服务器
  - `https://api.github.com/user` — 资源服务器
- **配置项**：`clientId` / `clientSecret` / `directUrl`（回调地址）
- **流程**：
  1. 后端生成 state 存入内存（防 CSRF）
  2. 重定向到 GitHub 授权页面
  3. GitHub 重定向回本站，携带 code 和 state
  4. 校验 state 匹配则继续
  5. POST code + client_id + client_secret 换 access_token
  6. GET /user 携带 token 获取用户信息

### 实战示例：QQ OAuth 登录
- **四个核心 URL**：
  - `https://graph.qq.com/oauth2.0/authorize` — 授权请求
  - `https://graph.qq.com/oauth2.0/token` — 换 token（有效期 30 天）
  - `https://graph.qq.com/oauth2.0/me` — 获取 openid
  - `https://graph.qq.com/user/get_user_info` — 获取用户信息
- **注意事项**：
  - 需要实名认证
  - 需要备案域名
  - code 有效期 10 分钟
  - Token 有效期 30 天，用户再次登录时自动刷新
  - 参数需带 `fmt=json` 才能返回 JSON 格式

### CSRF 防护（关键安全机制）
- **state 参数机制**：生成随机 state 值，回调时校验一致性，防止 CSRF 攻击
- **state 生命周期**：生成 → 存入内存 Set/Redis → 回调校验 → 立即删除（防重放）
- **不能省略**：忽略 state 参数可能导致 CSRF 攻击
