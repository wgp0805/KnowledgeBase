## 定义

热 key 探测是在突发流量把某个 key 打热**之前**，用独立集群实时计数、毫秒级判定并主动推送判定结果到应用服务器本地内存的机制。核心论断：**热 key 是"突发"的，不是"预设"的；热 key 的核心矛盾不是"缓存"，是"探测"**——一个普通商品可能因主播一句话或平台一个推送，几秒内变成爆款；不可能提前给几百万个 key 全配本地缓存（内存放不下），你得先知道谁热了，才能决定把谁推到本地内存。

## 关键信息

- **范式转变**：把热 key 的应对从"事后看监控才发现 Redis 扛不住"，变成"事前毫秒级判定并推到各机 JVM"——这是热 key 问题从被动救火到主动兜底的分界线
- **探测与缓存解耦**：探测框架只判定"热不热"并推送，**value 由业务方自取自存**（isHotKey 返回 true → 查 Redis 一次 → smartSet 进本地缓存）；框架不替你管数据，同一套判定可复用于本地缓存、限流、熔断、黑名单
- **分布式滑动窗口计数**：Client 攒批上报（默认 500ms）→ Worker 滑动窗口计数（阈值规则如"2 秒内 20 次算热"）→ 命中后长连接推送到订阅应用**所有**实例，保证集群判定一致（不会 A 机认为热、B 机不热）
- **成本账**：独立探测集群（1 台 Worker 撑 1000 台业务服务器）远比扩容 Redis 集群便宜；探测本身是"轻量集群 + jar 包"，不依赖也不改造 Redis
- **落地效果**：京东大促实测，探测出的热 key 本地缓存承接应用总访问量 50%+，Redis 层压力减半以上；探测集群自身 30 万 QPS 量级（protobuf 后 36 万+）
- **开源典型实现**：[[JD-hotkey]]（京东，Gitee 开源，2020 年 618/双 11 验证）
