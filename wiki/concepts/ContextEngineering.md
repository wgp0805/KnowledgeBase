## 定义
上下文工程（Context Engineering）是 2025 年 RAG 领域最重要的认知转变——RAG 的本质不是"检索增强生成"，而是"上下文工程"。核心关注点从"怎么检索到相关文档"升级为"怎么为模型构造最合适的上下文"。

## 关键信息

### 认知升级
- **旧视角**：RAG = 检索 + 拼接 + 生成，重点是检索质量
- **新视角**：RAG = 上下文工程，重点是构造最合适的上下文

### 上下文工程的核心关注点
1. **选取**：从大量候选文档中选取最相关的内容
2. **排序**：按重要性排列上下文中的信息
3. **压缩**：去除冗余，精炼上下文长度
4. **冲突处理**：当检索到的文档之间存在矛盾信息时如何处理

### 与 Prompt Engineering 的区别
- Prompt Engineering 关注指令措辞
- Context Engineering 关注给模型"看什么内容"，是更底层的工程问题

### 实践意义
- 单纯优化检索召回率已不够，需要端到端地优化上下文质量
- Rerank、压缩、去重、冲突消解都是上下文工程的子问题

### pi-agent 的两大上下文解决方案（源自 [[PiAgent]]）
1. **工具输出截断机制**：文件读取、命令行执行类工具返回超长文本会瞬间占满 Token 上限。对返回内容按字符/字节截断（保留首尾关键信息），完整原始数据本地持久化，仅将「截断摘要 + 本地文件路径」传入上下文，由模型自主判断是否读取完整文件。
2. **阈值驱动上下文自动压缩**：实时计算上下文占用，剩余 Token 低于阈值时自动启动压缩（详见 [[context-compression]]）。优化技巧：上一轮任务结束后提前预判压缩，避免新一轮请求开始时卡顿。压缩按结构化模板提炼（用户目标/约束条件/工作流程/历史决策/下一步计划），替换早期历史对话。
3. **提示词顺序编排**：固定系统提示词前置、减少前缀频繁变动，提升模型缓存命中率。

### 长对话收口（2026-09-19，详见 [[摘要-工作记忆vs长期记忆上下文工程]]）
- 大模型本身没有记忆，唯一能"想起来"的是当前窗口里那几万 token 的上下文
- "长对话先收口、再开新对话"是有理论支撑的方法论——上下文工程
- 相关术语：[[ContextRot]]（上下文腐烂）、[[Lost-in-the-Middle]]（中间迷失）
- 收口收三样：决策、关键事实/结论、下一步

### 游戏开发中的上下文工程：为什么 LLM 读不懂游戏（2026-10-15，详见 [[摘要-你的游戏本身就是Harness]]）
- **上下文膨胀的物理机制**：一次提示词调用可拆为系统提示词 / 助手提示词 / 用户提示词；会话中**此前发送过的每一条历史消息都会在发新消息时被完整重新提交给模型**（接龙式重放）。因此你真正能直接干预的永远只有"最新"那一条消息。
- **[[上下文污染]]**：前期产生的错误尝试、幻觉代码、无效日志会持续误导后续所有推理，导致生成质量断崖式崩塌。上下文工程的核心灵魂因此可概括为：**"我们如何以最低限度的污染，把最精准、最有效的高质量信息注入上下文中？"**
- **像素级污染案例**：直接把修改前后两张大图丢给多模态模型，无关像素构成纯粹噪点，模型极难识别细微改动——必须改用 [[图像差分]]（只呈现真正的像素差异 + 量化相似度数值）。
- **领域化结论**：LLM 在 Web 上近乎无所不能、在游戏上几乎必定翻车，**本质是上下文工程问题**，而非模型或领域的先天缺陷。解法是把被改造对象本身做成 Harness，让内部状态对模型透明可寻址，详见 [[HarnessEngineering]] 与 [[Agent迭代飞轮]]。
