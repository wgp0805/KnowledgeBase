## 定义
分布式会话是一种将会话数据存储在外部共享存储（如 Redis）中的会话管理方案，解决单机内存会话在集群环境下的状态不一致问题。

## 关键信息
### 为什么需要分布式会话
- **单机问题**：会话数据存放在 JVM 内存，重启丢失，集群节点间不共享
- **集群痛点**：用户登录请求落在节点 A，下次请求落在节点 B，节点 B 找不到会话返回 401
- **高可用需求**：应用重启后会话依然有效，增加节点不影响会话一致性

### 解决方案
- **接入 Redis**：将会话数据存储在 Redis 中，实现多节点共享
- **Sa-Token 集成**：引入 `sa-token-redis` 依赖即可
- **配置简单**：只需添加依赖，无需复杂配置

### 核心优势
- **登录态多节点共享**：用户在任意节点登录，所有节点都能识别
- **水平扩展能力**：增加节点不影响会话一致性
- **重启不丢数据**：应用重启，Redis 里的会话依然有效
- **统一管理**：会话数据集中存储，便于管理和监控

### 实现要点
- **存储层抽象**：Sa-Token 默认存在内存，可切换到 Redis
- **可插拔设计**：存储层通过接口解耦，支持多种实现
- **分布式锁**：结合 Redisson 实现分布式锁，防止并发问题

### 四种方案对比（2026-10-04，详见 [[摘要-分布式session实现难点]]）
微服务 + Nginx 轮询负载均衡下，用户在 Tomcat1 登录、请求被分到 Tomcat2 导致频繁重新登录。四种解法权衡：
| 方案 | 优点 | 缺点 |
|------|------|------|
| Session 复制 | 无需改代码，只改 Tomcat 配置 | 同步传输占内网带宽；多台同步性能指数级下降；占内存无法有效水平扩展 |
| 前端存储（Cookie） | 不占服务器内存 | 安全风险；数据大小受 cookie 限制；占外网带宽 |
| Session 粘滞（Sticky） | 无需改代码；服务端可水平扩展 | 新增机器重新 Hash 导致重新登录；应用重启后需重新登录 |
| 后端集中存储 | 安全；容易水平扩展 | 增加复杂度；需要改代码 |

**Java 落地两条路径**：
1. **[[SpringSession]] + Redis**：引入 spring-boot-starter-data-redis、commons-pool2、spring-session-data-redis 依赖并配置连接池，`request.getSession().setAttribute(ticket, user)` 自动写入 Redis，业务代码无感
2. **RedisTemplate 手工存取**：UUID 生成 ticket 写入 `user:{ticket}` 键并下发 Cookie，读取时按 ticket 从 Redis 取用户——灵活但侵入业务代码
