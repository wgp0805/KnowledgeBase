# 审批设计

## 核心定义
Agent 执行敏感动作时的审批机制设计。核心原则：审批按钮必须提供足够信息让用户在点击前看懂动作内容和影响范围，不能只有"允许/拒绝"。

## 审批信息要素
- 准备修改哪个文件
- 命令会在什么目录运行
- 是否可能访问网络
- 失败后是否留下中间状态
- 当前权限范围和需要扩大的范围
- 执行结束后权限是否恢复

## 常见问题
1. **审批疲劳**：所有风险都压到审批框，用户反复确认后形成无条件放行习惯，审批失去判断价值
2. **信息不足**：只有"允许/拒绝"两个按钮，用户无法判断后果
3. **笼统开关**：权限只分"可用/不可用"，不区分读取、写入、启动进程、访问网络的不同风险

## 更稳妥的做法
- 先按任务建立默认范围（日常代码检查只读指定工作区，修改限制在明确目录）
- 网络访问和工作区外写入单独确认
- 审批落到当次后果，不是笼统开关
- 一次性授权结束后给出结果（命令是否真的执行、使用了哪种范围、有无文件变化）

## DeepSeek Harness 的实践
- `workspace-write`：文件影响限制在工作区，需要时询问
- `danger-full-access`：允许更大范围，可配置不逐次询问
- 提权由已发生的具体拒绝触发，Agent 不应预先要求最高权限
- 遇到沙箱拒绝后可在同一轮用最小必要权限重试一次并提供理由

### 四状态审批与「失败即拒绝」（2026-11-26，详见 [[摘要-deepseek防提示词注入]]）

[[DeepSeekHarness|DSH]] 的审批结果一共**四个明确状态**，工具只有拿到**单次放行**（`allowed-once`）才会真正执行——不存在「放行一次就长期记住」的模糊态。这条约束的意义在于：把「这次批准」与「以后都批准」彻底分开，避免一次误点变成永久开口。

配套三条工程约束：

- **审批通道断开、抛异常、或系统处于无人值守模式，一律按拒绝处理**——失败方向取安全侧，不做「连不上就默认允许」的降级
- **先读后改**：会话里**没读取过的文件，不允许直接修改和覆盖**。这把「盲改」变成必须先建立观察，间接要求 Agent 在看到内容后才能动手
- **`medium` 级操作必须拿到「当前用户」的明确授权**——父级 Agent 或上游编排者的指令不能替代最终用户的批准（详见 [[自动审查模式]] 的三级分类）

这与上文「提权由已发生的具体拒绝触发」是同一设计哲学的两个面：**权限从窄处起步，向宽处只能由具体事件和具体人推动**。
