## 定义
LLM Wiki 是 Andrej Karpathy 于 2026 年初提出的一种知识库组织模式：把碎片化信息编译成结构化、高度相互链接的 Wiki 式知识库，使知识既可供人类阅读，也可供 LLM/Agent 高效读取、维护与交换。**[[OpenWiki]] 是这个理念的第一个完整工程实现**——LangChain 照着这套思路做出来的 CLI 工具，把代码库「编译」成一套 Agent 可以快速查阅的 Wiki，让 Agent 不用每次都从头翻代码。

## 关键信息
- **核心思想**：知识以「人能打开、能审查、能版本管理、能迁移的文件」形式存在，而不是锁在某个向量数据库/Agent 框架/模型 Memory 里
- **与 OKF 的关系**：OKF 把 LLM Wiki 模式正式定义成开放、厂商中立、可移植的知识格式标准；LLM Wiki 是 OKF 的前身模式
- **实践形态**：本仓库（wiki/ 编译输出层 + raw/ 不可变层）即 LLM Wiki 的具体实践
- **双向链接**：页面之间通过 [[wikilink]] 强制相互连接，杜绝孤岛页面
- **可验证性**：知识附带来源、状态、时效性，使 Agent 在使用知识前能判断是否值得相信；工程实现见 [[Claims溯源]]
- **解决的核心痛点**：AI 编程工具的「短期记忆」够了但「长期记忆」没有——每次任务都是全新开始，之前积累的理解完全浪费，你花时间让 AI 理解的项目架构，下个任务它完全不记得
- **设计原则反直觉**：为 Agent 写文档不是为人写文档。传统项目文档是给人看的，人类能容忍模糊、能脑补上下文；但 Agent 上下文窗口有限，每行无用信息都在消耗 Token，所以输出应是针对 LLM 上下文优化的结构化 Markdown，而非人类喜欢的叙事铺垫和背景介绍
- **一句话总结**：**RAG 让 AI 帮你找答案，OpenWiki 让 AI 记住你的项目**（详见 [[编译器模式vs解释器模式]]）
- **WorkBuddy + Obsidian 平民实现**（来自 [[摘要-workbuddy-obsidian-知识库]]）：苏三 2026-09-16 分享的保姆级教程——用 WorkBuddy + Obsidian 搭建自生长个人知识库，三层极简目录（raw 只读 / wiki 沉淀 / output 临时）+ AGENTS.md 宪法 + 每次入库更新 index.md 和 log.md。进阶可接入开源的 `claude-obsidian` 工具链，命令包括 `init` / `adopt` / `wiki-ingest` / `wiki-query` / `wiki-lint`。**两种方案选型**：日常阅读笔记 → 提示词直建法（轻量易掌控）；数万字以上复杂项目文档 → 工作流模块（有校验工具兜底）
- **三层架构落地版**（来自 [[摘要-llm-wiki-实战管理数字分身]]，详见 [[LLMWiki分层架构]]）：原始数据层（Raw，只读不可变）→ 规则约束层（Schema，AGENTS.md/CLAUDE.md）→ 知识编译层（Wiki，摘要/实体/概念/比较/概述/综合理解）。人机分工：人定规则、供原始数据、做价值审核与关键裁决，LLM 负责知识编译层维护更新
- **编译 vs 检索 vs 治理**（同上，详见 [[知识编译]]）：核心理念「预先编译，持续更新，反复复用」；检索侧是渐进式下钻——先搜索引与摘要定位页面 → 打开页面读全文 → 顺着关联页继续查 → 需要精确引用时回原始文档 → 来源冲突时比较时间、范围与出处
- **不是银弹**（同上）：LLM Wiki 是**编译时产物**，RAG 是**运行时手段**，两者互补。知识体量大起来后 `index.md` 会持续膨胀、检索与编译 Token 消耗同步变大、增量更新质量下降，需要用 BM25 + 向量重排的混合检索兜底
- **人的判断权不可外包**（同上）：LLM 并不知道哪些信息真的重要、哪些结论值得保留、哪些内容应该被丢弃，甚至会丢掉关键细节或生效条件。**信息筛选**与**知识编译**两个环节必须有人参与审核；Karpathy 本人也是倾向单篇知识摄入并全程参与
