## 定义

围绕推理引擎的**前缀缓存（Prefix Caching）**做上下文布局设计：把系统提示词按**稳定度从高到低**排列，把每轮都会变的内容全部推到最末尾，从而让会话期间的最长公共前缀尽量逐字节不变，命中缓存。

## 关键信息

### 为什么必须这么做
推理引擎的前缀缓存是**按词元序列从头往后做严格前缀匹配**的，中间只要改了一个字符，后面的 KV Cache 就全部失效。

### PaiCLI 的 9 层系统提示词组装规则
按稳定度从高到低排列：
1. **最前（永不改变）**：基础规则、人格、执行模式、审批规范、上下文管理指令、收尾指令
2. **中间（启停时变化 / 按天变化）**：Skills 索引、运行时日期
3. **最末（每轮动态变化）**：按用户每一轮提问动态检索出来的项目上下文与长期记忆

另外两条配套规则：
- **工具注册表导出 Schema 时按工具名称字典序固定排序**——保证前缀稳定
- **运行中按需加载的 Skill 正文作为同轮独立的 user 消息追加在对话尾部**，不去改动顶层 system 提示词

### 量化收益
根据 NVIDIA 对多轮编码 Agent 流量的实测数据：**保持前缀逐字节稳定能让多轮会话的 KV 缓存命中率达到 85% 到 97%，首字延迟降低约 5 倍，输入 Token 成本也能省下大半。**

### 与动态工具发现的呼应
同一篇分享里，Grok Bot 的做法是「工具定义、系统提示在不同调用之间保持不变」并强调「缓存没命中，其实就是系统里的一个 bug」——见 [[动态工具发现]]。

### 与模型侧优化的分工
缓存是应用侧手段，模型侧还有 [[HySparse2]] 这类架构级 KV 压缩；两者叠加才是完整的显存/成本治理路线，参见 [[KV Cache]]。

### 根节点机制与时间戳降级（2026-10-29，详见 [[摘要-为什么不能在System-Prompt里放时间戳]]）
沉默王二从**为什么不能放时间戳**切入，补足根节点命中的机制细节与三家 Harness 的降级策略：
- **根节点机制**：推理引擎把输入 Token 按固定块算出哈希值挂到 **Radix Tree 前缀树**上复用，命中规则从第 `0` 号 Token 开始逐块匹配。Agent 发给模型的顺序是「系统提示词→工具定义→历史对话→最新提问」，系统提示词位于前缀树**根节点**——一旦混入每秒变化的数字，根节点哈希块就改变，排在后面的工具定义和历史对话全部失联，每一轮都要重新 Prefill。
- **系统/用户提示词分工**：系统提示词只放不变的全局指令，随项目和会话变化的信息统一放进带 `<system-reminder>` 标签的第一条用户消息（答案 B 原则）。
- **日期降级**：日期从秒级降级到**按天/按月**——Claude Code 砍掉时分秒只保留年月日、会话启动时 `memoize` 一次塞进第一条 `<system-reminder>`；联网搜索工具提示词只放当前年月，一个月才更新一次缓存。
- **跨天/规则变更追加**：跨天时保留第一条消息旧日期不动，只在对话末尾追加一条新消息（Claude Code 追加 `<system-reminder>`，Codex 在用户消息环境信息里每轮对比、跨天才追加）；改 `AGENTS.md` 只往对话末尾追加用户消息。
- **DeepSeek Harness 的 in-history 模式**：系统提示词分段排序（身份说明最前、工具说明中间、易变本地路径最后）并存为消息列表第 `0` 号节点；支持 `in-history` 模式时，中途切 Plan 模式不改写 `0` 号节点，而是在已缓存历史末尾追加一条新的 `system` 消息（以最新一条为准，直到上下文压缩才合并回 `0` 号节点）。
- **量化**：Manus 团队公开——对话型 Agent 输入输出比约 `1:1`，长程任务 Agent 高达 `100:1`；主流模型缓存读取价格只有未命中的 `1/10`，放秒级时间戳会让账单贵 **10 倍**。
