## 定义

**git 一个冲突都不报，但 merge 到一起运行起来就有问题**的那一类冲突。根因是各 Agent 基于不同的代码基线做出假设，而这些假设的失效点在**不同的文件**里，版本控制系统无从检测。

## 关键信息

### 典型案例
Agent 张三把一个函数的返回值从字符串改成了对象。Agent 李四在另一个 worktree 里没看到这个改动，照着旧的返回值类型写了一段函数调用代码。

合并的时候：
- 这两处改动**在不同的文件里**
- git **一个冲突都不报**
- 但 merge 到一起之后，运行起来就有问题了

### 与文本冲突的对比
| 类型 | 触发条件 | 检测手段 | 后果 |
|---|---|---|---|
| 文本冲突 | 同一文件同一区域被两个 Agent 改动 | git 三方合并直接报冲突 | 合并时暴露，需人工解决 |
| **语义冲突** | 同一**契约**（函数签名、返回类型、接口约定、数据格式）被不同 Agent 在不同文件里分别改动 | **无自动检测手段** | **运行时才暴露** |

### 启示
无论是空间隔离（[[Worktree]]）还是时间串行（[[Agent并发写冲突]] 中的 Pi 队列），都**只能管住单个工具层面的文本写入**——它们防的是「同一处字节被覆盖」，防不了「不同文件之间契约不一致」。

> 补充：Claude Code 的 worktree 只是把冲突**延迟到合并那一步**，git 该报冲突还是会报；Pi 的队列连跨进程都看不见。这两类都是文本冲突层面的问题，语义冲突在两者之外。

### 实践含义
多 Agent 并行改同一仓库时，除了「别让两个 Agent 同时碰同一个文件」，还要**约定跨 Agent 的契约边界**（函数签名、接口、数据结构变更需要串行或显式广播），否则合并后才会发现运行时错误。
