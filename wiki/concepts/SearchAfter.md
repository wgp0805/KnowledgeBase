## 定义
Elasticsearch 的游标式实时翻页方案。思路：记住上一页最后一条的排序位置，下一页直接从那个位置往后取，避免 `from + size` 在深翻页时协调节点做归并排序。

## 关键信息

### 原理
- 第一页正常查，不用 `from`，只要 `size` + `sort`
- 把上一页最后一条的排序值数组塞进下一页的 `search_after` 参数
- 各分片直接定位到该排序值之后取 N 条，协调节点只处理几十条数据
- 不管翻到第 10 页还是第 10 万页，单次查询开销基本恒定

### 完整示例
```
POST /order/_search
{
  "size": 10,
  "search_after": [1699999999999, "order_10086"],
  "sort": [
    { "create_time": "desc" },
    { "_id": "asc" }
  ]
}
```

### 唯一性要求（关键）
**排序字段组合起来必须能唯一确定一条文档**。
- 如果只按 `create_time` 排序，同一秒可能有几百条订单，分片边界上无法判断从哪条开始，会漏数据或返回重复
- 标准做法：业务字段 + `_id` 做第二排序键兜底
- 这是面试官爱追问的点

### 短板
- **不能跳页**：只能一页一页往后翻
- **翻页过程中数据可能变化**：翻页时有人删了中间的数据，后续页可能漏数据
- **解决方案**：搭配 [[PIT]]（Point in Time）创建轻量级视图，保证整个翻页过程数据视图一致

### scroll vs search_after 核心区别
| 维度 | scroll | search_after |
|------|--------|--------------|
| 模型 | 快照模型，上下文固化结果集 | 无状态游标模型，每次查最新数据 |
| 实时性 | 非实时（快照冻结） | 实时 |
| 一致性 | 翻页过程数据一致 | 不保证一致性 |
| 适合场景 | 离线导出 | 实时深度翻页 |
| 资源占用 | 维护搜索上下文占堆内存 | 无状态不占资源 |

### ES 7.10+ 官方推荐
**PIT + search_after**：兼顾一致性和深分页的当前最佳实践。
