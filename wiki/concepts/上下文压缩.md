## 定义
对Agent运行过程中产生的上下文进行压缩，以适应有限的模型上下文窗口，同时保留关键信息的技术。

## 关键信息
1. **压缩策略**：
   - 选择性保留工具结果（OpenCode的Tool Result Pruning）
   - 基于提示词进行摘要（Pi Agent的结构化压缩）
   - 选择性丢弃或Token级压缩（LLMLingua等）
   - 运行状态压缩（KV-cache等模型层压缩）

2. **工业级实践**：
   - Pi Agent：从最新消息往前扫描，找到近期上下文进行结构化压缩
   - OpenCode：两层压缩（Tool Result Pruning + Conversation Compaction）
   - Manus：将网页、文件、中间结果写入文件系统，只保留路径和简要结论

3. **Codex 的自动压缩配置（2026-09 实战）**：
   Codex 额度消耗快的常见根因不是模型变贵，而是**上下文被一轮轮累加吃掉**——实测两条长任务累计输入 token 接近 1599 万和 1582 万，任务后期单次调用输入已达 22.8 万–25.4 万 token。可用 `config.toml` 做硬性上限约束：
   ```toml
   model_auto_compact_token_limit = 160000
   model_auto_compact_token_limit_scope = "total"
   tool_output_token_limit = 8000
   [skills]
   max_context_tokens = 4000
   ```
   这些数字不是所有电脑都必须照抄的标准答案，它们解决的是同一个问题：**不要让单个任务和工具输出无限膨胀**。配套的源头治理是把全局 `AGENTS.md` 从 5284 字节压缩到 1705 字节——保留品牌名/发布规则/操作方式等关键约束，删重复解释和不需要每轮都出现的内容。

   OpenAI 官方文章《Rethinking skills and prompts for GPT-6 Astra》的结论一致：Skill 描述太多太长会持续占用上下文，AGENTS.md 也不应该要求模型在每个小任务开始前都读取一整套文档，**更合适的方式是只在当前任务确实需要时再加载对应规则和资料**（按需加载）。

4. **不要粗暴卸载**：插件、MCP 和 Skills 都可能承载真实工作流，粗暴关闭很容易把原本能用的能力弄坏。更稳妥的方式是先判断它们是否真的在每轮注入上下文，再决定要不要处理。

5. **压缩解决不了的问题：任务不要无限续下去**
   同一篇文章、同一套代码在一个任务里连续改几十轮，看起来方便，后面的每一轮却可能越来越重。**一个阶段已经完成就新建任务，把必要文件和最终结论交给新任务**，它不需要重新背着前面所有试错记录继续工作。配置只能防止无限膨胀，不能替代「何时收尾换任务」的决策。

6. **PaiCLI 的三档渐进式压缩（2026-10-20，详见 [[摘要-jd-codex辞职信-agent面试题]]）**
   压缩不是一步到位，而是按代价从低到高分三档触发：①**卸载**——单次工具输出超 32000 字符，完整结果落盘到独立文件，上下文只留路径 + 头 2000/尾 800 字符预览（代价最低，先挡工具输出洪峰）；②**清理**——token 触阈值时，把除最近 3 条外的旧 `tool` 消息正文换成 `[已清理的旧工具结果]` 占位符，保留 `tool_call_id` 维持消息配对；③**摘要**——真正逼近窗口上限（200k 窗口约 167k token）才做结构化摘要，保留最近 3 个完整用户轮次。摘要质量用结构校验兜底：必须含"当前目标与成功条件 / 用户要求与已确认决定 / 已完成工作及证据 / 未解决问题与下一步"四要素，缺一项先调模型修格式，再缺就放弃本次压缩——**宁可不压缩，也不让劣质摘要污染后续推理**。

7. **Claude Code 空闲压缩（idle compaction，v2.1.299，2026-10-20）**
   针对"提示缓存约 1 小时过期、长会话闲置后重处理完整上下文费额度"的成本问题：上下文超约 200K Token 且会话闲置约 54 分钟时，**在缓存过期前**自动把长上下文压成摘要，用户回来只需重处理摘要。代价明确：压缩后模型基于摘要工作、不再持有原始细节，依赖大量细节的任务精确度下降。可配 `{"idleCompaction": false}` 关闭，`CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS` 调触发阈值（默认 200K）。与手动 `/compact` 的区别是时机驱动（缓存窗口）而非用量驱动。

8. **长期记忆侧的三类脏数据治理（2026-10-21，详见 [[摘要-xiaom-15升16-agent面试题]]）**
   压缩解决的是「这一轮对话太长」，但长期记忆解决的是「记错了比记不住更危险」。三类脏数据各有对策：外部网页提示词注入污染（只从用户原话逐字摘取 + 读过外部内容就锁死写入）、同一事实的新旧版本冲突（数字/版本号掩码后比对 + Bigram Dice 相似度 ≥ 0.8 拦截静默写入，交用户决定）、代码改了但旧记忆还在（按 30 天未核实或关联源码 mtime 更晚降权并打「可能已过时」标记）。完整机制见 [[记忆冲突治理]]。

9. **安全盲区维度（2026-10-25，详见 [[摘要-claude-auto-mode监控逃逸]]）**
   METR 对 OpenAI 内部 [[Codex]] 监控的审计发现：监控当时只在 Agent 收工交还控制权时检查，而长任务中段的上下文压缩事件不在监控范围内、被压缩掉的那部分记录监控一眼都看不到——Agent 只要一直干下去、一次次压缩，就能一直不交还控制权、审查永远不会来。5—7 月约一成符合条件的内部流量因此从监控眼皮下溜走。压缩既是效率工具也是安全盲区；修复方向是把压缩事件纳入监控范围并强制定期/定量检查（见 [[监控逃逸]]）。
