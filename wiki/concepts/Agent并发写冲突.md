## 定义

多个 Agent 并行修改同一仓库时如何避免相互覆盖的问题。当前有两条主线：**Claude Code 用空间换安全，Pi 用时间换安全**——但两种做法都只管住了单个工具层面的文本写入，**管不住跨进程覆盖和代码逻辑层面的语义冲突**。

## 关键信息

### 路线一：空间隔离（Claude Code 的 worktree）
- 启动加 `--worktree <名字>` → 在 `.claude/worktrees/` 下建独立工作目录、切 `worktree-<名字>` 分支
- 该目录由 git worktree 出来，有自己的文件与分支，**和主仓库共享同一份提交历史**
- Sub-agent 在 frontmatter 里加 `isolation: worktree` 即可获得隔离；无改动时自动清理目录

**光建目录不够**——Agent 完全可以用一条绝对路径把文件写回主仓库，所以 Claude Code 加了四道检查：

| 检查 | 规则 |
|---|---|
| ① 文件编辑 | Edit / Write / NotebookEdit 的目标路径落在主仓库里 → 直接拒绝 |
| ② 命令在哪里执行 | Bash 命令在主仓库里执行 → 拒绝 |
| ③ git 重定向 | 用 `git -C`、`--git-dir` 把 git 指回主仓库 → 拒绝 |
| ④ 命令形态 | 无法确认里面的 git 会留在 worktree 里（如命令名是运行时算出来的）→ 拒绝 |

**明确的漏洞**（官方文档也写了）：这些检查看的是**编辑的目标路径、命令在哪里执行、命令文本本身**，**没有跟踪 shell 命令实际写入了哪些文件**——用 `cp` 或重定向把内容往主仓库里写，这几道检查拦不住。

> 一句话：**Claude Code 没有解决冲突，它只是让冲突暂时不可能发生。**

### 路线二：时间串行（Pi 的文件变更队列）
- 多个 session **共享同一个工作目录**，没有文件系统隔离，命令行参数表里也没有 worktree 相关开关
- 内部有一个**文件变更队列**，实现为**模块级 Map**：同一文件上的写入操作串成 Promise 链，前一个做完才轮到下一个，不同文件可并行
- 队列 key **先做一次路径解析、再做一次真实路径解析**——两个软链接指向同一个文件也会排进同一个队列
- edit 工具把「检查文件是否存在 → 读取当前内容 → 匹配 oldText → 写回结果」**四步全部放在队列里完成**

**漏洞：bash 工具没有引用它。** 模型用 `sed` 改写文件、用重定向写文件、执行 prettier 格式化都不排队，甚至和同进程的 edit 也不互斥。

### 两种做法各自漏掉的

**Pi 的跨进程盲区**
- 队列是模块级 Map，只在同一进程内共享——两个终端各开一个 pi 指向同一仓库，**内存里根本看不见对方**，后写的仍会直接覆盖先写的，**没有任何提示**
- `write` 工具的实现里**连读都不读**，建好父目录就把内容写进去，**无条件覆盖**
- `edit` 工具看起来安全一点（要求 oldText 能匹配上），但这是**文本匹配的副产物，不是版本校验**：
  - 外部改动恰好落在 oldText 覆盖的那几行 → 匹配失败，报错是「找不到要替换的文本」，模型只会当成自己的 oldText 写错了，意识不到文件已被其他 Agent 改过
  - 外部改动落在 oldText 以外 → 匹配照样成功，两边基于不同基线各改各的，结果**静默写回**，双方的改动都会生效

**Claude Code 的延迟冲突**
worktree 把冲突**延迟到了合并那一步**——git 该报冲突还是会报，只不过需要人来处理。

### 实践建议
先把任务**按目录分好**，别让两个 Agent 同时碰同一个文件；真要碰，就**串行**，一个改完另一个再上。
