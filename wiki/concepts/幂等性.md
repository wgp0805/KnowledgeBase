## 定义
同一操作执行一次与多次效果相同。网络抖动、用户手抖、MQ 重试、客户端超时重发都会产生重复请求；幂等性是把"重复"从业务灾难降级为无害的行为。它是消息重试、表单重复提交、分布式协调共同依赖的性质。

## 关键信息

### 为什么必须做：重复请求的三种来源
| 来源 | 典型场景 | 后果 |
|------|----------|------|
| 用户行为 | 连点提交按钮、刷新重发 | 重复建单 |
| 网络行为 | 请求超时但服务端已成功，客户端重试 | 重复扣款 |
| 中间件行为 | MQ 至少一次投递、网关重试 | 重复发货、重复加积分 |

### 四种实现方案（来源：[[摘要-springboot接口幂等性4种策略]]）
| 方案 | 延迟 | 复杂度 | 外部依赖 | 适用场景 |
|------|------|--------|----------|----------|
| **Token 令牌** | 中 | 低 | Redis | 有预生成环节：下单、支付 |
| **数据库唯一索引** | 低 | 低 | 无 | 支付、注册 |
| **分布式锁** | 中 | 中 | Redis / ZK | 高并发抢券、秒杀 |
| **请求内容摘要** | 低 | 中 | Redis | 无预生成：转账、回调 |

#### ① Token 令牌
- 机制：预生成一次性令牌 → 请求携带 → 服务端**原子删除**，删成功才是首次
- 关键：`UUID` 保唯一、Redis `TTL` 防呆、`DELETE` 原子操作天然并发安全、Header 传参保持接口语义
- 适用：前端能配合"先取令牌再提交"的流程

#### ② 数据库唯一索引
- 机制：把业务唯一键（如支付流水号 `transaction_id`）做成唯一约束，重复写入抛 `DataIntegrityViolationException`
- 关键：**异常即幂等** —— catch 住后改为查询已存在记录并返回成功，用户体验丝滑
- 优势：数据库层面 100% 防重，**无外部依赖**，老系统改造成本最低
- 这是作者的**首选推荐**：有唯一业务键就不要上重型方案

#### ③ 分布式锁
- 机制：对"订单号/用户ID"加锁（Redisson `tryLock`），抢到锁后**先做业务幂等检查**（按 `requestId` 查记录）再执行
- 关键：lock + 幂等表 = **双保险**；`isHeldByCurrentThread()` 防误删他人锁；watchdog 自动续期
- 适用：高并发抢券、秒杀这类"同一资源被大量请求争抢"的场景
- 实现细节见 [[分布式锁]]、[[Redisson]]

#### ④ 请求内容摘要
- 机制：把请求体做 MD5/SHA256 作为幂等键，`setIfAbsent` 抢占，抢不到即判定重复
- 关键：**异常时回删键**，避免业务失败后合法重试被误杀；注解 + [[AOP]] 实现零侵入
- 优势：客户端无需任何改造，老接口加一行注解即可
- 风险：不同语义的请求若报文完全一致会被误判；需控制 TTL 窗口

### 选型判据（三步）
1. **有没有天然唯一业务键？** 有 → 唯一索引，收工
2. **前端能不能配合取令牌？** 能 → Token 方案，语义最清晰
3. **同一资源是否被并发争抢？** 是 → 分布式锁 + 幂等表
4. **只能看到请求本身、不能改客户端？** → 内容摘要 + AOP

> 通用原则：**不要过度设计**。能用唯一索引解决的，不要引入 Redis 与锁。

### 落地清单
- 梳理核心接口是否存在唯一业务键
- 幂等检查必须在**事务开始前**完成
- 幂等失败要打点告警（否则重复请求会被静默吞掉，问题被掩盖）
- 消息场景另有专门方案，见 [[重复消费解决方案]]
